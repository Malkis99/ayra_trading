# AYRA Trading — Supabase Instructions & Migration Setup

> **ВНИМАНИЕ / WARNING:** Внимательно проверьте SQL перед запуском в рабочей или тестовой базе данных Supabase!

## Порядок применения миграций (Migration Order)

1. Откройте **Supabase Dashboard** -> **SQL Editor**.
2. Скопируйте и выполните содержимое файла `supabase/migrations/0001_init.sql`.
   - Создаёт таблицу `public.profiles` с каскадным удалением от `auth.users`.
   - Настраивает триггеры для вычисления `minor_mode` и автоматического создания пустых профилей.
   - Включает RLS на всех таблицах и ограничивает UPDATE на уровне колонок для роли `authenticated`.
   - Создаёт RPC-функции `is_nickname_available` и `set_age_group`.
   - Создаёт резервные таблицы `telegram_identities` и `link_tokens` без политик (доступ закрыт по умолчанию).

3. Затем выполните `supabase/migrations/0002_profile_defaults.sql` (обязательно после 0001).
   - Исправляет падение регистрации нового пользователя: `minor_mode` больше не бывает NULL, пока возраст не выбран (ошибка 23502).
   - Сбой создания профиля больше не отменяет регистрацию в `auth.users` (в логах будет WARNING).
   - Создаёт пустые строки профиля пользователям, у которых их нет. Можно запускать повторно.
   - Проверка: `supabase/checks/0002_status.sql`. Тест (на тестовом проекте, всё откатывается): `supabase/tests/profile_defaults.sql`.
   - Локальная проверка без базы: `node scripts/test-migrations.mjs` (PGlite уже в devDependencies; эта проверка идёт и в CI).

4. Затем `supabase/migrations/0003_nickname_cooldown.sql` (после 0002). **Применяет владелец, только после подтверждения в PR.**
   - Добавляет колонку `profiles.nickname_changed_at` и триггер: ник можно сменить раз в 14 дней. Первый ник (в знакомстве) и первая смена после знакомства — сразу.
   - Дату пишет только сервер; клиент её изменить не может.
   - При нарушении правила обновление падает с кодом `P0001` и текстом `nickname_change_cooldown` — приложение показывает понятное сообщение.
   - Проверка: `supabase/checks/0003_status.sql` (обе колонки `true`). Тест на тестовом проекте (всё откатывается): `supabase/tests/nickname_cooldown.sql`.
   - Откат: `supabase/migrations/0003_nickname_cooldown.down.sql` (удаляет только колонку с датами и триггер, ники остаются).

## Проверка: применена ли миграция 0001

1. **Supabase Dashboard** → **SQL Editor** → **New query**.
2. Вставьте содержимое `supabase/checks/0001_status.sql` (только чтение, ничего не меняет) и нажмите **Run**.
3. Все колонки должны быть `true`. Если `profiles_table = false` — миграция не применена, выполните `0001_init.sql` (раздел выше). Файл можно запускать повторно: он использует `IF NOT EXISTS` / `OR REPLACE` / `DROP … IF EXISTS`.
4. Если таблица есть, раскомментируйте и выполните запрос 2: `users_without_profile` должно быть `0`. Если больше нуля (пользователи зарегистрировались до появления триггера), владелец может добавить им пустые строки:
   ```sql
   INSERT INTO public.profiles (id) SELECT id FROM auth.users ON CONFLICT (id) DO NOTHING;
   ```

**Как создаётся строка профиля.** Только сервером: триггер `on_auth_user_created` на `auth.users` вставляет пустую строку (`nickname = NULL`) при регистрации. Клиенту INSERT и DELETE запрещены (нет прав и политик), он только читает и обновляет свою строку (`auth.uid() = id`). Если строки нет, приложение считает это новым аккаунтом и ведёт на `/awakening`; если строки нет и после знакомства — показывает «Профиль не найден на сервере» вместо бесконечных переходов.

## Проверка RLS (Manual Verification)

1. Откройте **Supabase Dashboard** -> **SQL Editor**.
2. Вставьте содержимое `supabase/tests/rls.sql` и нажмите **Run**.
3. Убедитесь, что запросы выполняются успешно без ошибок синтаксиса и что изоляция пользователей соблюдается.

## Настройка шаблона писем (Email OTP Template Setup)

1. В **Supabase Dashboard** перейдите в раздел **Authentication** -> **Email Templates**.
2. Выберите шаблон **Magic Link** или **Confirm signup / OTP**.
3. Скопируйте HTML из файла `supabase/email-templates/otp.html` и вставьте его в редактор шаблона.
4. Сохраните изменения.

## Что делать, если вход не работает (Troubleshooting)

| Симптом | Возможная причина | Что проверить |
|---|---|---|
| Письмо с кодом не приходит | Достигнут лимит отправки писем (Rate limit) или не настроен SMTP-провайдер в Supabase | 1. Подождать 60 секунд.<br>2. В Supabase Dashboard -> Authentication -> Rate Limits / Provider settings.<br>3. Проверить папку Спам. |
| Ошибка «Неверный или просроченный код» | Код был введён с ошибкой или истёк срок жизни OTP (обычно 5–15 мин) | 1. Проверить правильность 6–8 цифр.<br>2. Запросить код повторно по кнопке.<br>3. Убедиться, что ссылка из письма открывается в том же браузере. |
| Ошибка сети или «вход недоступен» | Неверный адрес `NEXT_PUBLIC_SUPABASE_URL` или отсутствуют сетевые доступы | 1. Проверить `/api/health` для выявления статуса конфига.<br>2. Убедиться, что URL не содержит лишних путей `/rest/v1`.<br>3. Проверить доступность хоста Supabase. |
| Плашка «Ты на тестовом адресе» на `/login` | `location.origin` отличается от `NEXT_PUBLIC_SITE_URL` | 1. Для авторизации перейдите по ссылке на основной адрес.<br>2. Проверить значение `NEXT_PUBLIC_SITE_URL` в `.env.local`. |
| Регистрация падает, в Postgres Logs `null value in column "minor_mode"` (23502) | Не применена миграция 0002 | Выполнить `0002_profile_defaults.sql`, проверить `checks/0002_status.sql`. |
| Экран «Не удалось загрузить профиль» после входа | Таблица `profiles` не создана (HTTP 404, `PGRST205`), нет прав (HTTP 401/403, `42501`/`PGRST301`) или сбой сети | 1. Выполнить `supabase/checks/0001_status.sql`.<br>2. Посмотреть ответ запроса к `profiles` в DevTools → Network (статус и код ошибки). |
| Никнейм не сохраняется при входе | Локальный никнейм уже занят в базе данных | 1. Ввести другой никнейм на экране разрешения конфликта.<br>2. Убедиться в выполнении миграции `0001_init.sql` (RPC `is_nickname_available`). |

## Откат изменений (Rollback)

Для полной очистки базы данных и отката схемы выполните содержимое файла `supabase/migrations/0001_init.down.sql`.
