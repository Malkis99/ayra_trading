# Уведомления AYRA: бесплатная основа и дальнейший план

Issue #147; решения владельца от 4 ноября 2026 года. Статус — PR 1, а не вся система. Новые платные сервисы не подключаются. Ориентиры цен ниже — USD на дату исследования, без налогов; это не утверждённый бюджет.

## Реализовано в PR 1

- Колокольчик: личный inbox Supabase, счётчик, фильтр типов, «Все / Непрочитанные», явное прочтение, «Прочитать всё», постраничная загрузка.
- `/settings/notifications`: настройки аккаунта, матрица типов/каналов, важность, инструменты, тихие часы и часовой пояс.
- Таблицы `notifications`, `notification_settings`, `notification_preferences`; RLS, серверные read timestamps, атомарное сохранение настроек.
- История последних 90 дней. Физическая очистка — вместе с серверной обработкой на этапе 2.
- Простой реестр типов/каналов в коде. Без предварительного создания внешних очередей, price engine и мобильных токенов.

**Производителей событий пока нет.** Пустой центр — ожидаемое состояние. Матрица показывает «Скоро / Не подключено» и недоступные переключатели. Нет демонстрационных событий. Хранение начинает работать после ручного применения владельцем `0011_notifications.sql`. До этого интерфейс сообщает о незавершённой настройке сервера.

## Утверждённое поведение

- Общий выключатель подавляет новые необязательные события: рынок, цена, задания, серии, награды, журнал и другие продуктовые типы. История сохраняется.
- Критические `security_new_device` и `security_suspicious` обходят этот выключатель, важность и инструменты. Их канал сайта нельзя отключить даже прямым API-запросом. **Детекторы пока не подключены**, что явно указано в UI. Письма входа/восстановления — отдельная система.
- Открытие колокольчика не означает прочтение. «Прочитать всё» относится ко всей доступной личной истории, независимо от фильтра.
- Канал сайта по умолчанию включён для действующих типов. Внешние каналы по умолчанию выключены; требуют явного согласия, подключения и, для push, разрешения устройства.
- Тихие часы: локальные начало/конец и отдельная IANA-зона; поддерживаются полночь/DST. Равные начало и конец при включённом режиме запрещены как неоднозначные.
- В тихие часы inbox наполняется, внешняя доставка подавляется. Безопасное правило для необязательных типов — не отправлять накопленное после окончания тихих часов. Перенос продуктовых сообщений, утренние дайджесты и исключения критической безопасности для внешних каналов согласуем при реализации доставки. Просроченные рыночные напоминания не переносятся никогда.
- Фильтр инструментов применяется только к достоверно связанным событиям; общие экономические события не скрываются. Пустой выбор означает все инструменты, но не разрешение на price feed.
- Настройки не фильтруют старую историю задним числом. Они синхронизируются независимо от облака журнала: загрузка при входе/фокусе и раз в минуту в видимой вкладке, без обещания мгновенного Realtime. При несохранённых изменениях автоматическое чтение их не затирает.
- Срок отображения истории — 90 дней; физическая очистка позднее. Пользовательские DELETE права ограничены своими строками; автоматического удаления в PR 1 нет.
- Рыночные тексты нейтральны для всех возрастов, включая 16–17: без «купи / продай», с «Не является финансовой рекомендацией». Подробности сделок/P&L на lockscreen без отдельного решения не выводим.

## Этапы: один PR одновременно

Следующий PR начинается только после одобрения владельца и merge предыдущего. При необходимости этап делится на небольшие PR, сохраняя порядок.

| Этап | Функции | Условия |
|---|---|---|
| 1 — текущий | Центр, настройки, хранение/RLS | Ручная миграция владельцем; источников и отправки ещё нет |
| 2 | Календарь, actual/previous и пересмотр, напоминания 15/5 мин, официальные заявления, начало/конец сессий | Семантические события, серверные фильтры/дедуп, защита от backfill-спама, наблюдаемость и 90-дневная очистка |
| 3 | Web Push без стороннего платного сервиса | HTTPS, SW, VAPID, подписки устройств, явное разрешение, TTL/retries |
| 4 | Telegram собственного бота | BotFather владельцем, server-only токен, secret webhook, одноразовая привязка и подтверждение на сайте, отвязка/stop, throttle |
| 5 | Бесплатные ценовые алерты | Только инструменты с подтверждёнными коммерческими правами. Сейчас ни один feed не утверждён |
| 6 | Квесты, серия, награды, журнал, недельные итоги | Только достоверные данные. Игра пока локальная; надёжные события при закрытом сайте требуют согласованного серверного состояния |

Все исходные возможности сохранены: CPI/NFP/ВВП/PCE/решения ФРС и ЕЦБ, заявления Белого дома/ФРС/ЕЦБ, сессии, цена, продукт, безопасность и будущее сообщество. Лимиты алертов и частоты согласуются до price engine; прежние 5/50/200 в market-plan остаются заглушками.

## Источники и скорость

Этап 2 использует существующие `lib/market/feeds/*`, `market_events`, `market_news` и официальный collector. Виджеты TradingView не используются как API цен; обходы X/парсинг страниц не предлагаются.

Текущий news cron в репозитории — раз в 10 минут, release — раз в 2 минуты в UTC-окне; внутренний числовой retry первые часы — 10 минут. Для 10–20 секунд потребуется отдельный узкий fast path, lease и расчёт квот, а не только изменение cron. Это не часть PR 1. Расписание в файле не подтверждает активные production jobs.

BLS с ключом: 500 запросов/день, 50 рядов/batch. Окно ±5 мин: примерно 60 запросов при интервале 10 сек или 30 при 20. Историческое предупреждение о суточной задержке относится к v1; его не объявляем текущим SLA v2. Скорость источника, опрос, обработка и доставка измеряются отдельно. Для actual/previous нужны единицы, сезонность, release/vintage; официальные данные не заменяют consensus forecast.

[BLS FAQ](https://www.bls.gov/developers/api_faqs.htm), [BLS features](https://www.bls.gov/bls/api_features.htm), [Fed RSS](https://www.federalreserve.gov/feeds/feeds.htm), [ECB RSS](https://www.ecb.europa.eu/home/html/rss.en.html). Полноту White House RSS ещё проверяем. Часы сессий AYRA учитывают IANA/DST, но не являются полным биржевым праздничным календарём.

## Бесплатная доставка и ограничения

Собственная VAPID-отправка Web Push не требует покупки push-сервиса, но расходует compute/egress. На iPhone/iPad 16.4+ web app устанавливается на экран «Домой», затем запрашивает разрешение после действия пользователя. SW не выполняет постоянный мониторинг цен. [WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API).

Обычный Telegram Bot API не требует подписки; есть ограничения скорости, ориентировочно 30 сообщений/секунду массовой рассылки. Пользователь сначала должен начать разговор с ботом. Identity и private chat_id хранятся раздельно, username не является подтверждением. Токен не передаётся в чат/GitHub. [FAQ](https://core.telegram.org/bots/faq#how-do-i-avoid-hitting-limits), [deep links](https://core.telegram.org/bots/features#deep-linking).

«Бесплатно» — работа в имеющихся квотах без новых платных подписок, не безлимитность и не SLA. При нехватке лимитов автоматическую оплату не включаем; согласуем сокращение нагрузки или бюджет.

## Расширение без переделки основы

1. `lib/notifications/registry.ts`: стабильный код типа, группа, critical flag и capability. RU/EN — в существующих словарях. `available` включается только с настоящим производителем.
2. Матрица — строки `user/type/channel`, не новые boolean-колонки для каждого типа. Новый канал добавляется в реестр и при необходимости расширяет DB constraint небольшой миграцией.
3. `notifications` хранит личный snapshot payload и уникальный `(user_id,event_key,type_code)`. Клиент не создаёт контент. Неизвестный тип отображается нейтрально, не ломая список.
4. Производители этапа 2 применяют настройки и исключение критической безопасности на сервере; прежняя история не скрывается из-за выключателя.
5. При первой внешней доставке добавится очередь: задания на канал/адрес устройства, lease/TTL/retries/backoff/provider id. Inbox не является transport queue; клиентский outbox журнала не переиспользуется.
6. Перед отправкой перепроверяются consent, подключение, quiet hours, expiry/master. Exactly-once внешней доставки не обещаем. Секреты только на сервере.
7. Таблицы мобильных токенов, price evaluation и серверная экономика не создаются раньше своих этапов.

## Применение миграции 0011 владельцем

1. Проверить diff Draft PR, свежий `main` и свой журнал ручных SQL. `0006/0007` зарезервированы, `0011` свободна в проверенном main. Пустая `list_migrations` не доказывает отсутствие ручных изменений. При конфликте номера остановиться.
2. Сначала применить `supabase/migrations/0011_notifications.sql` через SQL Editor в отдельном тестовом проекте. Проверить выбранный проект. Секреты в чат не присылать.
3. Выполнить read-only `supabase/checks/0011_status.sql`: `tables=3`, `rls_enabled=3`, `save_function=true`, `client_can_forge_notification=false`, `client_can_change_payload=false`, `client_can_mark_read=true`, `anon_can_read=false`.
4. `supabase/tests/notifications_rls.sql` — только локальный PGlite/тестовый проект: содержит фикстуры auth и rollback. В production Auth этот тест не выполнять. Локально весь набор: `node scripts/test-migrations.mjs`.
5. После проверки и собственного одобрения применить тот же migration файл в нужном рабочем Supabase, сохранить запись о применении. Разработчик этого не делает. Миграция не включает jobs, очистку, отправку или платежи.
6. После обновления schema cache открыть `/settings/notifications`, сохранить настройки, перезагрузить. Тем же аккаунтом на втором устройстве проверить совпадение после загрузки/фокуса; облако журнала не влияет.
7. Другой аккаунт не видит личных настроек/сообщений; гость доступа не имеет. Пока источников нет, inbox пуст. Не вставлять тестовые рыночные события в production ради демонстрации.
8. При 42501/PGRST205 проверить проект, schema cache, Data API exposure/grants и status. Не отключать RLS для обхода ошибки.
