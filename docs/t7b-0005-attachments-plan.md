# 0005 — скриншоты сделок в облаке: план

Статус: **план принят** (2026-10-26). 0005-A: миграция применена и проверена владельцем. 0005-B: новые скриншоты в облаке — PR, ждёт «ок». 0005-C — после. Флаг не трогается.
Основа: `docs/t7b-sync-plan.md` (раздел 12: приватный bucket, подписанные ссылки), решения владельца (0005 обязателен до беты; лимиты на бету — **5 МБ на файл, 200 МБ на аккаунт**).

---

## 0. Как сейчас

- Скриншот хранится только в браузере (IndexedDB) того устройства, где его добавили. В сделке синхронизируется только список номеров скриншотов (`attachmentIds`).
- На другом устройстве вместо картинки — подпись «Скриншот хранится на другом устройстве» (сделано в 4f, исчезает сама, когда файл есть в облаке).
- **Обработка при добавлении уже есть** (`lib/journal/attachments/image-processor.ts`):
  - проверка формата по содержимому (PNG / JPEG / WebP; SVG и «замаскированные» файлы отклоняются);
  - на вход до 10 МБ и до 40 Мп;
  - перекодирование в **WebP**, не больше 1600 px по длинной стороне, качество 0,82, плюс превью 320 px;
  - обычный скриншот после этого — 100–400 КБ.

## 1. Хранилище и привязка к сделкам

### 1.1 Файлы

- **Отдельный приватный bucket** `journal-attachments` в Supabase Storage:
  - публичного доступа нет вообще;
  - **файл ≤ 5 МБ** — ограничение самого bucket;
  - разрешены только `image/webp`, `image/jpeg`, `image/png`.
- **Путь файла:** `<id пользователя>/<id скриншота>.webp`. Первая папка — всегда id владельца.
- **Права (политики Storage):** читать, загружать и удалять можно **только файлы в своей папке**. Загружать — только при включённом облаке (`cloud_sync`), как и записи журнала.
- **Показ на другом устройстве:**
  - файл скачивается по **подписанной ссылке на 60 секунд** и сразу кладётся в IndexedDB этого устройства;
  - дальше картинка показывается с устройства, ссылки нигде не хранятся;
  - чужой файл получить нельзя: ссылку выдаёт сервер только владельцу.
- **В облако идёт только основной файл (≤ 1600 px).** Превью делается на устройстве при скачивании — это экономит ~10 % места.

### 1.2 Привязка к сделкам — таблица `journal_attachments`

- Новая таблица по образцу девяти таблиц журнала из 0004: тот же триггер, «новее побеждает», мягкое удаление, те же права (только свои строки, запись — при включённом флаге).
- **В строке:** id скриншота, id сделки, тип (до входа / после / другое), подпись, ширина, высота, размер, хэш, путь файла, время изменения, отметка удаления.
- **Строки синхронизируются тем же движком, что и журнал:** очередь, повторы, «Автоматически / Вручную», конфликты (для подписи и типа).
- **Порядок:** сначала загружается файл, потом отправляется строка. Строка в облаке означает, что файл там уже есть.

### 1.3 Лимиты и сжатие

- **На входе** — как сейчас: до 10 МБ и 40 Мп, затем WebP 1600 px.
- **Если после сжатия файл всё ещё больше 5 МБ** (редкость: огромные подробные картинки):
  - вторая попытка — 1280 px, качество 0,7;
  - если и так больше 5 МБ, скриншот не добавляется, сообщение: «Скриншот слишком большой даже после сжатия (больше 5 МБ). Сделай скриншот части экрана или уменьши картинку.»
- **200 МБ на аккаунт — проверяет сервер** (правка а):
  - **правило загрузки в хранилище** отклоняет файл, если сумма размеров файлов в папке пользователя (только тех, чьи записи не удалены) вместе с новым файлом больше лимита;
  - **триггер на таблице `journal_attachments`** отклоняет запись, если сумма объявленных размеров живых записей больше лимита — это второй слой;
  - приложение проверяет то же заранее, только чтобы сразу показать понятное сообщение, а не отказ сервера;
  - удалённые скриншоты перестают учитываться сразу, хотя файл хранится ещё 30 дней (раздел 4).
- **Жёсткий потолок 400 МБ (2× лимита) — все файлы папки, включая ещё не убранные** (уточнение владельца 2026-10-26):
  - без него можно за 30 дней накопить больше 200 МБ: загрузил → удалил → место освободилось, а файл ещё лежит;
  - правило загрузки проверяет оба числа: занятое место (без файлов удалённых скриншотов) + новый файл ≤ 200 МБ **и** все файлы папки + новый файл ≤ 400 МБ;
  - файлы без записи (загрузка оборвалась) считаются в оба числа — их нельзя использовать, чтобы обойти лимит;
  - если упёрся в потолок, новые скриншоты остаются на устройстве (как при 200 МБ), место вернётся, когда уборка удалит файлы старше 30 дней;
  - потолок — строка `attachment_hard_cap_bytes` в `journal_limits`, меняется `UPDATE`;
  - проверочный запрос «сколько занято по пользователям»: `supabase/checks/attachments_usage.sql`.
- **Тип файла — тоже сервер:**
  - хранилище принимает только `image/webp`, `image/png`, `image/jpeg`;
  - правило загрузки проверяет тип ещё раз и размер ≤ 5 МБ;
  - прямой запрос с другим типом или больше лимита отклоняется (тесты, раздел 6.1).
- **Превышение лимита — ничего не теряется:**
  - скриншот сохраняется на устройстве, как сейчас, и виден на нём;
  - в «Облако и данные» и в панели значка облака: «Место для скриншотов в облаке закончилось (200 МБ). Новые скриншоты остаются на этом устройстве. Удали ненужные — освободится место»;
  - в карточке сделки: «Скриншот сохранён только на этом устройстве: в облаке нет места»;
  - когда место освободится, ждущие скриншоты загрузятся сами (в «Вручную» — по «Синхронизировать»).
- **Где задаются лимиты:**
  - 5 МБ — настройка bucket (меняется в панели Supabase, без миграции);
  - 200 МБ — одна строка в таблице лимитов `journal_limits` (меняется SQL-командой `UPDATE`, без миграции).
  - В приложении те же числа — константы в `lib/journal/cloud/config.ts`.

### 1.4 Скриншоты, которые уже есть на устройствах

- **После применения 0005 устройство с включённым облаком само находит** свои скриншоты, которых нет в облаке, и ставит их в очередь загрузки.
- **«Облако и данные» → блок «Скриншоты»:**
  - «В облаке: X из Y»;
  - прогресс загрузки «Загружено 12 из 40»;
  - кнопки **«Остановить»** (уже загруженное остаётся, продолжение не создаёт копий) и **«Продолжить»**;
  - неудачные загрузки повторяются с паузами (1 с / 5 с / 30 с / 2 мин / 5 мин, как у журнала); после нескольких неудач — строка «Не загрузились: N» и «Повторить».
- **Загрузка идёт в фоне**, по одному файлу, и не мешает работе. Закрыли вкладку — продолжится при следующем открытии.
- **Если старых скриншотов больше, чем 200 МБ:** загружаются, пока есть место, остальные остаются на устройстве с сообщением из 1.3.
- **Перенесённые из гостя скриншоты** (вариант А) загружаются так же.

## 2. «Автоматически / Вручную»

| | Автоматически | Вручную |
|---|---|---|
| Новый скриншот | загружается сам через несколько секунд | ждёт «Синхронизировать»; в «Облако и данные» и в панели значка — «Ждёт отправки», файлы учитываются в числе |
| Старые скриншоты (1.4) | загружаются в фоне сами, с прогрессом | загружаются по «Синхронизировать», с тем же прогрессом и «Остановить» |
| Скриншот с другого устройства | при открытии карточки сделки скачивается сам | в карточке — «Скриншот в облаке» и кнопка «Загрузить»; само не скачивается |
| Изменение подписи / типа, удаление | уходит само | по «Синхронизировать» |

Значок облака учитывает файлы: «Сохранено в облаке» — только когда и записи, и файлы в облаке.

## 3. Как исчезает подпись «Скриншот хранится на другом устройстве»

Сейчас подпись показывается, когда номера скриншота нет ни на устройстве, ни в «облачном хранилище» (в 4f это заглушка, которая всегда отвечает «нет»). В 0005 заглушка заменяется проверкой строк `journal_attachments`. Код подписи не меняется — это и было задумано.

| Где файл | Что видно в карточке сделки |
|---|---|
| на этом устройстве | картинка, как сейчас |
| только в облаке, «Автоматически» | «Загружается из облака…», затем картинка |
| только в облаке, «Вручную» | «Скриншот в облаке» + «Загрузить» |
| ни здесь, ни в облаке (ещё не загружен с другого устройства) | **«Скриншот хранится на другом устройстве»** — как сейчас |

Как только второе устройство загрузит файл, подпись на первом сама сменится на картинку при следующем обмене.

## 4. Удаление (правки б, в)

**Файл никогда не удаляется сразу.** Удаляется только запись (мягко, с отметкой времени), файл — не раньше чем через **30 дней**. Это гарантирует **правило удаления в хранилище на сервере**, а не только приложение.

- **Удалён скриншот, сделка или счёт со сделками:**
  - запись скриншота помечается удалённой (`deleted_at`), это уходит в облако;
  - файл остаётся в облаке 30 дней;
  - на другом устройстве копия убирается из IndexedDB при следующем обмене.
- **«Отменить» и восстановление:**
  - если сделку или скриншот вернули (запись снова живая), файл на месте, ничего не скачивается заново;
  - то же при конфликте «удалили против правки» с выбором версии с правкой — запись живая, файл на месте.
- **Через 30 дней:** при ежесуточной уборке устройство удаляет файлы, чьи записи удалены больше 30 дней назад. Раньше сервер удалить не даст.
- **Уборка «мусора» — файлы без записи** (например, сбой между загрузкой файла и отправкой записи). Удаляются только файлы:
  - **старше 24 часов** — свежий файл ждёт свою запись, которая ещё может уйти;
  - **только в папке своего пользователя.**
  - Оба условия проверяет правило удаления на сервере.
- **Файл с живой записью удалить нельзя вообще** — сервер откажет.
- **«Выйти и удалить данные аккаунта с этого устройства»:**
  - удаляются только копии на устройстве, облако не трогается;
  - в предупреждении учитываются скриншоты, которые ещё не загружены: «3 скриншота ещё не в облаке».
- **Удаление аккаунта (T7d, следующий шаг):**
  - все файлы папки пользователя и все записи удаляются на сервере ключом сервиса — правила хранилища на это не распространяются;
  - каскадного удаления файлов при удалении пользователя в Supabase нет, поэтому это отдельный шаг в T7d.

## 5. Миграция 0005

**Что создаёт** (`supabase/migrations/0005_journal_attachments.sql`, повторный запуск безопасен):
1. **Таблица `public.journal_attachments`** — как таблицы журнала из 0004: триггер «новее побеждает», RLS, права. Удаление с клиента запрещено (только мягкое).
   - **Дополнительный триггер:** `bytes` ≤ 5 МБ, тип из трёх разрешённых, сумма живых записей пользователя ≤ лимита.
2. **Таблица `public.journal_limits`** (одна строка): `attachment_quota_bytes = 209715200` (200 МБ), `attachment_file_bytes = 5242880` (5 МБ), `attachment_delete_after_days = 30`, `orphan_min_age_hours = 24`.
   - Читать может вошедший пользователь, менять — только ты, SQL-командой `UPDATE` (без миграции).
3. **Bucket `journal-attachments`:** приватный, `file_size_limit = 5242880`, `allowed_mime_types = {image/webp, image/png, image/jpeg}`.
4. **Правила доступа `storage.objects`** для этого bucket:
   - **чтение (SELECT):** только файлы в своей папке;
   - **загрузка (INSERT):** только в свою папку, облако включено, тип из трёх разрешённых, размер ≤ 5 МБ, сумма живых файлов вместе с новым ≤ лимита;
   - **изменение (UPDATE):** не разрешено никому — файл не меняется, новая версия — новый файл;
   - **удаление (DELETE):** только в своей папке и только если запись этого файла удалена больше 30 дней назад, **или** записи нет совсем и файлу больше 24 часов.

Готовый SQL с пояснением каждого правила по-русски, проверочный запрос и откат будут в описании PR 0005-A **до того, как ты его применишь**.

**Как применяешь ты (после слияния PR с миграцией, до PR с кодом):**
1. Supabase → SQL Editor → вставить весь файл `0005_journal_attachments.sql` → Run. Ответ — без ошибок.
2. Проверка: `supabase/checks/0005_status.sql`. Ожидается одна строка:
   - `attachments_table = true`, `rls_enabled = true`;
   - `bucket_private = true`, `bucket_size_limit = 5242880`, `bucket_mime_types = {image/jpeg,image/png,image/webp}`;
   - `storage_policies = 3` (чтение, загрузка, удаление; изменения нет), `quota_bytes = 209715200`, `delete_after_days = 30`, `orphan_min_age_hours = 24`;
   - `quota_trigger = true`;
   - `client_delete_grants = 0`.
3. Ничего в существующих данных не меняется: таблицы журнала, профили, флаги — как были.

**Откат** (`0005_journal_attachments.down.sql`):
- удаляет политики Storage, таблицы `journal_attachments` и `journal_limits`;
- **bucket удаляет, только если он пустой.** Если в нём уже есть файлы, откат останавливается с сообщением — файлы не удаляются без твоего отдельного решения;
- журнал, профили и флаг `cloud_sync` откат не трогает;
- проверка после отката — тот же `0005_status.sql`: `attachments_table = false`, `bucket_private = null`.

## 6. Тесты, риски, разбивка на PR

### 6.1 Тесты

- **Миграция (PGlite, в CI):**
  - применяется дважды;
  - тестовый SQL проверяет: чужие строки не видны и не пишутся; без флага запись запрещена; «новее побеждает»; удаление с клиента запрещено;
  - откат убирает всё и не трогает 0001–0004.
  - Storage в PGlite нет — для политик используется заглушка схемы `storage` (таблица объектов, функция папки), как заглушка `auth` сейчас. На ней проверяются прямые запросы в обход приложения:
    - загрузка в чужую папку, без флага, с типом `image/gif`, больше 5 МБ, сверх 200 МБ — **отклоняются**;
    - удаление файла с живой записью — отклоняется;
    - удаление файла, чья запись удалена 10 дней назад, — отклоняется; 31 день назад — разрешено;
    - запись удалили и вернули («Отменить») — удаление снова отклоняется;
    - файл без записи, загруженный 1 час назад, — удаление отклоняется; 25 часов назад — разрешено;
    - удаление в чужой папке — отклоняется всегда;
    - триггер `journal_attachments`: запись сверх лимита или с неверным типом — отклоняется.
- **Юнит:**
  - сжатие со второй попыткой и отказ больше 5 МБ;
  - проверка квоты;
  - очередь файлов (повторы, остановка, продолжение без копий);
  - правило подписи (таблица из раздела 3);
  - изоляция двух аккаунтов: файлы и строки одного не попадают в очередь другого.
- **e2e на фейковом Supabase** (в фейковый сервер добавляется Storage: загрузка, скачивание по подписанной ссылке, удаление, лимит размера, квота):
  - два устройства: скриншот на A → на B картинка (Автоматически) / «Загрузить» (Вручную);
  - старые скриншоты: прогресс, «Остановить», «Продолжить» без копий, повтор после ошибки сервера;
  - квота: превышение → сообщение, файл остался на устройстве, после удаления других — загрузился;
  - удаление скриншота и сделки → картинка исчезла на втором устройстве, **файл в облаке остаётся** (30 дней);
  - удалил → «Отменить» → файл на месте, картинка видна на обоих устройствах;
  - конфликт «удалили против правки» → «Взять из облака» с правкой → файл на месте;
  - уборка: свежезагруженный файл без записи не удаляется, файл старше 24 часов без записи — удаляется;
  - **превью на втором устройстве:** после скачивания строится маленькая копия и показывается в списке скриншотов сделки;
  - флаг выключен → ни одного обращения к Storage; гость → тоже;
  - 360 и 1440 px.

### 6.2 Риски

| Риск | Что делаем |
|---|---|
| Файл загрузился, а строка нет (сбой между шагами) | при следующем обмене строка отправляется; файлы без строк старше 24 часов убирает суточная уборка (раздел 4) |
| Удаление по ошибке или конфликт «удалили против правки» | файл живёт 30 дней после удаления записи; удалить раньше не даст сервер |
| Квота в настоящем Supabase: размер **загружаемого** файла правилу хранилища не виден (проверено владельцем 2026-10-26: при лимите 0 первый файл в пустой папке проходит, второй отклоняется) | лимиты 200 и 400 МБ могут быть превышены на один файл (≤ 5 МБ — этот предел bucket проверяет сам); одновременные загрузки в обход приложения — риск закрытой беты, контроль запросом `attachments_usage.sql`; усиление — триггер на файлах (предложение владельцу, отдельная миграция) |

## 8. Правки владельца (2026-10-26)

а) Лимит 200 МБ проверяет сервер (правило загрузки и триггер), тип файла ограничен изображениями на уровне bucket. Тест: прямой запрос сверх лимита или с другим типом отклоняется.
б) Файлы удаляются не раньше чем через 30 дней после мягкого удаления записи. Тест: удалил → отменил → файл на месте; конфликт с выбором версии с правкой → файл на месте.
в) Уборка файлов без записи — только старше 24 часов и только в своей папке. Тест: свежий файл без записи не удаляется.
г) Жёсткий потолок 2× лимита (400 МБ) с учётом ещё не убранных файлов — решение дешёвое, сделано в 0005-A (раздел 1.3).
