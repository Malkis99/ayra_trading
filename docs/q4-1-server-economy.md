# Q4.1 — Серверная экономика: схема и безопасность

**Статус.** Проектирование. Миграция `supabase/migrations/0014_game_economy.sql` лежит в репозитории, проверяется в CI на PGlite и на настоящем PostgreSQL 16 (задача `db-concurrency`) и **не применяется к production**.
- `game_sync` остаётся выключенным у всех.
- Ни один аккаунт не выходит из состояния `local`.
- Реальные XP и Coins не переносятся.

Основание: аудит Q4.0 и решения владельца для Q4.1:
- **В-25** — Next.js/Vercel + PostgreSQL;
- XP, Coins и награды — только сервер после миграции аккаунта;
- время и игровой день — серверные;
- клиент не передаёт сумму;
- начисления идемпотентны;
- **В-24** — на всех устройствах;
- никаких выплат задним числом.

**Номер миграции.** В прежних планах серверная экономика называлась «0007». Номера 0006 и 0007 не использованы, а 0008–0013 уже применены, поэтому файл назван `0014`: так порядок применения совпадает с номерами.

## 1. Схема

| Объект | Назначение | Гарантии |
|---|---|---|
| Роль `game_economy_owner` | Владелец всех таблиц и функций экономики | `NOLOGIN`, ни одна роль API (`anon`, `authenticated`, `service_role`) не входит в неё (раздел 2) |
| `user_features.game_sync` | Флаг включения, `FALSE` по умолчанию | Выключение **приостанавливает** серверные начисления и не возвращает локальные |
| `game_accounts` | Состояние экономики аккаунта: `local → migration_pending → cloud_active` | Триггер `game_account_state_guard`: из `cloud_active` назад нельзя никому, даже владельцу; `activated_at` не меняется |
| `game_award_kinds` | Виды начислений и их выключатель | **Все выключены** после установки; кроме `mission`, любой вид отклоняется кодом даже включённым, пока для него нет серверной проверки (раздел 3) |
| `game_reward_rules` | Суммы и лимиты (миссия 40 + 10, вариант C, ежедневная награда, самоотчёты) | Правило выбирает **сервер** по виду начисления, клиент его не называет; повторный запуск миграции не затирает правки владельца |
| `game_mission_sources` | Какие записи Журнала доказывают какую миссию (таблица и часть записи) | Заметка не доказывает разбор сделки, план — урок и т. д. |
| `game_limits` | Лимит Coins в день (100), окно поздних начислений (0 — решение В-28) | Одна строка |
| `game_ledger` | Журнал начислений | `UNIQUE (user_id, idempotency_key)`; формат ключа проверяется; `xp`, `coins` ≥ 0; UPDATE запрещён всем, включая владельца; DELETE — только в контексте владельца (каскад удаления аккаунта) |
| `game_source_claims` | Какая запись Журнала уже оплатила миссию в этот день | PK `(user_id, scope, source_key, game_day)`: одна запись (или её часть) — одна оплата на все устройства |
| `game_profile` | Проекция: всего XP, уровень, Coins, последняя учтённая строка, версия | Пишут только функции; пересобирается из журнала |
| `game_level_for_xp()` | Уровень по сумме XP | Та же формула, что `xpForNextLevel` (80 + 40·n), проверено тестом |
| `game_day_for()` | Игровой день: серверное время в поясе `profiles.timezone` | — |
| `game_apply_reward(user, kind, item, evidence)` | **Единственный** способ начислить | Только `service_role`; ключ, правило и источники строит сама функция (раздел 3) |
| `game_rebuild_profile()` | Пересборка проекции из журнала | Только `service_role` |
| `game_begin_migration()`, `game_activate_cloud()` | Переходы состояния | Только `service_role`; активация создаёт пустую проекцию, **XP не переносит** |
| `game_account_status()` | Своё состояние и флаг | Только `authenticated`, только о себе (`auth.uid()`) |

## 2. Кто может писать (исправление security review, задача 1)

**Что было не так в первой версии.** Триггер `game_writer_only` пропускал запись, если в сессии стояла настройка `ayra.game_writer = on`. Эту настройку может поставить кто угодно (`SET` / `set_config`), а у `service_role` был `GRANT ALL`. Значит, сервисный ключ мог записать любое начисление в обход функций.

**Новая модель — три независимых слоя:**

1. **Привилегии.** У `anon`, `authenticated` и `service_role` нет ни одного права `INSERT / UPDATE / DELETE / TRUNCATE` ни на одной таблице экономики. Клиент читает только свои строки (RLS), `service_role` — читает всё. Без прав запись отклоняется самим Postgres до любых триггеров.
2. **Владелец.** Таблицы и функции начисления принадлежат роли `game_economy_owner` (`NOLOGIN`). Функции объявлены `SECURITY DEFINER` и выполняются с правами владельца. Войти в эту роль API не может: ни одна роль API не является её членом, поэтому `SET ROLE game_economy_owner` от `service_role` даёт `permission denied` (проверено на настоящем Postgres через роль входа `authenticator`, как в Supabase).
3. **Триггер-страж** `game_owner_only` на всех восьми таблицах: запись проходит, только если `current_user = 'game_economy_owner'`. `current_user` нельзя подменить через `SET` / `set_config`, а сменить его на владельца может только член роли. Этот слой ловит ручной SQL администратора (суперпользователь проходит проверку прав, но не триггер).

**Что мы не используем как доказательство:** ни настройки сессии (GUC), ни `pg_trigger_depth()`, ни сам факт `SECURITY DEFINER`.

**Права самого владельца — минимальные:**
- чтение `profiles` (часовой пояс) и `user_features` (флаг);
- чтение таблиц Журнала и `UPDATE (device_id)` только ради блокировки `FOR SHARE`. Политика `WITH CHECK (FALSE)` не даёт владельцу реально изменить Журнал.

**Настройки** (`game_award_kinds`, `game_reward_rules`, `game_mission_sources`, `game_limits`) меняются только так: администратор выполняет `SET ROLE game_economy_owner` в SQL-редакторе Supabase (роль `postgres` — член владельца). Это ручное действие с вашего разрешения, не API.

## 3. Протокол начисления и авторизация (задача 2)

```
Клиент ── «проверь миссию m_lesson» ──▶ Next.js route (app/api/game/*, Q4.2)
  1. Пользователь — только из проверенной сессии (supabase.auth.getUser на сервере). user_id из тела запроса игнорируется.
  2. Чтение записей Журнала из облака (service_role) с версией и отпечатком, которые считает сам Postgres:
       SELECT data, client_updated_at, md5(data::text) AS fp FROM journal_notes WHERE user_id = $uid AND …
  3. Проверка правил миссии на TypeScript (lib/missions.ts) — те же модули, что в приложении.
  4. Вызов game_apply_reward(uid, 'mission', 'm_lesson', evidence = [{table, id, version, fp}]).
     Клиент и маршрут НЕ передают: сумму, правило, ключ идемпотентности, игровой день, ключ источника.
Postgres, одна транзакция (с правами владельца):
  a. item — только [A-Za-z0-9_.-]{1,80} (нельзя протащить двоеточие и собрать чужой ключ); не более 5 доказательств.
  b. Вид начисления: неизвестный → game_unknown_kind; не реализован → game_kind_not_implemented; выключен → game_kind_disabled.
  c. Аккаунт в cloud_active и флаг включён (иначе game_account_not_active / game_sync_paused).
  d. SELECT … FROM game_profile WHERE user_id = uid FOR UPDATE — все начисления пользователя идут по очереди.
  e. Игровой день = game_day_for(uid) по серверному времени. Ключ = 'mission:' || день || ':' || item строит функция.
     Ключ уже есть → вернуть сохранённый result (replay: true) и ничего не начислять.
  f. Миссия должна быть в game_mission_sources (иначе game_unknown_mission); без доказательств → game_evidence_required.
  g. Каждое доказательство: таблица должна подходить этой миссии (иначе game_evidence_type);
     SELECT client_updated_at, deleted_at, md5(data::text) … WHERE user_id = uid AND id = … FOR SHARE;
     нет строки (или чужая) → game_evidence_missing; удалена / другая версия / другой отпечаток → game_evidence_changed.
     Ключ источника = таблица:id:часть — строит функция.
  h. Лимиты дня на заблокированной проекции: 3 миссии → game_day_cap; Coins (100) урезаются.
  i. INSERT в game_ledger (result в строке), INSERT в game_source_claims (занято → game_source_used), UPDATE game_profile.
```

**Почему между проверкой и начислением ничего не меняется:**
- маршрут проверил запись в версии `V` с отпечатком `fp`;
- транзакция блокирует эту строку `FOR SHARE`: изменение Журнала ждёт конца начисления (проверено на настоящем Postgres, PG-E1);
- если Журнал меняют раньше, начисление ждёт его и затем отказывает (PG-E2);
- сравниваются и версия, и отпечаток. Отпечаток нужен, потому что Журнал принимает запись с **тем же** `updatedAt` как повтор, то есть содержимое может измениться без смены версии (тест X1);
- при несовпадении начисления нет, код `40001`: маршрут перечитывает Журнал и проверяет заново.

**Разделение ответственности:**

| Проверка | Где | Почему там |
|---|---|---|
| Кто пользователь | Next.js (сессия) | Postgres не видит cookie сессии; функция недоступна клиенту |
| Смысл записи (текст не пустой, урок действительно урок, правило миссии выполнено) | Next.js (`lib/missions.ts`) | Те же модули, что в приложении; в SQL не дублируем |
| Сумма, правило, ключ, игровой день | PostgreSQL | Не доверяем никому снаружи |
| Тип доказательства для миссии | PostgreSQL (`game_mission_sources`) | Маршрут с ошибкой не сможет оплатить урок сделкой |
| Запись существует, принадлежит пользователю, не изменена | PostgreSQL (`FOR SHARE` + версия + отпечаток) | Защита от гонки «проверил — изменили — оплатил» |
| Одна запись — одна оплата, повтор, лимит дня | PostgreSQL (ключи, PK, блокировка проекции) | Работает на всех устройствах и при параллельных запросах |

**Что безопасно и что нельзя включать до серверной проверки:**

| Вид | Статус в 0014 | Почему |
|---|---|---|
| `mission` | Реализован, **выключен** (`enabled = FALSE`). Включается только вашим решением в Q4.2 | Доказательство — запись Журнала, тип и неизменность проверяет SQL |
| `personal_quest` | **Отклоняется** (`game_kind_not_implemented`) даже если включить | Нужна серверная проверка завершения прохождения (В-24, распределение записей) — Q4.6 |
| `self_report` | Отклоняется | Нужно решение о правилах (вопрос 3) и сервер, ведущий самоотчёты — Q4.4 |
| `daily_reward` | Отклоняется | Нужен серверный счётчик серии — Q4.3 |
| `first_action` | Отклоняется | Нужен список «первых действий» и их доказательств |
| `journal_xp`, `achievement` | Отклоняется | Нужны свои правила проверки |

Чтобы разрешить новый вид, недостаточно поставить `enabled = TRUE`. Нужна новая миграция с ветвью проверки в `game_apply_reward` и тестами для неё.

## 4. Что не может сделать клиент и сервисный ключ

| Попытка | Почему не выйдет | Тест |
|---|---|---|
| Клиент увеличивает XP, Coins, уровень | Нет прав UPDATE | U6, W0 |
| Клиент записывает оплаченную миссию или квест | Нет прав INSERT; функция начисления только у сервера | U4, U11 |
| Запись от имени другого `user_id` | RLS + нет INSERT; доказательства чужого пользователя не находятся | U5, T9 |
| Изменить правила или своё состояние | Нет прав | U9, U10, U12 |
| Читать чужой журнал или проекцию | RLS по `auth.uid()` | U14, U15 |
| Сервисный ключ ставит старую метку `ayra.game_writer` и пишет в журнал | Нет прав INSERT у `service_role` | W1, PG-F2 |
| Сервисный ключ правит проекцию, включает вид, добавляет миссию, удаляет журнал | Нет прав | W2–W5 |
| Сервисный ключ становится владельцем | Не член роли: `permission denied to set role` | W6, PG-F1 |
| Ручной SQL администратора в обход функций | Триггер `game_owner_only` | W7, W8 |
| Владелец меняет строку журнала | UPDATE журнала запрещён всегда | W9 |
| Миссия без доказательства | `game_evidence_required` | T4 |
| Выдуманная миссия при допустимом правиле | `game_unknown_mission` | T5 |
| Ключ, собранный вручную (`m_lesson:2026-01-01`) | Формат item без двоеточия | T6 |
| Доказательство другого типа (заметка для разбора сделки) | `game_evidence_type` | T7 |
| Повторная оплата той же записи под другой миссией | `game_source_used` | T8, T12, PG-B |
| Обход лимита другим правилом | Правило выбирает сервер по виду; лимит общий на `mission` | T11, PG-C |
| Невыполненное прохождение личного квеста | Вид `personal_quest` отклоняется целиком | F2 |

## 5. Состояние аккаунта

```
local ──begin──▶ migration_pending ──activate──▶ cloud_active (навсегда)
  ▲                    │
  └──── (отмена до активации — Q4.5, решение) ┘
```

- **`local`** (сейчас у всех): экономика на устройстве, как сегодня. Сервер ничего не начисляет.
- **`migration_pending`**: перенос в работе. Сервер не начисляет. Приложение **не начисляет и локально** — правило для Q4.5, чтобы во время переноса не появилось «третьего» прогресса.
- **`cloud_active`**: источник истины — сервер. Обратного перехода нет (триггер), даже для владельца.
- **Флаг `game_sync`** включает начисления только у `cloud_active`. Выключение = пауза: сервер отвечает `game_sync_paused`, а приложение, прочитав состояние `cloud_active` (`game_account_status()`), **не возвращается** к локальным начислениям. Правило для клиента (Q4.4): локальные начисления разрешены только при `state = local`.

## 6. Перенос XP (только проектирование)

**Автоматически ничего не переносится:**
- `game_activate_cloud()` создаёт пустую проекцию;
- правила для «legacy» в таблице нет, поэтому функция начисления не может записать перенесённый XP;
- непроверяемый XP не утверждается автоматически.

**План Q4.5 (на согласование):**
1. Снимок `GameState` устройства в карантинную таблицу `game_imports`: на баланс не влияет, повтор не создаёт копий.
2. Разбор снимков на кандидатов с **теми же ключами**, что у новой системы:
   - `mission:<day>:<id>` — из истории и журнала источников;
   - `daily:<day>`, `first:<kind>`;
   - `pq:<runId>` — только `paid: true`.
3. Объединение устройств по ключу: дубли отбрасываются.
4. Экран предпросмотра: что переносится, что отброшено и почему.
5. Непроверяемый остаток (старые версии без истории) — отдельной строкой `legacy:<userId>` **только после вашего решения** о способе подсчёта и подтверждения человеком.

**Тестовые сценарии Q4.5:**
- два устройства с одной миссией одного дня → одна строка;
- завершение QH-8.4 без `paid` → не оплачивается;
- оплаченное QH-8.5 → строка `pq:<runId>` без повторной выплаты;
- повторный импорт → ничего нового;
- повреждённый снимок → отклонён целиком, без частичного переноса;
- Coins — по правилу 2026-10-27: пересчёт из данных, а не перенос числа.


## 7. Удаление (задача 3)

**Что было не так.** Первая версия разрешала DELETE из журнала, если `pg_trigger_depth() > 0`, то есть из **любого** вложенного триггера. Посторонний триггер на другой таблице мог стереть историю.

**Сейчас:**
- В обычной работе журнал только дополняется: UPDATE запрещён всем, DELETE — всем, кроме владельца, а у владельца нет функции, которая удаляет строки журнала.
- **Удаление аккаунта** (`DELETE FROM auth.users`, как делает Supabase) запускает каскад внешних ключей. Каскадное удаление Postgres выполняет от имени **владельца таблицы, которая ссылается** (`game_ledger` и другие принадлежат `game_economy_owner`). Поэтому страж пропускает именно этот путь.
- Посторонний вложенный триггер работает от имени вызвавшего, а не владельца. Он отклоняется (тесты DEL1 на PGlite и PG-G1 на Postgres): история цела.
- После удаления аккаунта не остаётся ни журнала, ни проекции, ни источников, ни состояния; у других аккаунтов всё на месте (D3, D4, PG-G2).

**Юридический вопрос** о хранении истории начислений после удаления аккаунта остаётся открытым (вопрос 10). Если понадобится хранить обезличенную копию, это будет отдельная таблица-архив с отдельной функцией владельца, а не ослабление стража.

## 8. Параллельные запросы на настоящем PostgreSQL (задача 4)

`scripts/test-concurrency.sh` и CI-задача `db-concurrency`:
- PostgreSQL 16 в служебном контейнере GitHub Actions;
- `psql`, который уже есть на сервере CI: **новых зависимостей нет**;
- скрипт отказывается работать, если `PGHOST` не `localhost`, и создаёт свою временную базу. До Supabase и production он не дотягивается.

Сессии запускаются одновременно: все ждут общую рекомендательную блокировку и стартуют в один момент.

| Проверка | Сценарий | Ожидание |
|---|---|---|
| PG-A | Один ключ идемпотентности из 10 сессий | 1 начисление + 9 повторов того же результата; 1 строка журнала; проекция 40/10, версия 1 |
| PG-B | Одна запись Журнала для 5 разных миссий в 8 сессиях | 1 начисление; остальные `game_source_used` |
| PG-C | 5 разных миссий с разными записями сразу, лимит 3 | Ровно 3 начисления (120 XP, 30 Coins, уровень 2), 2 × `game_day_cap` |
| PG-D1 | 10 одновременных активаций аккаунта в переносе | Все `cloud_active`, одна проекция |
| PG-D2 | 5 одновременных попыток вернуть `cloud_active` в `local` от владельца | Все отклонены `game_state_one_way` |
| PG-E1 | Начисление держит запись; Журнал меняют в это время | Изменение ждёт конца начисления; оплачена ровно проверенная версия |
| PG-E2 | Журнал меняют первым; начисление с прежним доказательством | Начисление ждёт, затем `game_evidence_changed`, ничего не записано |
| PG-F1 | Роль входа `authenticator` → `service_role` → `SET ROLE game_economy_owner` | `permission denied to set role` |
| PG-F2 | `service_role` ставит `ayra.game_writer = on` и вставляет в журнал | `permission denied for table game_ledger` |
| PG-G1 | Посторонний вложенный триггер удаляет журнал | `game_write_only_through_functions`, история цела |

## 9. Модель угроз

| Угроза | Мера | Тест |
|---|---|---|
| Второе устройство или вкладка оплачивает то же | Ключ идемпотентности, PK источников, блокировка проекции | T2, PG-A, PG-B |
| Запись Журнала изменена между проверкой и начислением | `FOR SHARE` + версия + отпечаток | X1–X3, PG-E1, PG-E2 |
| Чужая запись Журнала как доказательство | Поиск только по `user_id` начисления | T9 |
| Подмена суммы, правила или ключа | Всё строит SQL по виду и миссии | T1, T5, T6 |
| Перевод часов | Серверное время и день | D1, D2 |
| Обход лимитов параллельными запросами | Лимиты считаются под `FOR UPDATE` проекции | T11, PG-C |
| Утечка или злоупотребление сервисным ключом | Нет прав записи; войти во владельца нельзя; сервис может только вызвать функцию, которая сама проверяет доказательства | W0–W6, PG-F1, PG-F2 |
| Ручная правка истории администратором | Страж владельца; UPDATE журнала запрещён всем | W7–W9 |
| Посторонний триггер стирает историю | Удаление только в контексте владельца | DEL1, PG-G1 |
| Включение вида без серверной проверки | Код отклоняет нереализованные виды | F2 |
| Возврат к локальным начислениям выключением флага | Флаг — пауза; `cloud_active` необратим | S6–S8, PG-D2 |
| Порча проекции | Пересборка из журнала | R1 |
| Удаление аккаунта | Каскад от имени владельца | D3, D4, PG-G2 |
| Утечка сервисного ключа из браузера | Ключ только в `app/api/**/route.ts` (защита T7a), в Vercel env | — (политика) |
