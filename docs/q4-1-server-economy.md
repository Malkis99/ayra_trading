# Q4.1 — Серверная экономика: схема и безопасность

**Статус.** Проектирование. Миграция `supabase/migrations/0014_game_economy.sql` лежит в репозитории, проверяется в CI на PGlite и **не применяется к production**.
- `game_sync` остаётся выключенным у всех.
- Ни один аккаунт не выходит из состояния `local`.
- Реальные XP и Coins не переносятся.

Основание: аудит Q4.0 и решения владельца для Q4.1:
- **В-25** — Next.js/Vercel + PostgreSQL;
- XP, Coins и награды — только сервер после миграции аккаунта;
- время и игровой день — серверные;
- клиент не передаёт сумму;
- начисления идемпотентны;
- **В-24** — на всех устройствах;
- никаких выплат задним числом.

**Номер миграции.** В прежних планах серверная экономика называлась «0007». Номера 0006 и 0007 не использованы, а 0008–0013 уже применены, поэтому файл назван `0014`: так порядок применения совпадает с номерами.

## 1. Схема

| Объект | Назначение | Гарантии |
|---|---|---|
| `user_features.game_sync` | Флаг включения, `FALSE` по умолчанию | Выключение **приостанавливает** серверные начисления и не возвращает локальные |
| `game_accounts` | Состояние экономики аккаунта: `local → migration_pending → cloud_active` | Триггер `game_account_state_guard`: из `cloud_active` назад нельзя, даже `service_role`; `activated_at` не меняется |
| `game_reward_rules` | Суммы и лимиты (миссия 40 + 10, вариант C, ежедневная награда, самоотчёты) | Запрос называет **правило**, а не сумму; повторный запуск миграции не затирает правки владельца |
| `game_limits` | Лимит Coins в день (100), окно поздних начислений (0 — решение В-28) | Одна строка |
| `game_ledger` | Журнал начислений | `UNIQUE (user_id, idempotency_key)`; формат ключа проверяется; `xp`, `coins` ≥ 0; триггер `game_ledger_immutable` запрещает UPDATE всегда и DELETE, кроме каскада удаления аккаунта; триггер `game_writer_only` — вставка только из функций |
| `game_source_claims` | Какая запись Журнала уже оплатила миссию или личный квест в этот день | PK `(user_id, scope, source_key, game_day)`: одна запись — одна оплата в своей области на все устройства (миссии; В-24 для квестов) |
| `game_profile` | Проекция: всего XP, уровень, Coins, последняя учтённая строка, версия | Пишется только функциями (`game_writer_only`); пересобирается из журнала |
| `game_level_for_xp()` | Уровень по сумме XP | Та же формула, что `xpForNextLevel` (80 + 40·n), проверено тестом |
| `game_day_for()` | Игровой день: серверное время в поясе `profiles.timezone` | — |
| `game_apply_reward()` | **Единственный** способ начислить | `SECURITY DEFINER`, только `service_role` (раздел 2) |
| `game_rebuild_profile()` | Пересборка проекции из журнала | Только `service_role` |
| `game_begin_migration()`, `game_activate_cloud()` | Переходы состояния | Только `service_role`; активация создаёт пустую проекцию, **XP не переносит** |
| `game_account_status()` | Своё состояние и флаг | Только `authenticated`, только о себе (`auth.uid()`) |

**Доступ:**
- клиент (`anon`, `authenticated`) может только **читать свои строки** журнала, проекции и состояния;
- изменять, вставлять, удалять и вызывать начисляющие функции клиент не может;
- `service_role` (серверный маршрут Next.js) вызывает функции, но и он не может вручную изменить журнал или проекцию: это проверено тестами V1–V4.

## 2. Протокол начисления и защита от TOCTOU

```
Клиент ── «проверь миссию m_lesson» ──▶ Next.js route (app/api/game/*)
  1. Пользователь — только из проверенной сессии (supabase.auth.getUser на сервере). user_id из тела запроса игнорируется.
  2. Чтение записей Журнала из облака (service_role), вместе с версией и отпечатком, которые считает сам Postgres:
       SELECT data, client_updated_at, md5(data::text) AS fp FROM journal_notes WHERE user_id = $uid AND …
  3. Проверка правил на TypeScript (lib/missions.ts, lib/personal-quests*.ts) — те же модули, что в приложении.
  4. Вызов game_apply_reward(uid, key, rule, evidence = [{table, id, version, fp, source_key}]).
Postgres, одна транзакция:
  a. Аккаунт в cloud_active и флаг включён (иначе game_account_not_active / game_sync_paused).
  b. SELECT … FROM game_profile WHERE user_id = uid FOR UPDATE — все начисления пользователя идут по очереди.
  c. Ключ уже есть → вернуть сохранённый result (replay) и ничего не начислять; тот же ключ с другим правилом → game_key_conflict.
  d. Правило из game_reward_rules (сумма только отсюда; неизвестное правило → game_unknown_rule).
  e. Игровой день = game_day_for(uid) по серверному времени; будущий день и прошлый вне окна → game_day_not_open.
  f. Для каждой записи-доказательства: SELECT client_updated_at, deleted_at, md5(data::text) … WHERE user_id = uid AND id = … FOR SHARE.
     Нет строки (или она чужая) → game_evidence_missing; удалена, другая версия или другой отпечаток → game_evidence_changed.
  g. Лимиты дня на заблокированном состоянии: число (миссии 3, ежедневная 1) → game_day_cap; XP самоотчётов (90) и Coins (100) урезаются.
  h. INSERT в game_ledger (result сохраняется в строке), INSERT в game_source_claims (занято → game_source_used), UPDATE game_profile.
  i. Метка «пишет функция» снимается до возврата.
```

**Почему между проверкой и начислением ничего не меняется:**
- маршрут проверил запись в версии `V` с содержимым, отпечаток которого `fp`;
- транзакция блокирует эту строку `FOR SHARE`: любое изменение Журнала будет ждать конца начисления;
- затем сравниваются и версия, и отпечаток. Отпечаток нужен, потому что Журнал принимает запись с **тем же** `updatedAt` как повтор (LWW «same time = retry»), то есть содержимое может измениться без смены версии (тест X1);
- при любом несовпадении начисления нет, ошибка `40001`: маршрут перечитывает Журнал и проверяет заново.

**Гарантии транзакции:**

| Требование | Как обеспечено | Тест |
|---|---|---|
| Уникальность операции | `UNIQUE (user_id, idempotency_key)` + проверка ключа под блокировкой проекции | T2, T3, T10 |
| Корректность пользователя | `user_id` только из проверенной сессии на маршруте; функция недоступна клиенту; доказательства ищутся только среди строк этого пользователя | AN3, U12, T7 |
| Актуальное состояние | Состояние аккаунта, флаг, версия и отпечаток записей Журнала, лимиты — внутри транзакции | S1–S6, X1–X3, T11, T14 |
| Однократная вставка в журнал | Ключ + PK источников; при ошибке откатывается всё | T6, X4 |
| Однократное обновление проекции | Одна UPDATE после вставки; повтор возвращает сохранённое без UPDATE (`version` = 1) | T3 |
| Сохранённый результат при повторе | `result` хранится в строке журнала | T2 |

## 3. Что клиент не может сделать

| Попытка клиента | Почему не выйдет | Тест |
|---|---|---|
| Увеличить XP или Coins, изменить уровень | Нет прав UPDATE на `game_profile`; триггер-писатель | U6, V4 |
| Записать оплаченную миссию | Нет прав INSERT на `game_ledger`; функции начисления только у сервера | U4, U12 |
| Выдать себе достижение | Достижения — строки журнала (`kind = achievement`) через ту же функцию | U4 |
| Поставить `paid=true` личному квесту | Флага нет: «оплачено» — это строка `pq:<runId>` в журнале, вставить её клиент не может; повтор того же прохождения — replay | U4, T10 |
| Записать от имени другого `user_id` | RLS + нет INSERT; доказательства чужого пользователя не находятся | U5, T7 |
| Изменить правила или своё состояние | Нет прав | U9, U11, U13 |
| Читать чужой журнал или проекцию | RLS по `auth.uid()` | U15, U16 |

## 4. Состояние аккаунта

```
local ──begin──▶ migration_pending ──activate──▶ cloud_active (навсегда)
  ▲                    │
  └──── (отмена до активации — Q4.5, решение) ┘
```

- **`local`** (сейчас у всех): экономика на устройстве, как сегодня. Сервер ничего не начисляет.
- **`migration_pending`**: перенос в работе. Сервер не начисляет. Приложение **не начисляет и локально** — правило для Q4.5, чтобы во время переноса не появилось «третьего» прогресса.
- **`cloud_active`**: источник истины — сервер. Обратного перехода нет (триггер), даже для `service_role`.
- **Флаг `game_sync`** включает начисления только у `cloud_active`. Выключение = пауза: сервер отвечает `game_sync_paused`, а приложение, прочитав состояние `cloud_active` (`game_account_status()`), **не возвращается** к локальным начислениям. Правило для клиента (Q4.4): локальные начисления разрешены только при `state = local`.

## 5. Перенос XP (только проектирование)

**Автоматически ничего не переносится:**
- `game_activate_cloud()` создаёт пустую проекцию;
- правила для «legacy» в таблице нет, поэтому функция начисления не может записать перенесённый XP;
- непроверяемый XP не утверждается автоматически.

**План Q4.5 (на согласование):**
1. Снимок `GameState` устройства в карантинную таблицу `game_imports`: на баланс не влияет, повтор не создаёт копий.
2. Разбор снимков на кандидатов с **теми же ключами**, что у новой системы:
   - `mission:<day>:<id>` — из истории и журнала источников;
   - `daily:<day>`, `first:<kind>`;
   - `pq:<runId>` — только `paid: true`.
3. Объединение устройств по ключу: дубли отбрасываются.
4. Экран предпросмотра: что переносится, что отброшено и почему.
5. Непроверяемый остаток (старые версии без истории) — отдельной строкой `legacy:<userId>` **только после вашего решения** о способе подсчёта и подтверждения человеком.

**Тестовые сценарии Q4.5:**
- два устройства с одной миссией одного дня → одна строка;
- завершение QH-8.4 без `paid` → не оплачивается;
- оплаченное QH-8.5 → строка `pq:<runId>` без повторной выплаты;
- повторный импорт → ничего нового;
- повреждённый снимок → отклонён целиком, без частичного переноса;
- Coins — по правилу 2026-10-27: пересчёт из данных, а не перенос числа.

## 6. Модель угроз

| Угроза | Мера | Тест |
|---|---|---|
| Второе устройство или вкладка оплачивает то же | Ключ идемпотентности, PK источников, блокировка проекции | T2, T6 |
| Запись Журнала изменена между проверкой и начислением | Блокировка `FOR SHARE` + версия + отпечаток | X1–X3 |
| Чужая запись Журнала как доказательство | Поиск только по `user_id` начисления | T7 |
| Подмена суммы | Суммы только из правил | T4, T5 |
| Перевод часов | Серверное время и день | T12, T13 |
| Обход лимитов параллельными запросами | Лимиты считаются под `FOR UPDATE` строки проекции | T11, T14 (последовательно) |
| Ручная правка истории сервисным ключом | Триггеры append-only и writer, метка снимается после функции | V1–V4 |
| Возврат к локальным начислениям выключением флага | Флаг — пауза; `cloud_active` необратим | S6, S7 |
| Порча проекции | Пересборка из журнала | R1 |
| Удаление аккаунта | Каскад удаляет журнал, проекцию, источники | D3 |
| Утечка сервисного ключа | Ключ только в `app/api/**/route.ts` (защита T7a), в Vercel env | — (политика) |

## 7. Тесты

- **`supabase/tests/game_economy.sql`** (запускается `scripts/test-migrations.mjs`, блок N), всё в одной транзакции с откатом:
  - аноним AN1–AN4;
  - состояние S1–S8;
  - начисления T1–T14;
  - TOCTOU X1–X4;
  - пользователь U1–U16;
  - сервис V1–V4;
  - пересборка R1;
  - день и каскад D1–D3.
- **Блок N:**
  - миграция применяется дважды;
  - правки владельца сохраняются;
  - `game_sync` по умолчанию выключен;
  - правила и лимиты совпадают с приложением;
  - формула уровня;
  - откат удаляет только экономику.
- **`lib/game-economy-rules.test.ts`** — суммы в SQL совпадают с `GAME_CONFIG` и вариантом C.
- **Проверка мутациями:** отключение сравнения отпечатка роняет X1, разрешение UPDATE журнала роняет V1.

**Ограничение:** PGlite — одно соединение. Настоящие параллельные транзакции на нём не запустить. Повторы проверены последовательно, а защита от гонок держится на гарантиях Postgres: уникальный индекс и блокировка строки проекции, под которой считаются лимиты. Для реальной проверки гонок предлагается отдельный CI-шаг с настоящим Postgres (вопрос 2).
