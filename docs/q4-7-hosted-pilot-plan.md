### Supabase и AYRA: кто что гарантирует

| Свойство | Supabase (проверено на пилоте) | AYRA (0023) |
|---|---|---|
| пользователь Auth с файлами | **удаляется**; строки `storage.objects` остаются без владельца | `account_deletion_ready` не пускает к `deleteUser`, пока есть хоть один файл аккаунта (папка или `owner_id`); маршрут удаляет пользователя только после `ready` |
| загрузка во время удаления | проверка прав + запись байтов + окончательная вставка строки | страж на `storage.objects` и блокировка аккаунта: вставка после запроса — отказ (P2.1–P2.4) |
| удаление файла | `remove()` — строка сразу, байты сразу или из очереди; пользователь не может удалить то, что запрещает RLS (молча) | файлы удаляются ключом сервиса, список сверяется с сервером до пустого |
| прямое удаление строки SQL | запрещено триггером `protect_objects_delete` | ни одна миграция AYRA не удаляет `storage.objects` SQL-запросом |
| физическое удаление байтов | не видно из проекта | не утверждается; косвенно — размер Storage в Dashboard (раздел 8) |

**Вывод для модели гонки.** Наш локальный тест Q1 моделировал загрузку одной транзакцией: удаление ждало её и удаляло файл. На hosted загрузка, прошедшая проверку до удаления, **получит отказ при окончательной вставке**, а её байты удалит очередь Storage. Оба исхода безопасны: файл аккаунта не переживает удаление. Пилот проверяет именно hosted-порядок (P2.1, P2.2).

## 1. Требования к изолированному проекту

1. **Новый проект Supabase на тарифе Free** (решение владельца, без платных изменений), только для пилота, например `ayra-pilot-1`:
   - Free достаточен для P0–P8. Резервных копий на Free нет, поэтому пункт P9 «резервные копии» проверяется только по документации;
   - регион — любой (лучше тот же, что у Production, для сравнимого времени P8);
   - на Free проект засыпает после недели без активности — перед запуском разбудить его в Dashboard.
2. **Ничего из Production:**
   - ни данных, ни пользователей, ни ключей;
   - тот же организационный аккаунт допустим;
   - Production-ref записывается в настройки пилота только для запрета (раздел 3).
3. **В проекте не должно быть других пользователей и таблиц.** P0 это проверяет; `init-marker` отказывается работать в непустом проекте.
4. **Hook (Custom Access Token Hook) остаётся выключенным.** Функция из 0018 появится, но в Auth → Hooks её не подключать.
5. **Vercel** не нужен, Preview не создаётся (решение владельца). Приложение для P6–P8 запускается локально (`serve`) из этого репозитория против пилота.
6. **Команды выполняет Claude Code на компьютере владельца** (решение владельца). Ключи есть только в `.env.pilot.local`.

## 2. Настройки пилота

**Файл `.env.pilot.local`** в корне рабочей копии. Он не попадает в git (`.env*`). Значения вписывает владелец; в отчёты они не выводятся:

```
AYRA_PILOT_PROJECT_REF=<ref пилота, 20 символов>
AYRA_PRODUCTION_PROJECT_REF=<ref Production — только для запрета>
AYRA_PILOT_SUPABASE_URL=https://<ref пилота>.supabase.co
AYRA_PILOT_ANON_KEY=<anon (legacy JWT) или publishable key пилота>
AYRA_PILOT_SERVICE_ROLE_KEY=<service_role (legacy JWT) или secret key пилота>
AYRA_PILOT_DB_URL=postgresql://postgres.<ref пилота>:<пароль>@<регион>.pooler.supabase.com:5432/postgres
AYRA_PILOT_DB_CA_FILE=<путь к сертификату проекта, .crt>
```

- **Адрес базы:** Project Settings → Database. Нужен **Session pooler (5432)** или прямое подключение. Transaction pooler (6543) скрипт отклоняет.
- **Сертификат:** там же, «SSL Configuration → Download certificate». Соединение проверяет сертификат; без него скрипт не запустится.

**Auth** (Dashboard → Authentication):
- Email provider включён, «Confirm email» включён (по умолчанию). Письма не отправляются: пилот получает коды через `admin.generateLink`;
- «Write audit logs to the database» — **включить** для P9;
- Hooks — **выключены**.

**Storage:** ничего не создавать вручную — bucket создаёт 0005.

**Запуск локального приложения для P6–P8:** `serve` собирает этот репозиторий в `.next-pilot/`.
- **Окружение приложения — только allowlist**, а не окружение терминала:
  - системные переменные, без которых не запускается Node: `PATH`, `SystemRoot`, `TEMP`, `HOME`/`USERPROFILE`, `APPDATA` и подобные;
  - явные переменные пилота: адрес, два ключа, флаг удаления `1` (только в этом процессе), серверная экономика `0`, миссии `0`.

  Ничего из терминала — `VERCEL_*`, `NODE_OPTIONS`, `DATABASE_URL`, другие адреса и ключи Supabase, e2e-флаги — в сборку и сервер не попадает. Перед запуском результат проверяется ещё раз: лишняя переменная или Production-ref в любом значении → отказ.
- Next сам загружает файлы `.env*`. Запуск отказывается, если в папке есть любой из них, кроме `.env.example` и `.env.pilot.local` (его Next не читает).

## 3. Защита от ошибки окружения

`scripts/hosted-pilot/env.mjs` (unit-тесты `env.test.ts`) отказывает:
- без `--target <ref>`, совпадающего с `AYRA_PILOT_PROJECT_REF`;
- если ref пилота совпадает с Production или Production-ref встречается в любом адресе или ключе;
- если адрес API не `https://<ref пилота>.supabase.co`, а адрес базы — не база пилота;
- если используется transaction pooler или нет файла сертификата;
- **ключи — fail closed, без сети:**
  - принимаются только поддерживаемые форматы нужного вида: anon — legacy JWT роли `anon` или `sb_publishable_…`; service — legacy JWT роли `service_role` или `sb_secret_…`;
  - JWT должен содержать **ровно** ref пилота; JWT без ref, неизвестный формат, ключ не той роли и один и тот же ключ дважды — отказ.

**Ключи — доказательство по сети.** Отсутствие ref ничего не доказывает, поэтому **в начале каждого шага** выполняются три чтения только у шлюза **пилота** (`lib.mjs`, `verifyKeysOwnership`):
1. anon-ключ принят: `GET /auth/v1/settings` → 200;
2. anon-ключ **не** имеет прав администратора: `GET /auth/v1/admin/users` → 401/403;
3. service-ключ принят: `GET /auth/v1/admin/users?per_page=1` → 200.

Ключ другого проекта шлюз пилота не принимает. Любой другой ответ или ошибка сети — отказ. Новые форматы ключей передаются только в заголовке `apikey`.

Шаги, которые **пишут**, требуют `--confirm <ref пилота>` **и** отметку в базе (`public.ayra_pilot_marker`, ставится только в пустом проекте).

**Секреты:**
- ключи, адрес базы, пароли и токены тестовых аккаунтов собираются в список и **вырезаются из каждой строки вывода и каждого отчёта**;
- если секрет всё же попал бы в отчёт, отчёт пишется без него, а шаг получает FAIL.

**Пароли одноразовых тестовых аккаунтов:**
- лежат **отдельно от отчётов** — в `.pilot-secrets/<run>.accounts.secret.json`;
- папка доступна только текущему пользователю: на Windows — ACL без наследования, только пользователь; на POSIX — права 700, файлы 600;
- если ограничить права не удалось, тестовый аккаунт не создаётся;
- `.pilot-secrets/` в `.gitignore`, это проверено тестом;
- реестр аккаунтов для `cleanup` (`pilot-runs/<run>/accounts.json`) — только id и e-mail;
- после пилота: `forget-secrets` перезаписывает и удаляет файлы паролей и удаляет `.next-pilot/`.

Ограничение: на SSD перезапись не гарантирует физического стирания. Это пароли одноразовых аккаунтов, которые к этому моменту удалены `cleanup`, а проект пилота можно удалить.

## 4. Тестовые данные

- **Аккаунты** создаются самим пилотом: `ayra-pilot-<run>-<роль>-<hex>@example.com`. Пароль — случайный; письма не отправляются (`admin.createUser`/`generateLink`). Реальных персональных данных нет.
- **Файлы:** `<user id>/<имя>.webp`, 64 байта (заголовок WEBP); для гонки — 4,5 МБ; для объёма — 3000 штук.
- **Строки:** `journal_notes` через API от имени пользователя, `user_features.cloud_sync` для тестовых аккаунтов.
- **Контрольный аккаунт:** в P6 его строки и файлы сравниваются до и после.

## 5. Шаги, команды и критерии

Все команды запускаются из корня репозитория. `<REF>` — ref **пилота**.

```
node --import ./scripts/hosted-pilot/ts-resolve.mjs scripts/hosted-pilot/pilot.mjs <шаг> --target <REF> [--confirm <REF>]
```

Каждый шаг печатает `PASS/FAIL/NOTE` и пишет `pilot-runs/<run>/<шаг>.json`. Код выхода: 0 — всё PASS, 1 — есть FAIL, 2 — отказ guard.

| # | Шаг | Пишет? | Проверка | PASS | FAIL → действие |
|---|---|---|---|---|---|
| P0 | `preflight` | нет (read-only сессия) | `supabase/checks/pilot_preflight.sql`: версия, роль, владелец `storage.objects`, права TRIGGER/SELECT, `owner_id text`, `storage.foldername`, `REFERENCES auth.users`, роли, `uuid-ossp`; пустой проект | все PASS | остановиться: миграции в этом проекте не пройдут — отчёт владельцу |
| — | `init-marker` | да (2 служебные таблицы) | только в пустом проекте | отметка поставлена | непустой проект → не продолжать |
| P1 | `migrate` | да | 0001…0023 по порядку, каждый файл в своей транзакции; список применённых — в `ayra_pilot_migrations` | все применены | первая ошибка останавливает; текст ошибки в отчёте; см. раздел 6 |
| P1b | `check-schema` | нет | `supabase/checks/pilot_0023_hosted.sql`: триггер на `storage.objects` включён, у каждой из 30 таблиц есть страж, функции `SECURITY DEFINER`, владелец читает `storage.objects`, права только у `service_role`, таблицы удаления закрыты, правила 0005 и закрытый bucket | все PASS | не запускать P2+ |
| P2/P3 | `race` | да | **P2.0** обычная загрузка: строка, `owner_id` = загрузивший. **P2.1** проверка Storage прошла до запроса удаления (видна ожидающей блокировки), запрос встал за ней, окончательная вставка после запроса — **отказ, строки нет**. **P2.2** (`race --only P2.2`) окончательная вставка точно **между `ready` и удалением пользователя**: (1) проверка Storage проходит до начала удаления — видна ожидающей, удаление встаёт за ней; (2) одна транзакция берёт блокировку и выполняет `begin` → `manifest` → `ready`, не закрываясь; (3) окончательная вставка Storage видна ожидающей этой блокировки (`pg_locks`: ExclusiveLock у транзакции удаления, ShareLock у сервера Storage не выдан), загрузка ещё не ответила; (4) фиксация → отказ, строки нет; (5) затем удаление пользователя. | P5 | `amr` | да | `amr` для регистрации, пароля, кода из письма, magic link, recovery и после обновления токена; решение — настоящей функцией приложения `newestAuthTime` | регистрация, пароль, код и ссылка засчитываются; recovery — нет; **после обновления время входа не сдвигается** (±1 с) | если обновление сдвигает время → **блокер**: удаление без пароля станет возможным через 10 мин после любого обновления; исправить код до включения |

**Порядок запуска:**
1. P0;

3. P1, P1b;
4. P2, P4, P5;
5. `serve` в отдельном окне;

Успех удаления распознаётся **ровно** по ответу настоящего обработчика: `200` и `{ state: "deleted" }` (`isDeletedResponse`). «Продолжить» — `503` и `{ retry: true }`. Тест сравнивает с ответами самого `handleAccountDeletion`.

**P10 — межвкладочный выход и смена пространств.** Hosted для этого шага не нужен: это отдельный регрессионный аудит на локальном fake Supabase. Существующие тесты:
- `e2e-supabase/auth-logout-race.spec.ts`;

План аудита: каждая пара переходов «гость ↔ аккаунт A ↔ аккаунт B» с выходом в другой вкладке во время переключения. Критерии:
- нет вечного скелета;
- запись идёт только в своё пространство;
- после выхода нет данных прошлого аккаунта.

Делается отдельной задачей после пилота или параллельно — по слову владельца.

## 6. Восстановление после ошибки

- **Пилот одноразовый.** Самый надёжный откат — удалить проект пилота (Dashboard → Settings → Delete project) и создать новый. Production при этом не затрагивается.
- **Ошибка миграции:** файл выполняется в своей транзакции, ошибка откатывает только его. Следующие файлы не применяются. Список применённых — в `ayra_pilot_migrations`; повторный `migrate` продолжит с первой неприменённой.
- **Откат миграций:** `rollback --to <NNNN>`. 0023 откатывается только без незавершённых удалений. При сбое отката — удалить проект.
- **Тестовые аккаунты и файлы:** `cleanup`. Если Storage вернул ошибку — повторить; оставшиеся строки видны в P9.
- **Зависшая транзакция в гоночном шаге** (например, оборвалась сеть): блокировки снимаются при закрытии соединения. Шаг можно повторить — каждый раз создаются новые аккаунты.

## 8. Что нельзя проверить автоматически

1. **Физическое удаление байтов** после отказанной загрузки и после `remove()`. Storage удаляет их сам — сразу или через очередь, — а из проекта видны только строки. **Отсутствие строки `storage.objects` и ответ «Object not found» на скачивание не доказывают, что байты стёрты в хранилище**: оба смотрят на строку. Косвенная проверка вручную: Dashboard → Usage → размер Storage после пилота должен вернуться к нулю (с задержкой подсчёта).
2. **Порядок операций в hosted-версии Storage** может отличаться от `master` в GitHub. P2.1/P2.2 проверяют наблюдаемое поведение. Если проверка Storage не видна ожидающей (`probe seen waiting` = FAIL), hosted работает иначе — разбираем по фактическому ответу.
3. **Резервные копии:** что удалённый аккаунт остаётся в копиях до истечения их срока, следует из документации. Проверить можно только восстановлением копии в отдельный проект (Pro, ручное действие).
4. **Внешний журнал аудита Auth** (не копия в базе) виден только в Dashboard. Срок хранения по тарифу в документации не указан явно — проверяется вручную в Dashboard → Logs.
5. **Время на Vercel** без Preview-развёртывания замеряется только локально.
6. **Реальная доставка писем** (код и ссылка) в пилоте не проверяется: используется `generateLink`, письма не отправляются. Сам вход по коду и ссылке проверяется полностью.
