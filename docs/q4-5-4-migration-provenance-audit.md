# Q4.5-4 — Перенос прогресса устройств в серверную экономику

**Решение владельца (2026-11-23):** V2 — непроверяемый остаток хранится в карантине, сверяется и подтверждается человеком; V3 — облачные записи Журнала только как независимое свидетельство; **неподтверждённый остаток никогда не начисляется автоматически.**

**Статус:** реализовано в репозитории (Draft PR). В Production ничего не применялось: SQL, хук, флаги, деплой, реальные аккаунты, XP и Coins не трогались.

## 1. Что хранит устройство и что из этого доказуемо

`GameState` в `localStorage` пространства аккаунта (`ayra:<uid>:ayra_demo_v1`).

- `level`, `xp` — `xp` хранит опыт **внутри уровня**. Полный опыт = Σ порогов `80 + 40·n` пройденных уровней + `xp` (как в `lib/game.ts` и `game_level_for_xp`).
- `coins` — баланс.
- **Coins не тратились ни в одной версии** (поиск по всей истории git: списаний нет, кроме симуляций `econ-sim`). Значит, баланс = всё заработанное.

| Источник | Запись на устройстве | Ключ | Доказуемо |
|---|---|---|---|
| Квесты и миссии | `history` (не обрезается): `questId`, игровой день, xp, coins (фактически выплаченные) | `quest:<день>:<questId>` | **Да** — сумма из записи, в пределах правил |
| Первые действия | `firstActions`: вид → время | `first:<вид>` | **Да** — сумма по правилу своего времени (раздел 2) |
| Личные квесты | `personalLedger` с `paid: true` (с #200, 2026-11-17) | `pq:<runId>` | **Да** — только оплаченные; XP из списка 50/90/100/125/180/250 |
| Ежедневная награда | `coinLog` `dailyReward` (до 500 записей, с `coinLogSince`) | `daily:<игровой день>` (зона аккаунта) | **Частично** — только в окне журнала Coins |
| Скриншоты | `rewardedScreenshotHashes` | — | **Нет** — хеш не доказывает ни суммы, ни дня |
| XP Журнала (сделки, заметки, планы, без сделок, дисциплина) | только `dailyStats[день].xpGained` — сумма дня, смешанная с квестами | — | **Нет** |
| Coins до журнала Coins | только баланс | — | **Нет** |
| Достижения | `achievements` | — | Наград не дают; сохраняются как есть |

## 3. Алгоритм сверки (`lib/migration/reconcile.ts`)

Чистая детерминированная функция: одни и те же снимки в любом порядке дают один и тот же результат (проверено тестом). Ничего не начисляет.

**Шаг 1. Один снимок → события с ключами.** Каждая запись проверяется:
- **формат:** день `YYYY-MM-DD`, id `[A-Za-z0-9_.-]`, суммы — целые ≥ 0; иначе `bad_record`;
- **сумма в правилах:** квест ≤ 200 XP и ≤ 100 Coins (плейсхолдер), личный квест — из списка, ежедневная — 10/15/20/25/50; иначе `amount_out_of_rule`;
- **повтор ключа внутри снимка:** `duplicate_in_snapshot`, засчитывается первый;
- **дневной лимит Coins 100** (с 2026-10-27) для квестов и ежедневных наград: превышение срезается, `daily_coin_cap`.

**Шаг 2. Несколько устройств.**
- Один и тот же ключ на нескольких устройствах — **одно** событие. **События разных устройств никогда не суммируются.**
- Суммы расходятся → подтверждается **меньшая**, разница — конфликт `amount_mismatch`.

**Шаг 3. Кандидат остатка — отдельно для каждого снимка.**
- Кандидат = полный XP (Coins) снимка − подтверждённое **этого** снимка, не меньше 0.
- Это **верхняя граница, а не сумма к начислению**: семантика частей разная, поэтому к кандидату приложена разбивка причин:
  - `journal_xp_by_day` — XP по дням сверх квестов (без событий);
  - `screenshot_hashes`;
  - `coins_before_log` — Coins до журнала Coins;
  - `legacy_format` — сохранение старее любых записей.
- Баланс меньше собственных записей → конфликт `balance_below_records`.
- Уровень и XP не согласованы → `level_xp_inconsistent`.
- **Кандидаты разных устройств не складываются.** Максимум по устройствам — тоже только кандидат.

**Шаг 4. Предложение.**
- Подтверждённые XP и Coins, уровень по ним, наибольший исходный уровень и разница уровней (`levelGap`), исходные Coins.
- Достижения со всех устройств — как есть.
- Исходные значения хранятся рядом и не меняются.

**V3 — свидетельство из Журнала.**
- `game_mig_journal_days` показывает число облачных записей Журнала по дням в зоне аккаунта. Импортированные записи считаются отдельно (импорт никогда не давал наград), удалённые не считаются.
- Запись не доказывает награду, её время не доказывает время награды, правка не создаёт награду. Свидетельство показывается проверяющему рядом с кандидатом и **не меняет ни одного числа**.

## 4. Карантин остатка (V2)

Таблица `game_legacy_reviews`: одна строка на принятый снимок.
- **Содержимое:** id снимка; исходные итоги (уровень, полный XP, Coins, версия сохранения); подтверждённая часть; кандидат; причины; статус; кто, когда и почему решил.
- **Статусы:** `pending_review` → `accepted` / `rejected` / `needs_evidence`.
- **Принять** можно не больше кандидата (ограничение в базе). **На аккаунт — не больше одного принятого остатка** (уникальный индекс): один и тот же остаток нельзя начислить дважды под другим снимком.
- Новая сверка с изменившимся кандидатом **возвращает** решение в `pending_review` и пишет это в журнал.
- **Активация невозможна**, пока хоть один остаток в `pending_review` или `needs_evidence`.
- Принятый остаток пишется в журнал наград одной строкой `legacy:<аккаунт>` (ключ уникален на аккаунт) с ссылкой на снимок, автором и причиной.

## 5. Приём снимков (0019 `game_import_snapshot`)

- **Кто вызывает:** только серверный маршрут `POST /api/game/migration/snapshot` (service_role). Пользователь — из проверенной сессии, клиент не может назвать чужой аккаунт.
- **Свежесть:** отметка `ayra_economy` в токене = состояние сейчас и токен выпущен после смены (проверка 0018). Строка аккаунта удерживается до записи, поэтому приём и активация не проходят одновременно.
- **Окно:** `migration_pending` → `accepted`; второй снимок того же устройства → `duplicate_install` (хранится, в сверку не входит); после активации → `late` (хранится отдельно, никогда не сверяется и не начисляется); до окна → отказ, ничего не хранится.
- **Пределы:** схема 1; ≤ 1 МБ; ≤ 20 снимков на аккаунт (плейсхолдеры).
- **Идемпотентность:** тот же id и то же содержимое → повтор; тот же id с другим содержимым или с другого устройства → отказ `game_import_conflict`.
- **Хранится как пришло:** содержимое, md5, размер, время сервера, сессия, состояние аккаунта на момент приёма. Изменить снимок нельзя даже владельцу.
- **Идентификатор устройства** — случайный id хранилища. Он группирует снимки, но **не является доказательством устройства**.

## 6. Активация (`game_mig_activate`)

Никогда не автоматическая. Одна транзакция:
1. Аккаунт в `migration_pending`. Сверка — последний черновик **ровно для принятых сейчас снимков** (id + md5). Новый снимок после сверки → отказ `game_mig_inputs_changed`.
2. Все остатки решены.
3. Уровень ниже исходного → отказ, если владелец явно не подтвердил (`--level-gap-ack` с текстом). **Скрытого понижения уровня нет.**
4. В журнал наград пишутся события `import:<ключ>` и принятый остаток `legacy:<аккаунт>`; затем состояние → `cloud_active`, проекция пересчитывается из журнала, действие пишется в журнал решений.
5. Повторный вызов — повтор без изменений.
6. Любой отказ откатывает всё: аккаунт остаётся в `migration_pending`, снимки и решения на месте.

**Обход сверки закрыт:** аккаунт со снимками не переводится в `cloud_active` прямым вызовом. Серверная роль больше не может менять состояния вообще: `game_economy_transition`, `game_begin_migration` и `game_activate_cloud` у service_role отозваны.

## 7. Офлайн-устройства

- Устройство замораживает свой снимок **один раз**, когда впервые узнаёт об окне или о переносе. Дальше оно отправляет **ту же копию** до ответа сервера: повтор на сервере — это повтор, а не второй снимок.
- Своё сохранение устройство не меняет и не удаляет.
- **Подключилось после активации:** снимок принимается как `late`, хранится отдельно; человеку показывается, что прогресс сохранён и будет рассмотрен отдельно и что автоматически он не добавляется.
- **Токен до смены состояния:** отказ `session_stale`, приложение обновляет сессию и повторяет.
- **Двойного приёма нет:** один id — одна строка; одно устройство — одна строка в сверке.
- **Срок окна не установлен — его задаёт владелец** (вопрос 1).

## 8. Инструмент владельца (`scripts/migration-admin.mjs`)

**Не API**: запускается на компьютере владельца с прямым подключением к базе (`AYRA_MIGRATION_DB_URL`, строка нигде не печатается).
- **Роль:** сразу `SET ROLE game_migration_admin` — роль без входа; в неё не входит ни одна роль API (проверено тестами).
- **Права:** роль читает карантин, аккаунты, журнал наград и проекцию; пишет **только** через функции 0019. Содержимое Журнала не читает — только число записей по дням.
- **Подтверждение:** каждое изменение требует автора (`--actor`), причины (`--reason`) и ввода id аккаунта.
- **Журнал решений** `game_migration_audit` только дополняется; кроме введённого автора хранит вход в базу (`session_user`).

| Команда | Что делает |
|---|---|
| `show <user>` | снимки, решения, сверки, журнал решений |
| `open <user> --actor --reason` | открывает окно (`migration_pending`) |
| `reconcile <user> [--save --actor]` | предпросмотр: события, конфликты, кандидаты, свидетельства Журнала, предложение; `--save` — черновик |
| `decide <user> <snapshot> <status> [--xp --coins] --actor --reason` | решение по остатку |
| `activate <user> <id> --actor [--level-gap-ack]` | активация |

Требуется Node ≥ 22.18: инструмент импортирует `reconcile.ts` напрямую.
