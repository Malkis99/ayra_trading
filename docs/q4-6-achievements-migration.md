# Q4.6 — Достижения на сервере и завершение подготовки переноса

**Статус:** объединено в `main` (#221, `d8b5257`). Решения владельца по вопросам ниже и блокеры запуска — в `docs/q4-7-owner-decisions-launch-blockers.md`. В Production ничего не применялось: миграции, хук, флаги, деплой, реальные аккаунты, XP, Coins и достижения не трогались.

**Опирается на:** Q4.4 (серверный день), Q4.5-1 (метка экономики на клиенте), Q4.5-2 (метка в токене, свежесть сессии, `RequestScope`, `AuthGeneration`), Q4.5-4 (`docs/q4-5-4-migration-provenance-audit.md`: карантин снимков, сверка, которую считает база, окно 7 дней, активация).

Новая миграция — `supabase/migrations/0020_game_achievements.sql` (+ откат).

## 1. Аудит достижений

**Три вида достижений.**

| Вид | Где на устройстве | Стабильный id на сервере |
|---|---|---|
| Достижения профиля (14) | `GameState.achievements` (`id → true`), список в `lib/profile.ts` `PROFILE_ACHIEVEMENTS` | сам id, например `firstQuest` |
| Лучший ранг категории «Моего пути» (QH-8.4/8.5) | `GameState.personalAchievements[категория] = {rank, runId, day}` | `category:<категория>` |
| Трофей недели (QH-7) | `GameState.weekTrophies[] = {week, boss, …}` | `week:<понедельник>` |

**Что показала история git:**
- 14 идентификаторов профиля появились в T3–T6d (2026-10-05…09). **Ни один не переименовывался и не удалялся, условия ни разу не менялись** — их только добавляли. Формула уровня (`80 + 40·n`) та же с T3.
- **Ни одно достижение никогда не давало XP или Coins:** при открытии пишется только запись в хронику. От достижений зависят лишь косметические титулы.
- Достижения открываются только на устройстве (`checkAchievements` и соседние функции). На сервере их до Q4.6 не было.

**Важная находка: `stylist` открывается у каждого.** Условие — «в снаряжении есть хотя бы один предмет», а у каждого нового персонажа есть стартовый комплект. Значит, это правило выполняется для любого аккаунта.

### Матрица происхождения

| id | Условие | Чем сервер может подтвердить | Статус при переносе |
|---|---|---|---|

| `firstTrade` | квест записи сделки или первая сделка | событие `quest:…:q_tradelog` или `first:trade`; иначе запись в облачном Журнале (`journal_trades`) | verified / pending_review |

| `week:<понедельник>` | победа в вызове недели | **ничем**: проверка недели шла на устройстве | pending_review |

**Чего здесь нет и не будет:**
- **Локальный флаг никогда не выдаётся за подтверждение.** Без доказательства — `pending_review` с источником `device_flag`.
- **Сервер не добавляет достижений, которых не было ни на одном устройстве.** Перенос сохраняет открытое, а не открывает новое.
- **Неизвестный id** (не из каталога) и повреждённые записи не записываются. Они перечисляются отдельно в журнале решений, а снимок хранит их как пришли.

## 2. Серверная модель

**`game_achievement_catalog`** — 14 стабильных id: когда появились, как доказываются, правило.

**`game_achievements`** — одна строка на аккаунт и стабильный id.

| Поле | Смысл |
|---|---|
| `user_id`, `achievement_id` | аккаунт и стабильный id (CHECK: только 14 id, `category:<6 категорий>`, `week:YYYY-MM-DD`) |
| `family` | profile / category / week |
| `status` | **verified** / **legacy_accepted** / **pending_review** / **rejected** |
| `source` | reconciled_event / journal_record / confirmed_level / accepted_level / game_rule / device_flag |
| `detail` | что сказали устройства (ранг, босс) — никогда не число к начислению |
| `evidence` | чем доказано (ключ события, число записей, уровень, заявленные ранги и боссы при расхождении) — **без содержимого Журнала** |
| `claimed_by` | какие принятые снимки его содержали (одна строка, сколько бы устройств ни было) |
| `rules_version`, `reconciliation_id` | версия правил q4.6 и сверка, с которой пришло |
| `idempotency_key` | `ach:<id>` (уникален на аккаунт) |
| `recorded_at`, `decided_by`, `decided_at`, `reason` | время записи на сервер и последнее решение человека |

**История решений** хранится в `game_migration_audit` (`achievement_decided`: до, после, причина, автор).

**Права:**
- Писать в таблицы может **только** владелец через функции 0020: активация, перенос для ранее активированного аккаунта, решение человека.
- Ни одна роль API не читает и не пишет таблицы. Человек получает **свои** достижения только через `GET /api/game/achievements`: маршрут проверяет сессию, а база — её свежесть (`game_achievements_for_session`, только service_role).
- **Произвольным запросом клиента разблокировать достижение невозможно.** Маршрут только читает и не принимает ни id, ни статуса.
- **Повторного начисления нет:** ни одна строка достижений не касается `game_ledger`, XP и Coins (проверено тестами AC7, M1).

**Решения человека** (`game_mig_decide_achievement`, команда `decide-achievement`):
- переход между pending_review, legacy_accepted и rejected;
- причина обязательна;
- **verified вручную не меняется** (`game_mig_achievement_verified`);
- rejected не удаляется: строка остаётся со своей историей.

## 3. Порядок безопасного импорта

Активация (`game_mig_activate`, 0020) — одна транзакция, всё из Q4.5-4 плюс достижения:
1. Окно закрыто. Сверка равна расчёту базы сейчас. Все остатки решены. Уровень не понижается скрыто.
2. Журнал наград: события и принятый остаток. Переход в `cloud_active`. Проекция пересчитывается.
3. **Достижения:**
   - `game_mig_achievement_plan` собирает их из всех **принятых** снимков (поздние не участвуют);
   - дедуплицирует по стабильному id;
   - проверяет происхождение по сверке базы, облачному Журналу и итоговому XP;
   - спорные сохраняет как `pending_review`;
   - пишет строки `ON CONFLICT DO NOTHING` и отмечает `achievements_transferred_at`.
4. Журнал решений: `achievements_transferred: true`, сводка, неизвестные id.

Ещё три свойства:
- **Сбой на любом шаге откатывает всё** (тест F1: сбой при записи достижений → аккаунт остаётся `migration_pending`, ни строки журнала наград, ни достижения, черновик как был). Повтор после устранения проходит.
- **Повторная активация** — `replay`, ничего дважды (AC10, M1).
- **Аккаунт, активированный до 0020**, переносится отдельно: `game_mig_transfer_achievements`, команда `transfer-achievements`, один раз (F3, M2).

`achievements_transferred` становится `true` **только** после успешной записи достижений в той же транзакции. До этого человек видит «Достижения пока хранятся на этом устройстве…».

**Клиент:**
- в `cloud_active` приложение читает серверный список и применяет ответ только к своему аккаунту и пространству (`RequestScope`, `answerBelongs`);
- вкладка «Достижения» показывает серверные состояния: подтверждено, «Перенесено с устройства», «Перенесено, ждёт проверки», «Не подтверждено при переносе»;
- **локальные флаги устройства не трогаются** и остаются архивом;
- перезагрузка и повторный вход ничего не обнуляют, несколько устройств не создают дублей: строка одна на id;
- UI Quest Hub не менялся. Блоки «Моего пути» и трофеев недели пока показывают архив устройства (их серверные состояния есть в базе — вопрос 7).

## 4. Большие снимки (решение владельца: ограниченное сжатие одним запросом)

**Замеры на синтетических сохранениях** (реальные не читались):

| Нагрузка | Сохранение | gzip | Сжатие |
|---|---|---|---|
| 90 дней × 6 квестов | 0,15 МБ | 8 КБ | 18× |
| 1 год × 6 | 0,50 МБ | 26 КБ | 20× |
| 2 года × 8 | 1,19 МБ | 58 КБ | 21× |
| 3 года × 10 | 2,13 МБ | 97 КБ | 23× |
| 5 лет × 10 | 3,51 МБ | 158 КБ | 23× |
| «Бомба»: 8 МБ пробелов | 8 МБ | 8 КБ | ~1000× |

**Пределы:**
- до 4 МиБ после распаковки — покрывает 5 лет по 10 квестов в день;
- до 1 МиБ в сжатом виде;
- коэффициент сжатия ≤ 50: в 2 раза выше наблюдаемого, но в 20 раз ниже «бомбы»;
- не больше 16 МиБ снимков на аккаунт — плейсхолдер: 4 устройства максимального размера.

**Как работает:**
- **До 1 МиБ** — ровно как в Q4.5-4: тот же запрос, то же поведение.
- **Больше 1 МиБ:**
  - устройство один раз замораживает **сжатую** копию: gzip точных байт сохранения, их длина и SHA-256. Так копия помещается рядом с сохранением в хранилище браузера;
  - заморозка идёт под межвкладочной блокировкой (Web Locks), а без неё повторное чтение перед записью оставляет копию той вкладки, что успела первой;
  - отправка — одним запросом на тот же маршрут.
- **Сервер** проверяет всё до обращения к базе:
  - тело читается с ограничением (сначала `Content-Length`, затем поток; целиком в память — никогда);
  - сжатое — ≤ 1 МиБ;
  - заявленный размер — ≤ 4 МиБ, коэффициент проверяется **до** распаковки;
  - распаковка с остановкой на 4 МиБ (Node бросает ошибку и не выделяет больше);
  - фактический размер должен равняться заявленному, коэффициент проверяется повторно;
  - SHA-256 сравнивается;
  - текст — строгий UTF-8, JSON — объект.
- **Частично распакованное никогда не принимается.**
- **Независимость от транспорта.** После распаковки база получает тот же объект, что и без сжатия, а md5 содержимого в базе делает повтор повтором (тест: одинаковые аргументы базы для обычного и сжатого варианта).
- **Тот же id снимка при повторе:** замороженная копия никогда не переписывается. Старая обычная копия больше 1 МиБ (из Q4.5-4) сжимается только для запроса.
- **Чужой аккаунт:** пространство хранилища и `RequestScope` те же, что в Q4.5-4.
- **Браузер без сжатия:**
  - ничего не отправляется, сохранение не удаляется;
  - если в хранилище есть место, момент замораживается обычной копией, и новый браузер отправит её же;
  - человек видит: «Этот браузер не умеет сжимать большое сохранение для отправки. Оно не удалено: обновите браузер, и копия отправится сама».
- **Больше 4 МиБ** — безопасный отказ с прежним объяснением: «…напишите в поддержку».

**Найдено и исправлено попутно:** порядок блокировок приёма из 0019 приводил к взаимной блокировке с удалением аккаунта. В 3 из 3 прогонов PostgreSQL прерывал именно **удаление** (тест M3). В 0020 приём сначала записывает снимок (внешний ключ берёт строку пользователя), а уже потом блокирует строку аккаунта и перепроверяет состояние; если оно изменилось — ответ `session_stale`, устройство повторит. Порядок совпадает с удалением, взаимная блокировка исчезла (M3, M4, M5 — по 3 прогона).

## 5. Ограничения сжатых снимков

- **Коэффициент 50** может отказать сохранению, которое состоит из почти одинаковых записей. В реалистичных данных сжатие 18–23×, у предельно однообразных синтетических — сотни раз. Отказ безопасный: сохранение остаётся на устройстве, человек видит объяснение.
- **Вес base64:** +33 % к сжатому телу. Запрос — до ~1,34 МиБ, далеко от предела Vercel (4,5 МБ).
- **Синхронная распаковка** до 4 МиБ занимает функцию маршрута на миллисекунды. Частота ограничена 10 запросами в минуту на человека.
- **Квота 16 МиБ на аккаунт** считается по размеру уже принятых снимков, а повтор (replay) не считается.

## 6. Политика хранения

| Данные | Срок | Как обеспечено |
|---|---|---|
| Снимки | **минимум 90 дней после активации** | Автоматического удаления нет. Ручная очистка `game_mig_purge_snapshots` (команда `purge`) отказывает раньше 90 дней, во время переноса, при открытом решении по остатку или достижению, если достижения ещё не перенесены. **Поздние снимки не удаляет никогда.** Удаление записывается в журнал решений (число, id:md5, причина — без содержимого) и в обезличенный счётчик |
| Решения по остаткам, сверки, достижения, журнал наград | пока существует аккаунт | ничего их не удаляет, кроме удаления аккаунта |
| Журнал решений владельца | цель — до 2 лет | автоматической очистки нет: нужна отдельно утверждённая политика (раздел 10) |
| Обезличенные счётчики (`game_privacy_stats`, `game_deletion_log`) | цель — до 2 лет | персональных данных нет, удаление — отдельным решением |

**Автоматической очистки в этом PR нет — сознательно.** Её безопасность зависит от решений, которых пока нет: утверждённая политика приватности, срок для журнала решений, график. Ручной механизм с проверками готов, план автоматизации — в разделе 10. Поле даты само по себе ничего не «соблюдает»: соблюдение — это отказ функции очистки раньше срока и отсутствие других путей удаления. Обе вещи проверены тестами P1–P6 и T14.

## 7. Удаление аккаунта

**Как оно происходит сейчас.** Встроенного удаления в приложении нет: в настройках — «Удаление аккаунта (скоро)». Аккаунт удаляется только в Supabase Auth (панель или Admin API), и строки удаляются каскадом `ON DELETE CASCADE` от `auth.users`. Процедуру я не менял: добавлены только счётчики, которые срабатывают при удалении.

**Что удаляется каскадом:**
- `profiles` → `telegram_identities`, `link_tokens`; общий `audit_log` (0001);
- `user_features` и все таблицы Журнала (0004);
- `journal_attachments` (0005);
- синхронизация Market (0008), уведомления (0011);
- `game_accounts`, `game_ledger` → `game_source_claims`, `game_profile` (0014);
- `game_days` (0015);
- `game_imports` → `game_legacy_reviews`, `game_reconciliations` → `game_achievements`;
- `game_migration_windows`, `game_migration_audit` (0019);
- `game_achievements` (0020).

**Решение владельца выполнено так:**
- Снимки, прогресс, достижения, решения и **журнал решений аккаунта удаляются целиком.**
- **Псевдонимизацию я отверг.**
  - Хеш `user_id` не анонимизирует.
  - md5 снимка связывает запись с копией на устройстве человека.
  - Сочетание «время + суммы + автор» повторно идентифицирует человека для того, кто принимал решение.
  - Свободный текст причины может содержать персональные данные.

  Поэтому, как вы и указали, при ненадёжной анонимности — удаление.
- Остаются **только обезличенные счётчики:**
  - `game_privacy_stats`: (месяц, действие, количество) — журнал решений удаляемого аккаунта сворачивается в счётчики **до** удаления строк;
  - `game_deletion_log`: (день, причина `account_deleted` / `retention_purge`, таблица, количество).

  Нет ни id, ни сумм, ни текста, ни авторов, время — с точностью до месяца или дня. Тест X3 проверяет, что в этих таблицах ровно 3 и 4 столбца.
- **Проверено:**
  - удаление аккаунта посреди переноса (открытый остаток, черновик, продлённое окно) и после активации (достижения, журнал наград) — ни одной строки этих аккаунтов ни в одной таблице с колонкой пользователя (X1, X2);
  - другие аккаунты целы (X5);
  - удаление во время загрузки снимков проходит (M3).

**Чего каскад не покрывает (уже существующие пробелы, вне этого PR):**
1. **Файлы скриншотов в Storage** (`journal-attachments/<user>/…`): `auth.users` их не удаляет. Нужна отдельная процедура удаления аккаунта.
2. **Таблицы Журнала, Market и уведомлений** удаляются каскадом, но в `game_deletion_log` не считаются: триггеры на них я не добавлял, чтобы не менять чужие части.

## 8. Восстановление и откат

- **До первой активации на 0020:** откат `0020_game_achievements.down.sql` возвращает приём 0019 (1 МБ) и активацию 0019 и удаляет таблицы 0020. Он **отказывает**, пока существует хоть одно серверное достижение (тест T: отказ, достижение сохранено). Тесты 0019 после отката проходят.
- **После активаций:** откат не делать — исправлять вперёд.
  - Достижения восстановимы, пока хранятся снимки: план пересчитывается из них, `game_mig_transfer_achievements` повторно не пишет.
  - Поэтому очистка снимков требует, чтобы достижения уже были перенесены.
- **Сбой активации** откатывает всю транзакцию, аккаунт остаётся `migration_pending` (F1). Повтор безопасен.
- **Обезличенные счётчики** при откате удаляются вместе с 0020: персональных данных в них нет.

## 9. Остаточные риски

1. Достижения, известные только устройству (`author`, `propDisciplined5`, трофеи недель, неподтверждённые ранги, `plans7` без Журнала), требуют решения человека по каждому аккаунту (вопрос 1).
2. Записи облачного Журнала считаются доказательством достижений вида «сделал запись» (вопрос 3). Для XP Журнал по-прежнему только свидетельство (V3).
3. Коэффициент сжатия 50 может отказать очень однообразному сохранению (раздел 5).
4. Файлы Storage при удалении аккаунта не удаляются (раздел 7).
5. Автоматической очистки по сроку нет; журнал решений живущих аккаунтов растёт без срока (раздел 10).
6. Блоки «Моего пути» и трофеев недели в профиле пока показывают архив устройства.
7. Владелец базы технически может обойти любые проверки. Защита рассчитана на ошибки, а не на злой умысел.

## 10. План дальнейшей активации экономики

1. **Ревью и merge этого PR владельцем.**
2. **Применение 0014–0020** на отдельной, не рабочей базе Supabase (ветка или копия): прогон тех же SQL-тестов на настоящем Supabase, включая проверку отсутствия `GRANT … TO CURRENT_USER` и `CREATE` на `public`.

4. **Пилот на тестовом аккаунте владельца:**
   - `open` → загрузка снимков (обычных и сжатых) → `reconcile --save` → решения → закрытие окна → `activate`;

   - `show`;
   - удаление тестового аккаунта и проверка счётчиков.

7. **Отдельные задачи:**
   - удаление аккаунта в приложении (с файлами Storage);
   - утверждённая автоматическая очистка по сроку — задача по расписанию, которая вызывает ту же проверенную функцию, с журналом и без удаления открытого;

   - серверные «Мой путь» и трофеи в профиле.
