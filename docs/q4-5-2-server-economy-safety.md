# Q4.5-2 — Серверная основа безопасного перехода экономики (Custom Access Token Hook)

**Статус.** Вторая фаза Q4.5, архитектура по решению владельца от 2026-11-23: отметка экономики приходит в токен через **Custom Access Token Hook** Supabase.

- **Где проверялось:** на официальном локальном стеке Supabase с включённым хуком (раздел 6); в CI — на PGlite и настоящем PostgreSQL 16.
- **Миграции:** изменены 0014–0016 и 0018; все не применены ни к одному проекту Supabase.

**Ничего не включено:**
- хук в hosted Supabase не включён;
- ни один аккаунт не меняет состояние;
- флаги `NEXT_PUBLIC_AYRA_SERVER_ECONOMY`, `AYRA_SERVER_MISSION_PAYOUTS`, `NEXT_PUBLIC_AYRA_MISSION_SHADOW` не тронуты;
- вид начисления `mission` выключен; перенос не запускается.

Локальная экономика работает как раньше.

## 1. Архитектура

```
Переход (только service_role):      game_economy_transition(user, from, to)
                                    → game_accounts.state, state_changed_at   [одна транзакция PostgreSQL]
Выпуск токена (сервер авторизации): вход / обновление → hook game_access_token_hook(event)
                                    → в токен: "ayra_economy": <состояние из game_accounts в этот момент>
Экономический запрос (маршрут):     getSession → getUser(ЭТОТ токен)     [подпись, срок, живая сессия — сервер авторизации]
                                    → из этого же токена: session_id, iat, ayra_economy
                                    → строгая проверка тела запроса
                                    → game_session_check(...)            [ответ даёт БАЗА]
                                    → свежая: действие; устаревшая: 401 session_stale + состояние
Начисление:                         только game_apply_reward_for_session(...) — строка аккаунта удерживается,
                                    сессия перепроверяется, затем game_apply_reward (идемпотентно)
```

**Атомарность — граница обещания:**
- **Смена состояния** атомарно фиксируется в PostgreSQL (compare-and-set на заблокированной строке, тесты K1–K2).
- **Следующий выпущенный токен** несёт это состояние: хук читает его при выпуске (проверено на настоящем Supabase Auth, раздел 6).
- **Уже выданные токены не меняются.** JWT нельзя отозвать: он несёт старую отметку до своего `exp`. Это не скрывается — такие токены отсекает база (раздел 4).

## 2. Модель состояний

```
local ──▶ migration_scheduled ──▶ migration_pending ──▶ cloud_active (навсегда)
  └──────────────────────────────▶ migration_pending
```

| Переход | Результат |
|---|---|
| `local → migration_scheduled`, `local → migration_pending`, `migration_scheduled → migration_pending`, `migration_pending → cloud_active` | Разрешены |
| Пропуск стадии | `game_state_invalid_transition` |
| Шаг назад, выход из `cloud_active` | `game_state_one_way` — даже для владельца и SQL администратора |
| Цель `local`, неизвестное состояние | `game_bad_request` |
| Состояние ≠ ожидаемому `from` | `game_state_conflict` (кто-то уже перевёл аккаунт) |
| Состояние уже = `to` | Повтор: ничего не меняется (`changed: false`) |

- `state_changed_at` ставит страж; подвинуть его нельзя.
- `cloud_active` создаёт пустую проекцию — **XP и Coins не переносятся** (это Q4.5-4).
- `game_begin_migration` и `game_activate_cloud` (0014) идут через переход.
- **Клиентского доступа к переходам нет** — ни функции, ни маршрута.

## 3. Хук `game_access_token_hook`

**Где отметка: отдельное утверждение верхнего уровня `ayra_economy`, не `app_metadata`.**
- Сервер авторизации сам не ставит верхнеуровневых утверждений с таким именем, поэтому его наличие значит «поставил хук из базы».
- `app_metadata` можно записать иначе (Admin API с сервисным ключом), и для экономики оно **не читается**: ни сервером, ни клиентом.
- Изменения минимальны: сервер читает утверждения в одном месте (`lib/game-server/session-token.ts`), клиент — в одном (`lib/economy-mode.ts`).

**Что делает хук:**
- берёт `user_id`, который передал сервер авторизации, и читает **только** `game_accounts.state` (нет строки — `local`);
- данные пользователя не читает, пользовательским утверждениям не доверяет: прежние `ayra_economy` и `ayra_economy_status`, если были, **удаляются и заменяются**;
- **все стандартные утверждения сохраняет как есть** (`iss`, `aud`, `exp`, `iat`, `sub`, `role`, `aal`, `session_id`, `email`, `phone`, `is_anonymous`, `amr`, `app_metadata`, `user_metadata`) и добавляет ровно одно (тесты K1–K3, проверено на настоящем Supabase Auth);
- **понижения не бывает:** состояние в базе только растёт, а хук читает его при каждом выпуске (тест K8: 10 токенов во время активации — каждый `pending` или `cloud_active`; 5 обновлений подряд — всегда текущее);
- **при ошибке чтения не роняет вход:** токен выпускается **без** отметки и с `ayra_economy_status: "unavailable"`. База считает такой токен устаревшим для любого не-`local` аккаунта (fail-closed).

**Права (минимальные):**
- **Владелец и режим.** Хук — `SECURITY DEFINER`, принадлежит `game_economy_owner` (роль без входа); `search_path` закреплён.
- **`supabase_auth_admin`** (роль сервера авторизации) получает **только** `EXECUTE` на хук. Таблиц игры он не видит, переходы и начисления вызвать не может (K10–K12, G4, K6d).
- **`service_role`, `authenticated`, `anon`** хук вызвать не могут — подделать отметку через API нельзя (G2, G8, K6a).
- **Схема `auth`:** ни одна наша роль не имеет на неё прав, ничего туда не пишется.

## 4. Свежесть сессии и начисления

`game_session_check(user, session_id, iat, ayra_economy)`:

| Условие | Ответ |
|---|---|
| В токене нет `session_id` | `session_revoked` |
| Отметка ≠ состоянию сейчас (старая, нет — хук выключен или «unavailable» —, подделка) | `mark_changed` |
| `iat` раньше секунды последней смены | `issued_before_change` |
| Иначе | `fresh: true` |

- **Живая ли сессия — проверяет сервер авторизации.** Маршрут проверяет пользователя через `getUser` именно этим токеном, а сервер авторизации отклоняет токен завершённой сессии даже до `exp`: `403 session_not_found: Session from session_id claim in JWT does not exist` (проверено на настоящем Supabase Auth, раздел 6).
- **Почему база больше не читает `auth.sessions`.** Supabase не позволяет передать права на схему `auth` (раздел 6).
- **Начисление:**
  - только `game_apply_reward_for_session`: `FOR SHARE` на строку аккаунта, проверка свежести, затем `game_apply_reward`;
  - у `service_role` прав на голые `game_apply_reward` и `game_apply_reward_at` **нет** (G11, K6c);
  - идемпотентность прежняя: свежий токен ×10 одновременно → 1 начисление (K4).

## 5. Клиент (адаптация Q4.5-1)

- **Отметка из токена.** `lib/economy-mode.ts`: `sessionEconomyOf(session, source)` читает `ayra_economy` из утверждений **токена этой сессии**; срок берётся из `exp` того же токена.
  - Токен чужого `sub` отметки не даёт.
  - Чтение утверждений — не проверка подписи. Отметка может сделать устройство только строже, а её отсутствие ничего не доказывает (основание `unconfirmed`).
- **При загрузке** (`lib/auth/auth-context.tsx`) путь зависит от возраста сохранённого токена:
  - **токен старше `SESSION_MARK_MAX_AGE_S`** (PLACEHOLDER 600 с) — одно обновление сессии. Отметка живёт только в токенах, и обновление приносит отметку, данную после выпуска старого токена;
  - **токен моложе** — как до Q4.5-2: `getUser` именно с этим токеном (сервер авторизации его проверяет), отметка читается из него — ей не больше 10 минут. В обоих случаях обновляются флаги `hasPassword` / `isOwner`.
- **Почему не обновлять при каждой загрузке.** Так было в `8dc7747`, и CI это поймал:
  - вкладки одного браузера ждали блокировку обновления друг друга (`two-tabs-login`);
  - устройство сразу выходило после глобального выхода на другом (`journal-day-in-life`).
  - Записано в PR до повторов, причина найдена сравнением с main.
- **Защита AuthGeneration** сохранена на обоих путях: ответ для прошлой сессии (выход, другой аккаунт, новый вход) не меняет ничего. Тесты на самом `AuthProvider` проверены мутацией: без неё падают 3; отдельный тест — молодой токен проверяется, а не обновляется.
- **`TOKEN_REFRESHED`, `SIGNED_IN`, `USER_UPDATED`** — источник `verified`, отметка из нового токена.
- **Монотонность:** `mergeSessionEconomy` — строже никогда не откатывается; срок и источник берутся от одного токена; чужой аккаунт заменяет всё; выход очищает.
- **Каждый ответ сервера — только своему аккаунту** (`lib/economy-scope.ts`).
  - Запрос делается для области (scope): загруженное пространство аккаунта, его поколение (сколько раз загружалось пространство), поколение сессии входа (AuthGeneration: выход, другой аккаунт, новый вход того же аккаунта) и id аккаунта.
  - Сервер в каждом ответе называет `account` — пользователя, которого он проверил по токену.
  - Ответ применяется **только** если `account` = аккаунт запроса и область не изменилась: то же активное и загруженное пространство, те же оба поколения. Так — и для немедленного слушателя `session_stale`, и для последующей обработки результата (статус, изменения дня, проверка миссии).
  - Иначе ответ не меняет ничего. Текущее активное пространство само по себе ничего не доказывает.
  - Регрессионные тесты на настоящем `GameProvider` (`lib/economy-scope.test.tsx`):
    - A → B во время запроса;
    - A → гость;
    - выход → вход A с новой сессией;
    - два запроса разных поколений;
    - ответ, называющий другой аккаунт или никакой;
    - корректный `session_stale` без смены аккаунта.
  - Проверено 5 мутациями: каждая удалённая защита роняет от 1 до 6 тестов.
- **`session_stale`:**
  - состояние из отказа передаётся игре **сразу**, до попытки обновить сессию (`onSessionStale`) — устройство перестаёт давать локальные награды, даже если сервер авторизации медленный или сломан;
  - затем одно обновление (не дольше 10 с) и один повтор.

## 7. План активации хука в hosted Supabase (НЕ выполнять без решения владельца)

**1. Только чтение** — права `postgres` на `auth` и версия; ожидается как на локальном стеке:
```sql
select version();
select table_name, privilege_type, is_grantable from information_schema.role_table_grants
 where grantee = 'postgres' and table_schema = 'auth' and table_name in ('users','sessions');
```

**2. Ветка или копия проекта (если будет решение о платной ветке):**
- применить 0014, 0015, 0016, 0018 и выполнить `supabase/tests/game_economy_sessions.sql`;
- в Dashboard ветки: **Authentication → Hooks → Customize Access Token (JWT) Claims hook → Postgres** → схема `public`, функция `game_access_token_hook` → Enable;
- войти синтетическим аккаунтом и проверить утверждение `ayra_economy`.

**3. Production — только после ветки и вашего решения:**
1. применить миграции (до включения хука ничего не меняется: функция есть, но её никто не вызывает);
2. включить хук в Dashboard;
3. проверить вход синтетическим аккаунтом;
4. проверить, что вход реальных пользователей не изменился (аккаунты `local` получают `ayra_economy: local`).

**4. Порядок важен:**
- **функция до хука** — иначе вход не работает (проверено: «Error running hook URI»);
- **хук до любого перехода** — иначе сессии переведённого аккаунта будут устаревшими до появления хука (fail-closed, но экономика недоступна).

**5. Срок JWT** не меняется (ваше решение).

## 8. Наблюдаемость и восстановление

**Диагностика хука:**
- **Сбой хука** виден в логах Auth (Dashboard → Logs → Auth): `Error running hook URI` и текст ошибки базы (например, `permission denied for function game_access_token_hook`). При этом вход и обновление падают с 500.
- **Хук не смог прочитать состояние** — вход работает, но в токене `ayra_economy_status: "unavailable"`. Обнаружение: экономические маршруты отвечают `session_stale` с причиной `mark_changed` для не-`local` аккаунтов. Число таких ответов — метрика.

**Несовпадение JWT и PostgreSQL** — запрос только на чтение для владельца:
```sql
select a.user_id, a.state, a.state_changed_at from public.game_accounts a where a.state <> 'local' order by a.state_changed_at desc;
```
Затем у такого аккаунта сравнить `ayra_economy` в токене с `state`. Ожидаемо расходятся только токены, выпущенные до `state_changed_at` (до часа после смены).

**Восстановить вход, не отключая защиту экономики:**
- если вход падает из-за прав на хук — вернуть `GRANT EXECUTE ON FUNCTION public.game_access_token_hook(jsonb) TO supabase_auth_admin;` (вход сразу работает, проверено);
- если сломана сама функция — исправить миграцией, хук не выключая.

**Безопасно отключить хук** (Dashboard → Hooks → Disable), когда ничего другое не помогло:
- вход сразу работает;
- новые токены без отметки, поэтому база отвечает `session_stale` для всех не-`local` аккаунтов: серверная экономика закрыта, наград нет (fail-closed);
- устройства, уже знающие режим, его не теряют (Q4.5-1, только вперёд);
- аккаунты `local` не затронуты.

**Уже выданные JWT:** остаются действительными до своего `exp` (по умолчанию 1 час) и несут ту отметку, с которой выпущены. Для экономики устаревшие отсекает база; для Журнала и Market они действуют как обычно.

## 9. Безопасный откат

- **Никаких автоматических разрушительных откатов.**
- **Сначала выключить хук, потом откатывать.** Без функции при включённом хуке вход перестанет работать.
- `0018_game_economy_sessions.down.sql`:
  - отказывает, пока есть аккаунт `migration_scheduled`, и ничего не меняет;
  - иначе удаляет хук, проверку свежести, начисление с сессией и переход; возвращает страж, CHECK и функции переходов 0014, а `service_role` — право на `game_apply_reward`;
  - **строк журнала начислений, проекции, источников и состояний не удаляет** — XP, Coins и история сохраняются (тест в блоке Q и проверка на локальном Supabase).
- Откаты 0015 и 0016 выдают и забирают временный `CREATE` так же, как прямые миграции.

## 10. Права на `public` (условия владельца)

| Условие | Как выполнено |
|---|---|
| Право действительно необходимо | Без `CREATE` на `public` новый владелец таблицы или функции не назначается (`permission denied for schema public` на Supabase; проверено) |
| Минимально необходимой роли | Только `game_economy_owner` (без входа, без членов, кроме `postgres`) |
| В контролируемой миграции | `GRANT` — в начале транзакции миграции, `REVOKE` — перед `COMMIT` (0014, 0015, 0016, 0018 и откаты 0015, 0016, 0018) |
| Отзывается после создания объектов | Проверено: после всех миграций `CREATE` нет ни у кого (G6, блок Q, локальный Supabase) |
| Нет неожиданных наследуемых прав | Ни одна API-роль не член `game_economy_owner` (G12, локальный Supabase) |
| Нет новых опасных возможностей у `anon` / `authenticated` / `service_role` | Полная таблица прав на функции (раздел 6) |
| Транзакция с проверяемым откатом | Миграция — одна транзакция; ошибка откатывает и `GRANT` (проверено первым прогоном: 0018 откатилась целиком) |
| Повторное применение не расширяет права | 0014–0018 применены дважды; права те же (локальный Supabase, блок Q) |

## 11. Оставшиеся риски

1. **Офлайн-устройство,** никогда не видевшее отметку, даёт локальные награды. Это предел клиента (F1); сервер их не примет — Q4.5-4.
2. **Токены, выданные до смены,** живут до `exp` (до 1 часа). Экономика их отсекает; устройство без запросов к экономике узнает отметку при следующем обновлении.
3. **Отметка на открытом устройстве** приходит при загрузке, если токен старше 10 минут, при автообновлении токена (до часа) или сразу через `session_stale`, когда включена серверная экономика. Устройство с молодым токеном узнаёт новую отметку не позже чем через 10 минут после выпуска токена. Награды за это время — только локальные, перенос их не примет (Q4.5-4).
3a. **Выход — решение владельца 2026-11-23: «Выйти» завершает сессию только этого устройства** (`signOut({ scope: "local" })` в приложении и в маршруте `/logout`). Другие устройства остаются в аккаунте; отдельной кнопки «выйти на всех устройствах» пока нет.
   - **Проверено на настоящем Supabase Auth (локальный стек, 11 проверок):**
     - завершается только своя сессия; её токен сразу получает `403 session_not_found`;
     - другое устройство работает и обновляет токен;
     - повторный вход создаёт новую сессию;
     - состояние другого аккаунта не меняется;
     - для сравнения: глобальный выход завершает и другое устройство.
   - **Fake Supabase моделирует тот же контракт** (403 для завершённой сессии); e2e `logout-this-device` и `journal-day-in-life` согласованы с ним.
   - **`scope: "others"` после смены пароля оставлен** — это сознательное завершение других сессий ради безопасности.
4. **Отключение хука** закрывает серверную экономику для не-`local` аккаунтов до его возврата (сознательно, fail-closed).
5. **Hosted Supabase:** локальный образ может отличаться версией от production; перед применением нужен запрос из раздела 7 (только чтение).
6. **Выход одновременно с начислением:** если проверка ещё видела живую сессию, начисление засчитывается как сделанное до выхода; дважды — никогда.
7. **Тесты 0015 (`game_days.sql`)** написаны под сигнатуры 0015, которые заменила 0016; вместе с 0016 они не выполняются (так было и до Q4.5-2).
