# Q4.5-2 — Серверная основа безопасного перехода экономики

**Статус.** Вторая фаза Q4.5. **Не готово к применению:** проверка на официальном стеке Supabase показала, что схема отметки требует изменения (раздел 7). Миграция `supabase/migrations/0018_game_economy_sessions.sql` (откат: `0018_game_economy_sessions.down.sql`) лежит в репозитории и проверяется в CI на PGlite и на настоящем PostgreSQL 16. **В Supabase не применяется.**

**Ничего не включено:**
- ни один аккаунт не меняет состояние;
- отметка `ayra_economy` не записана ни одному пользователю;
- флаги `NEXT_PUBLIC_AYRA_SERVER_ECONOMY`, `AYRA_SERVER_MISSION_PAYOUTS`, `NEXT_PUBLIC_AYRA_MISSION_SHADOW` не тронуты;
- вид начисления `mission` выключен;
- перенос прогресса не запускается — это Q4.5-4.

Локальная экономика работает как раньше. Серверные маршруты по-прежнему закрыты переключателем (404). Без применённых миграций они отвечают 503 `server_economy_unavailable`, как в Q4.4.

## 1. Архитектура

```
Приложение ──▶ Next.js route (app/api/game/day/*, /api/game/missions/verify)
  1. Пользователь: getSession → getUser(ЭТОТ токен) — подпись и срок проверяет сервер авторизации.
  2. Из этого же токена читаются только session_id, iat, app_metadata.ayra_economy (lib/game-server/session-token.ts).
  3. Тело запроса проверяется строго (как в Q4.4); плохой запрос не доходит до базы.
  4. game_session_check(user, session_id, iat, mark) — ответ даёт БАЗА:
       свежая → действие; устаревшая → 401 session_stale + состояние аккаунта (своё, из базы).
  5. Начисление — только game_apply_reward_for_session(...): база ещё раз проверяет сессию,
     держа строку аккаунта, и только потом вызывает game_apply_reward.
PostgreSQL (одна база с Supabase Auth):
  game_accounts.state / state_changed_at  ←→  auth.users.raw_app_meta_data.ayra_economy  (одна транзакция)
                                         ←→  auth.sessions / auth.refresh_tokens        (удаление — по запросу)
```

**Почему атомарность возможна.** Таблицы Supabase Auth (`auth.users`, `auth.sessions`, `auth.refresh_tokens`) лежат в той же базе PostgreSQL, что и таблицы игры. Поэтому смена состояния, отметка в сессии и (по запросу) удаление сессий выполняются в **одной транзакции**: либо всё, либо ничего. Это проверено тестами: при сбое записи в `auth.users` состояние не меняется (A1–A2).

**Чего атомарность не даёт** — граница, а не недосмотр:
- уже выданный access token нельзя «отозвать»: это подписанный JWT без состояния, он действует до `exp` у сервера авторизации и PostgREST;
- поэтому отсечение для экономики делает база на каждом экономическом запросе (раздел 4), а не удаление сессий.

### Роли и права (минимальные)

| Роль | Что может | Чего не может |
|---|---|---|
| `game_economy_owner` (0014, NOLOGIN) | Таблицы игры; функция перехода; проверка сессии; начисление | **Никаких прав на схему `auth`** (тест A4, G4) |
| `game_auth_marker` (новая, NOLOGIN, без членов) | `UPDATE (raw_app_meta_data)` на `auth.users`; `DELETE` на `auth.sessions`, `auth.refresh_tokens`; чтение `game_accounts.state` | Писать в таблицы игры; отметку, которая не равна состоянию аккаунта (`game_mark_not_state`, A3) |
| `service_role` (маршрут) | `game_economy_transition`, `game_session_check`, `game_apply_reward_for_session` | `game_apply_reward` напрямую (отозвано), `game_auth_mark`, `SET ROLE game_auth_marker`, запись в `auth.users` (G2, G6–G7, K6a–d) |
| `authenticated`, `anon` | Читать своё состояние (RLS) | Любую функцию перехода, проверки, отметки, начисления (G1, G9) |

Функцию отметки `game_auth_mark` может вызвать только `game_economy_owner`, то есть только изнутри перехода.

## 2. Модель состояний

```
local ──▶ migration_scheduled ──▶ migration_pending ──▶ cloud_active (навсегда)
  └──────────────────────────────▶ migration_pending
```

| Переход | Разрешён | Что ещё происходит |
|---|---|---|
| `local → migration_scheduled` | Да | Отметка `migration_scheduled` |
| `local → migration_pending` | Да (перенос без заблаговременного уведомления) | Отметка |
| `migration_scheduled → migration_pending` | Да | Отметка |
| `migration_pending → cloud_active` | Да | Отметка; пустая проекция `game_profile`, `activated_at`; **XP и Coins не переносятся** |
| Любой пропуск (`local → cloud_active`, `scheduled → cloud_active`) | Нет — `game_state_invalid_transition` | — |
| Любой шаг назад, выход из `cloud_active` | Нет — `game_state_one_way` (даже для владельца и SQL администратора) | — |
| Цель `local`, неизвестное состояние | Нет — `game_bad_request` | — |

**Функция** `game_economy_transition(user, from, to, revoke_sessions = false)`:
- **сравнение с ожидаемым (compare-and-set).** Вызывающий называет состояние, которое он видел (`from`). Строка аккаунта блокируется (`FOR UPDATE`):
  - состояние = `from` → переход;
  - состояние уже = `to` → повтор: отметка проверяется, больше ничего не меняется (`changed: false`);
  - иначе → `game_state_conflict` (кто-то уже перевёл аккаунт).
- **Время смены** `state_changed_at` ставит страж (триггер 0014, расширенный в 0018). Подвинуть его вручную нельзя никому (H1).
- **0014-функции** `game_begin_migration` и `game_activate_cloud` сохранили сигнатуры и теперь идут через переход, поэтому сменить состояние без отметки нельзя (B1–B5).

**Кто вызывает переход.** Только `service_role`, и маршрута для этого **нет**: клиент не может ни вызвать переход, ни назвать состояние. Как владелец будет запускать переходы (скрипт администратора с проверкой, отдельный защищённый инструмент) — решение для Q4.5-3/Q4.5-4.

## 3. Отметка в сессии

- `auth.users.raw_app_meta_data.ayra_economy` пишет только `game_auth_mark`. Остальные ключи `app_metadata` (`provider`, `providers`, роль владельца) сохраняются (T2).
- Сервер авторизации кладёт `app_metadata` в каждый новый токен. Поэтому после смены состояния новая отметка приходит устройству при обновлении токена или при чтении пользователя (Q4.5-1).
- Отметку нельзя записать отдельно от состояния: функция отказывает, если отметка ≠ текущему состоянию строки аккаунта.

## 4. Свежесть сессии для экономики

`game_session_check(user, session_id, iat, mark)` — ответ `{state, fresh, reason}`:

| Условие | `reason` |
|---|---|
| Сессии с этим `session_id` у этого пользователя нет (удалена, чужая, истекла по `not_after`, не передана) | `session_revoked` |
| Отметка в токене ≠ состоянию аккаунта сейчас (нет отметки, старая, подделанная) | `mark_changed` |
| Токен выпущен раньше секунды последней смены (`iat < floor(state_changed_at)`) | `issued_before_change` |
| Иначе | `fresh: true` |

- **Почему отметка — главный признак, а `iat` — дополнительный.** Отметка пишется в той же транзакции, что и состояние. Значит, токен с текущей отметкой выпущен **после** фиксации смены. `iat` в секундах, и одна его проверка пропустила бы токен, выпущенный в ту же секунду до фиксации; отметка этот случай закрывает.
- **Аккаунт, который никогда не переводили** (`local`, без строки), свеж без отметки — существующие пользователи не замечают Q4.5-2 (C6).
- **Маршрут** проверяет также, что `sub` токена = пользователь, подтверждённый сервером авторизации.
- **Ответ `session_stale`** (401) содержит `state` — состояние аккаунта самого пользователя из базы — и `reason`. Неизвестные значения не передаются.

### Начисления

`game_apply_reward_for_session(...)`:
1. `SELECT … FOR SHARE` строки аккаунта — переход ждёт конца начисления, или начисление ждёт перехода;
2. `game_session_check` → не свежая: `game_session_stale`;
3. `game_apply_reward` (0014–0015, без изменений: идемпотентность, доказательства, лимиты).

У `service_role` право на голый `game_apply_reward` **отозвано**: начислить в обход проверки сессии нельзя (G2, G6, K6c).

### Удаление сессий

- **По умолчанию `revoke_sessions = false`.** Обновить токен можно, и новый токен несёт новую отметку. Человек не выходит из аккаунта, а старый токен для экономики уже отсечён проверкой выше.
- **`revoke_sessions = true`** удаляет все сессии и refresh-токены аккаунта (включая токены без сессии). Устройства должны войти заново. Чужие сессии не трогаются (R1–R3, K5).
- **Удаление сессии не делает выданный access token недействительным.** Он отсекается для экономики проверкой `session_revoked`. Для остальных запросов к Supabase (Журнал, Market) он действует до `exp` — это свойство Supabase, а не Q4.5-2.

## 5. Клиент на `session_stale`

`lib/server-day-client.ts`:
- **ровно одно** обновление сессии (`auth.refreshSession`) и **ровно один** повтор запроса. Отказанный запрос на сервере ничего не изменил, поэтому повтор безопасен;
- обновление не удалось (офлайн, сессия удалена) — повтора нет, ответ сохраняет `state` из отказа;
- `lib/game-context.tsx` запоминает это состояние только вперёд (`rememberMode`) и только для загруженного пространства этого аккаунта. Устройство перестаёт давать локальные награды, даже если обновить сессию нельзя;
- новый токен приносит отметку, и Q4.5-1 применяет её (`TOKEN_REFRESHED` → `sessionEconomy`);
- другие отказы и обрыв сети никогда не обновляют сессию.

## 6. Что видит человек

Ничего нового. Строки плашки — из Q4.4 и Q4.5-1. Отказ `session_stale` обрабатывается без сообщения: обновление происходит само, а состояние берётся из ответа.

## 7. Проверка на настоящем Supabase и решения владельца

### Где проверялось
- **Hosted Supabase Branch не создавалась.** Ветки (Branching) — платная функция плана Pro. Токена доступа к аккаунту Supabase в этой среде нет. По решению владельца в таком случае ветка не создаётся.
- **Вместо неё — официальный локальный стек Supabase** (`supabase start`, CLI 2.30.4): образы `supabase/postgres:17.4.1.048` и `supabase/gotrue:v2.176.1`.
  - Схему `auth` создали миграции GoTrue; владелец таблиц — `supabase_auth_admin`. Роль `postgres` без суперпользователя, как в hosted.
  - Полностью изолирован: проект не связан ни с одним удалённым (`supabase link` не выполнялся), база пустая (0 пользователей), только этот компьютер.
  - После проверки контейнеры и тома удалены.
- **Ограничение.** Версия образа может отличаться от production (там может быть PostgreSQL 15). Права `postgres` на `auth` в Supabase одинаковы во всех версиях с 2025 года, но это нужно подтвердить на настоящем проекте только чтением (запрос ниже).

| 6 | 0018 откатилась целиком: ни роли, ни функций не создано | — | Миграция атомарна и при ошибке прав | Проверено |

### Варианты для владельца

**По находке 2 (0014–0016 и 0018):**
- **(А, рекомендую)** Временно выдать `CREATE ON SCHEMA public` роли `game_economy_owner` в начале каждой миграции и забрать в её конце, в той же транзакции. Роль без входа (NOLOGIN); право существует только на время миграции. Проверено локально: так 0014–0016 применяются.
- **(Б)** Отдельная схема `game`, принадлежащая `game_economy_owner`. Постоянных прав на `public` не нужно, но это большая переделка 0014–0016.

**По находке 3 (отметка в сессии):**
- **(1, рекомендую) Custom Access Token Hook** — штатный механизм Supabase. Сервер авторизации при выпуске **каждого** токена вызывает нашу функцию, и она добавляет в токен `ayra_economy` из `game_accounts.state`.
  - Писать в `auth` не нужно; более привилегированная роль не нужна. Функции хука нужно только чтение состояния — узкое право для `supabase_auth_admin`.
  - Отметка в токене — всегда зафиксированное состояние на момент выпуска, поэтому «токен с текущей отметкой выпущен после смены» выполняется само собой.
  - Нужно: включить хук в Dashboard (Authentication → Hooks) — настройка проекта, только вашим действием, плюс изменение клиента. Q4.5-1 читает отметку из `user.app_metadata`, а хук пишет её в утверждения токена — клиент будет читать утверждения токена.
  - Удаление сессий при этом варианте недоступно; вы и так решили держать его выключенным.
  - Проверяется на локальном стеке Supabase (хук настраивается в `config.toml`) без ветки и без production.
- **(2)** Функция отметки от имени `postgres`. Проверено: у `postgres` есть нужные права, атомарность сохраняется. Но права заметно шире (CREATEROLE, BYPASSRLS) — **запрещено без вашего согласования**, не делаю.
- **(3)** Отметка через Admin API с сервисным ключом и очередь записи. Состояние атомарно в базе, а отметка появляется с задержкой; до этого экономика закрыта (fail-closed). Сложнее, есть окно рассинхронизации.

**Остальные решения уже приняты:** удаление сессий по умолчанию выключено; срок JWT не меняется; production SQL не применяется.

**Перед любым применением в production** — только чтение, без изменений:
```sql
select table_name, privilege_type, is_grantable from information_schema.role_table_grants
 where grantee = 'postgres' and table_schema = 'auth' and table_name in ('users','sessions','refresh_tokens');
select version();
```

## 8. Оставшиеся риски

1. **Офлайн-устройство,** которое никогда не видело отметку, продолжает давать локальные награды. Это физический предел клиента (Q4.5-1, F1). Сервер их не примет: граница — снимки в Q4.5-4.
2. **Сервисный ключ + Admin API** (`auth.admin.updateUserById`) могут записать любую `ayra_economy`. Поддельная отметка ≠ состоянию в базе, поэтому сервер отвечает `session_stale` и экономику не открывает. Клиент от такой отметки станет только строже. Ключ хранится только в Vercel env и в `app/api/**/route.ts` (T7a).
3. **Для неэкономических запросов** (Журнал, Market) старый access token действует до `exp`.
4. **Проверка сессии и действие дня** (принять, «не сегодня», режим) — два вызова, не одна транзакция. Окно не даёт наград: решения принимает база по своему состоянию, а начисление проверяет сессию атомарно (K3, K4).
5. **Повтор на клиенте после `session_stale`** — один. Если сразу после обновления состояние меняется ещё раз, ответ остаётся `session_stale`, а следующий запрос (фокус, действие) повторит обновление.
6. **0018 в нынешнем виде на Supabase не применяется** (раздел 7, находки 2–3): нужна смена схемы отметки (вариант 1) и решение по правам на `public` (вариант А).
7. **`game_days.sql` (тесты 0015)** написан под сигнатуры 0015, которые заменила 0016. Поэтому вместе с 0016 и 0018 он не выполняется — так было и до Q4.5-2 (блок P запускает его только после отката 0016). Проверено отдельным прогоном на 0014–0016 без 0018: тот же отказ A1.

## 9. Откат

`0018_game_economy_sessions.down.sql`:
- отказывает, пока есть аккаунт `migration_scheduled` (в 0014 такого состояния нет), и ничего не меняет;
- иначе удаляет функции 0018, возвращает страж, CHECK и функции переходов 0014, возвращает `service_role` право на `game_apply_reward`, удаляет роль `game_auth_marker`;
- отметки в `auth.users` остаются. Они только делают клиента строже, и до применения 0018 ни одной не будет.

## 11. Что нужно для Q4.5-4 (перенос прогресса)

1. **Приём снимка** — своей функцией, которая, как начисление, держит строку аккаунта и проверяет сессию той же логикой:
   - отметка = `migration_pending`;
   - `iat ≥ state_changed_at` смены на `migration_pending`.
   Снимок от сессии до объявления переноса не принимается.
2. **Время приёма — серверное.** После `cloud_active` снимки не принимаются никогда.
3. **Один снимок на устройство.** Карантинная таблица `game_imports`, идемпотентно; более поздний прогресс устройства не принимается.
4. **Сведение по каноническим ключам** (`mission:<day>:<id>`, `daily:<day>`, `first:<kind>`, `pq:<runId>`), не по балансам. Coins пересчитываются из данных (правило 2026-10-27).
5. **Инструмент владельца для переходов** (`game_economy_transition`): кто запускает, с какой проверкой, с журналом действий.
6. **Решения владельца:**
   - `revoke_sessions` для `migration_pending`;
   - офлайн-устройства после окна переноса (Q4.5-1, решение 5 аудита);
   - непроверяемый остаток (В-26).
