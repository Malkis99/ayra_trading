## 1. Цель и границы

**Цель.** Один аккаунт видит одни и те же данные на всех устройствах. XP и монеты начисляет только сервер.

**Что синхронизируется:**
- Журнал: счета, сделки, стратегии, записи «не вошёл», планы дня и недели с разборами, заметки, партии импорта.
- Вложения (скриншоты сделок).
- Профиль: «О себе», страна, опыт, рынки, стиль, соцсети, видимость. Ник уже в `profiles`.
- Персонаж: внешность, экипировка, рамка, титул, фон сцены.
- Прогресс: XP, уровень, монеты, квесты, достижения, серии, хроника — **только через сервер**.
- Соцданные: подписки и лайки профиля. Модель есть, событий пока нет.

**Что не синхронизируется:**
- ключи устройства: язык интерфейса, «аренда» знакомства, события вкладок, флаги баннеров;
- гостевые данные — остаются на устройстве, перенос в аккаунт идёт через уже готовый экран `/profile-select` (C1);
- черновики знакомства до его завершения.

**Вне T7b:** Telegram (T7c), удаление и слияние аккаунтов (T7d), кейсы и маркетплейс (T12), лента и комментарии Сообщества (T11), Realtime-подписки — пока синхронизация при входе, при возврате на вкладку и по таймеру.

## 3. Принципы

1. **Сервер — источник правды для аккаунта.** Локальное хранилище аккаунта — кэш для быстрого открытия и работы без сети.
2. **Офлайн-очередь.** Изменения сначала пишутся локально и в очередь отправки (outbox), потом уходят на сервер. При сбое — повтор с паузами.
3. **Last-write-wins по записи** (не по всему журналу) **с диалогом конфликта**, когда одну и ту же запись изменили на двух устройствах после последней синхронизации.
4. **Награды — только сервер:**
   - клиент присылает **событие** («записал сделку», «выполнил квест», «прикрепил скриншот»);
   - сервер проверяет правила и лимиты и пишет **запись в книгу учёта (ledger)**;
   - баланс = сумма записей;
   - клиент не может вставить или изменить запись в книге.
5. **Идемпотентность:**
   - у каждого события уникальный ключ (например, `quest:q_tradelog:2026-10-15`, `trade:tr_123:xp`);
   - повтор запроса не создаёт второе начисление.
6. **Целые числа** для XP и монет, никаких дробей.
7. **RLS везде:** пользователь видит и меняет только свои строки. Чужие данные — только через специальные функции с учётом видимости профиля.
8. **Без новых тяжёлых зависимостей:** используется `@supabase/supabase-js`, который уже есть.

## 4. Таблицы (эскиз; точный SQL — в миграциях после подтверждения)

### 4.1 Журнал — общая форма таблиц

Для каждой сущности журнала своя таблица:
- `journal_accounts`, `journal_trades`, `journal_strategies`, `journal_no_trades`;
- `journal_day_plans`, `journal_week_plans`, `journal_notes`, `journal_import_batches`.

Общие колонки:

| Колонка | Тип | Зачем |
|---|---|---|
| `user_id` | uuid → `auth.users`, часть первичного ключа | владелец, RLS |
| `id` | text (как сейчас в приложении: `tr_…`, `acc_…`), часть первичного ключа | связь с локальными записями без перекодирования |
| `data` | jsonb | сама запись в формате приложения (схема версии `schema_version`) |
| `schema_version` | int | миграции формата записи |
| `client_updated_at` | timestamptz | время изменения на устройстве — для last-write-wins |
| `updated_at` | timestamptz, ставит сервер (триггер) | курсор «что изменилось с прошлой синхронизации» |
| `deleted_at` | timestamptz null | мягкое удаление («надгробие») |
| `device_id` | text | какое устройство сделало последнее изменение (для текста диалога конфликта) |

Плюс вынесенные поля для поиска и будущей аналитики на сервере:
- сделки: `account_id`, `opened_at`, `instrument`, `verification`;
- планы: `date_key`;
- «не вошёл»: `date_key`.

**Почему `jsonb`, а не все поля колонками.** Модель журнала большая и ещё меняется (проп-правила, Process Score, разборы). `jsonb` + `schema_version` повторяет локальную модель один в один, и её можно развивать без миграции на каждое поле. Поля, по которым нужен поиск, вынесены отдельно. Проверка формата — на клиенте (типы) и минимальная на сервере (`CHECK` на обязательные ключи).

Индексы: `(user_id, updated_at)` во всех таблицах; `(user_id, opened_at)` у сделок.

### 4.2 Вложения

- Таблица `journal_attachments`: `user_id`, `id`, `trade_id`, `sha256`, `mime`, `size_bytes`, `width`, `height`, `storage_path`, `created_at`, `deleted_at`.
- **Приватный bucket** Storage `journal-attachments`:
  - путь файла `{user_id}/{attachment_id}`;
  - политики Storage: читать и писать только в свою папку (`(storage.foldername(name))[1] = auth.uid()::text`);
  - публичного доступа нет.
- Показ — через **подписанные ссылки** (`createSignedUrl`), срок жизни **60 минут** `PLACEHOLDER`. Приложение кэширует ссылку до истечения.
- Лимиты: размер файла и общий объём на аккаунт — `PLACEHOLDER` (сейчас локально есть только предупреждение о квоте браузера).
- Дубли: уникальность `(user_id, sha256)`. Повторная загрузка того же файла не занимает место дважды. Это совпадает с локальным правилом «тот же хэш не даёт XP».

### 4.3 Профиль и персонаж

- **`profiles`** (уже есть): добавить `bio`, `country`, `experience`, `markets text[]`, `styles text[]`, `socials jsonb`, `visibility` (`public`/`hidden`). Расширить разрешение UPDATE на эти колонки. Ник и правило 14 дней уже на сервере (0003).
- **`character_state`** (одна строка на пользователя): `appearance jsonb`, `equipment jsonb`, `frame int`, `selected_title text`, `stage_background text`, `updated_at`.
  - Клиент может менять (это оформление, наград за него нет).
  - Сервер проверяет, что предмет/титул/рамка **открыты** — по уровню и достижениям из книги учёта. Иначе можно «надеть» закрытый предмет, подменив запрос.

### 4.4 Прогресс и экономика (только сервер)

| Таблица | Назначение | Кто пишет |
|---|---|---|
| `reward_events` | входящие события от клиента: `user_id`, `type`, `payload jsonb`, `idempotency_key` (unique по пользователю), `status` (`accepted`/`rejected` + причина), `created_at` | клиент через RPC `submit_event()`; напрямую — нельзя |
| `ledger_entries` | книга учёта, **только добавление**: `user_id`, `currency` (`xp`/`coins`), `amount int` (может быть отрицательной только у компенсирующей записи), `source` (из списка разрешённых), `event_id`, `rules_version`, `created_at` | только серверная функция |
| `quest_completions` | `user_id`, `quest_id`, `day` — unique; основа идемпотентности квестов | только сервер |
| `achievements` | `user_id`, `achievement_id` — unique, `unlocked_at` | только сервер |
| `streaks` | текущая и лучшая серия, щиты, дата последней активности | только сервер |
| `chronicle` | лента событий персонажа (последние N) | только сервер |
| `reward_rules` | версии правил: XP за квест/сделку/скриншот, дневные лимиты, ежедневная награда; `version`, `rules jsonb`, `active_from` | **только владелец** (изменение экономики — с подтверждения) |
| view `balances` | `xp_total`, `coins_total`, `level` = сумма записей книги | чтение |

**Функция `submit_event(type, payload, idempotency_key)`** (`SECURITY DEFINER`):
1. Проверяет вход, тип события и формат.
2. Проверяет идемпотентность: тот же ключ — вернуть прежний результат.
3. Проверяет правила текущей версии: дневные лимиты по источнику и в целом, правдоподобие (дубли сделок за минуту, даты из будущего), **импортированные сделки — 0** (решение владельца 2026-10-14).
4. В одной транзакции пишет записи книги учёта, отметку квеста или достижения и строку хроники.
5. Возвращает новые итоги (XP, уровень, монеты, что открылось). Клиент показывает их, но сам ничего не считает.

**Ежедневная награда, квесты, серии, щиты** — тоже события; дата «сегодня» считается по часовому поясу профиля на сервере.
**Kill switch:** флаг в `reward_rules` (или отдельная таблица) мгновенно останавливает начисления.
**Сверка:** в будущем — задание по расписанию, проверяющее, что балансы равны сумме книги (раздел 2.7 spec v1.2). В T7b — проверочный SQL в `supabase/checks/`.

### 4.5 Соцданные

- `follows` (`follower_id`, `followee_id`, `created_at`): первичный ключ — пара; `CHECK (follower_id <> followee_id)` — подписаться на себя нельзя.
- `profile_likes` (`user_id`, `profile_id`, `created_at`): то же правило.
- Счётчики — функция `social_counts(profile_id)`: возвращает числа владельцу всегда, другим — только при `visibility = 'public'`.
- Списки подписчиков и подписок открываются вместе с Сообществом (T11). В T7b — только таблицы, правила и счётчики.
- Лимиты на частоту подписок (анти-фарм, spec v1.2 §3) — `PLACEHOLDER`, вводятся вместе с T11.

## 6. Как идёт синхронизация

### 6.1 Первый вход на устройстве (кэш аккаунта пуст или сервер пуст)

1. **Сервер пуст, локально есть данные аккаунта** (кто пользовался до T7b): одна загрузка всего журнала, вложений, профиля и персонажа.
   - Прогресс (XP, монеты) переносится **отдельным событием `migration`** — см. 6.4.
2. **Сервер не пуст, локально пусто:** скачать всё (журнал — страницами по `updated_at`, вложения — по требованию, через подписанные ссылки).
3. **Данные есть и там, и там:** объединение по `id`.
   - Запись есть только с одной стороны — берётся она.
   - Запись есть с обеих сторон и отличается — правило 6.3.

### 6.2 Обычная работа

- **Отправка:** каждое изменение пишется локально и попадает в очередь (`ayra_sync_outbox`, AppStorage пространства аккаунта). Очередь отправляет пачками, при ошибке повторяет с паузами (1 с, 5 с, 30 с, 2 мин). Видно в интерфейсе: «Сохранено в облаке» / «Ждёт сети».
- **Получение:** при входе, при возврате на вкладку и раз в N минут (`PLACEHOLDER`, предлагаю 5) — запрос «что изменилось с `last_pulled_at`» по каждой таблице.
- **Несколько вкладок:** синхронизацию ведёт одна вкладка-«лидер» (тот же механизм аренды, что у знакомства). Остальные получают изменения через существующий канал событий вкладок.
- **Смена аккаунта:** перед переключением пространства очередь сбрасывается (как уже сделан flush). Чужая очередь не уходит в другой аккаунт.

### 6.3 Конфликты: last-write-wins с диалогом

- **Конфликт** — когда запись изменена на сервере (`updated_at` новее, чем последняя синхронизация этой записи) **и** на устройстве (есть неотправленное изменение).
- **Без конфликта** побеждает более позднее `client_updated_at` — молча.
- **При конфликте** — диалог со сравнением ключевых полей: например, у сделки результат, инструмент, заметка, время изменения и устройство. Варианты:
  - «Оставить версию с этого устройства»;
  - «Взять версию из облака»;
  - для сделок и заметок ещё «Сохранить обе» — вторая сохраняется копией с новым `id`.
  
  Пока диалог не решён, обе версии хранятся, ничего не теряется.
- **Удаление против изменения:** если на одном устройстве запись удалили, а на другом изменили — тоже диалог («Восстановить» / «Удалить»).
- Для **персонажа и профиля** конфликт решается полем к полю: побеждает более позднее изменение, без диалога. Это оформление, потеря невелика.
- **Прогресс** конфликтов не имеет: его считает только сервер.

### 6.4 Перенос уже накопленного прогресса (один раз) — нужно решение владельца

Локальным XP и монетам доверять нельзя (их можно было подменить в браузере). Варианты:
- **А (рекомендую):** одно событие `migration` с текущими локальными значениями, ограниченное потолком (`PLACEHOLDER`, например «не больше X XP и Y монет»). Запись в книге с источником `migration`, по одной на аккаунт (идемпотентно). Для честных бета-пользователей прогресс сохранится, а «накрученный» ограничен.
- **Б:** начать прогресс с нуля после включения T7b.
- **В:** пересчитать прогресс на сервере по истории (квесты, сделки) — точнее всего, но локальная история неполная (хранится ограниченно).

### 6.5 Гость

Ничего не меняется: всё на устройстве. При входе — уже существующее предложение перенести данные гостя (C1). Перенесённые данные дальше синхронизируются как данные аккаунта.

## 8. Изменения в приложении (после миграций)

1. **Подготовка локальной модели:**
   - `updatedAt` для счетов, стратегий и «не вошёл»;
   - мягкое удаление (`deletedAt`) во всём журнале;
   - `deviceId` (ключ устройства);
   - миграция локальной схемы журнала v5 → v6.
2. `SupabaseJournalRepository` — та же интерфейсная форма `JournalRepository`. Над ним — **движок синхронизации** (outbox, pull по курсору, слияние, конфликты). Для гостя остаётся `LocalStorageJournalRepository`.
3. **Вложения:** загрузка в bucket после сохранения сделки, показ через подписанные ссылки, локальный кэш файлов в IndexedDB.
4. **Игровой контекст:** вместо локального начисления — вызов `submit_event`; локальное состояние обновляется ответом сервера. Для гостя остаётся локальная логика, без облака.
5. **Профиль и персонаж:** чтение и запись в `profiles` / `character_state`.
6. **Соцданные:** `SupabaseSocialRepository` (интерфейс `SocialRepository` уже есть).
7. **Интерфейс:**
   - значок состояния синхронизации («Сохранено в облаке» / «Ждёт сети» / «Нужно решить конфликт»);

## 9. Риски

- **Удаление «воскресает» без надгробий** — поэтому шаг 1 обязателен до любой синхронизации журнала.
- **Часы устройства врут** (last-write-wins по `client_updated_at`). Курсор синхронизации — по серверному `updated_at`. Если время устройства сильно расходится с сервером (больше 5 минут, `PLACEHOLDER`), конфликт решается через диалог, а не молча.
- **Объём вложений** в бесплатном тарифе Supabase — нужны лимиты на аккаунт (вопрос 3).
- **Переход наград на сервер** меняет ощущение мгновенности: XP показывается после ответа сервера (обычно меньше 1 с). Без сети событие ждёт в очереди и начисляется позже — показываем «Начислится после подключения».
- **16–17:** никаких дополнительных данных не собираем. Режим 16–17 хранится в `profiles` (уже есть), правила Pack 15.3 соблюдаются.

## 12. Решения владельца (2026-10-18)

1. **Журнал:** запись целиком в `jsonb` + отдельные колонки для поиска и фильтров (`id`, `user_id`, `account_id`, дата, инструмент, направление, результат, `updated_at`, `deleted_at`). Версия схемы записи — внутри самой записи (`data.schemaVersion`), отдельной колонки нет.
2. **Включение — флаг на аккаунт:** сначала аккаунт владельца, потом закрытая бета, потом все. Пока флаг выключен, приложение работает как сейчас, только локально. Откат — выключить флаг. Флаг хранится в `public.user_features.cloud_sync` (миграция 0004), меняет его только владелец.
3. **Конфликты:** last-write-wins по `updated_at` записи; при расхождении — диалог «Оставить это устройство / Взять из облака». Удаление мягкое (`deleted_at`).
4. **Перенос прогресса:** вариант **Б** — XP и монеты аккаунта начинаются с нуля. Гостевые данные в аккаунт автоматически не переносятся (правило уже действует). XP и монеты считает только сервер (append-only ledger, идемпотентные награды, дневные лимиты по spec v1.2).
5. **Вложения:** приватный bucket, подписанные ссылки. Лимиты — плейсхолдеры: **5 МБ на файл, 200 МБ на аккаунт**, вынесены в константы (меняются без миграции).
6. **Посты и соцчасть в T7b не входят:** их таблицы создаются на этапе Сообщества (T11). Миграция 0008 из раздела 7 переносится туда.

### Как это сделано в 0004

- 9 таблиц: `journal_accounts`, `journal_trades`, `journal_strategies`, `journal_no_trades`, `journal_day_plans`, `journal_week_plans`, `journal_notes`, `journal_import_batches` и `journal_settings` (одна строка на пользователя: основной проп-счёт).
- Колонки для поиска заполняет **сервер** из `data` (триггер), клиент пишет только `id`, `data`, `device_id`. Поэтому колонки и запись не могут разойтись.
- Время изменения записи — `client_updated_at` (из `data.updatedAt`); более старая версия не перезаписывает более новую. `updated_at` ставит сервер — это курсор «что изменилось».
- Время из будущего (больше чем на 5 минут, `PLACEHOLDER`) отклоняется — иначе такая запись побеждала бы всегда.
- Писать в облако можно только при включённом флаге; читать свои строки — всегда.
- В `data` нельзя положить поля наград (`xp`, `coins` и т. п.) — награды появятся только в серверной книге учёта (0007).
- Размер одной записи — до 256 КБ (`PLACEHOLDER`).

### Отклонения от первоначального плана (приняты владельцем 2026-10-18)

- **Таблица `journal_settings`** — её не было в эскизе 4.1. Хранит настройки журнала целиком (сейчас — основной проп-счёт), одна строка на пользователя, `id = 'journal'`.
- **Флаг включения — в базе, в 0004**, а не переменной окружения `NEXT_PUBLIC_AYRA_SYNC` в конце (раздел 8, пункт 8). Это `public.user_features.cloud_sync` на каждый аккаунт; меняет только владелец; без флага сервер не принимает запись. Так можно включать по одному аккаунту и откатываться без релиза.
- **Нет колонки `schema_version`** — версия схемы внутри записи (`data.schemaVersion`).
- **Подтверждённые плейсхолдеры:** до 256 КБ на запись; время изменения из будущего больше чем на 5 минут отклоняется.

### T7b-3: облачный репозиторий журнала

- `CloudJournalRepository` (`lib/journal/cloud`) — тот же интерфейс `JournalRepository`. Рабочая копия — локальный журнал: чтение всегда локальное, запись сначала локально. Затем, **только если у аккаунта включён флаг**, изменённые записи уходят в облако в фоне (upsert, сервер оставляет более новую версию), удаление — мягкое.
- При входе на экран Журнала — забор изменений из облака по курсору `updated_at`; более новая облачная версия заменяет локальную (last-write-wins, без диалога).
- Флаг выключен, гость, нет сети, ошибка сервера — Журнал работает как раньше, локально; ошибки не показываются и не ломают сохранение.
- Клиент сам не присылает колонки для поиска; поля XP, монет, достижений и квестов в облачную запись не попадают; записи больше лимита и «из будущего» не отправляются.
- Лимиты — в `lib/journal/cloud/config.ts`.
- **Ещё нет (T7b-4):** очередь изменений с повторами (сейчас неудачная отправка повторится только при следующем изменении записи), диалог конфликта, первая загрузка уже накопленных локальных данных по кнопке, значок состояния.
