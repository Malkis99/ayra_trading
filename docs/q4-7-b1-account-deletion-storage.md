# Q4.7-Б1 — Удаление аккаунта вместе с файлами Storage

Основа: `main` `2705a92` (merge #226). Миграция — `supabase/migrations/0023_account_deletion.sql` (+ откат). Нигде не применялась. Реальные аккаунты и файлы не трогались.

## 1. Перечень хранилищ (аудит)

**Storage — один bucket.**

| Bucket | Кто создаёт файлы | Путь | Владелец | Правила доступа | Связь с PostgreSQL | Замена и удаление |
|---|---|---|---|---|---|---|
| `journal-attachments` (приватный, 0005) | приложение, только с сессией самого человека (`lib/journal/cloud/attachment-files.ts`) | `<user id>/<attachment id>.<webp\|png\|jpg>` | `owner_id` — ставит **сервер Storage** по сессии загрузившего; папка — правило вставки требует `<auth.uid()>/…` | чтение и вставка только в своей папке; удаление своей папки — через 30 дней после удаления строки или для файла без строки старше 24 ч; замены нет | `journal_attachments.file_path` (строка может отсутствовать: прерванная загрузка) | файлы не заменяются |

**Чего нет:** аватаров, других загрузок, общих файлов, загрузок от имени service role.

**PostgreSQL.** Каждая таблица с данными человека ссылается на `auth.users` с `ON DELETE CASCADE`:
- профиль: `profiles`, `telegram_identities`, `link_tokens`, `audit_log`;
- `user_features`, все `journal_*`, `journal_attachments`;
- `market_user_data`;
- уведомления;
- все `game_*` с `user_id`.

`game_shadow_diagnostics` колонки `user_id` не имеет и обезличена.

**Принадлежность файла** определяется не по пути из запроса: объект — файл аккаунта, только если его папка равна id аккаунта **и** `owner_id` (ставит сервер Storage) тоже равен ему. Любое расхождение останавливает удаление для проверки владельцем.

## 2. Архитектура

Удаление строки `storage.objects` SQL-запросом оставляет сам файл в хранилище. Поэтому файлы удаляются только через Storage API, вне транзакции PostgreSQL, а процедура хранит своё состояние, и любой её шаг можно повторить.

```
человек: «Удалить аккаунт» → УДАЛИТЬ/DELETE → пароль (или вход ≤ 10 мин назад подтверждённым способом)
POST /api/account/delete  (сессия → auth.getUser; service key только на сервере)
  1. account_deletion_begin       ждёт загрузки «в полёте» (блокировка аккаунта), создаёт запрос;
                                  с этого момента — ни одной записи аккаунта (раздел 4)
  2. auth.admin.signOut(others)   другие устройства выходят
  3. account_deletion_manifest    серверный список файлов (папка И owner_id), сохраняется ДО удаления;
                                  «удалён» = Storage его больше не содержит (проверяет база)
  4. Storage API remove(...)      пакеты до 1000; 3–4 повторяются, пока список не пуст
  5. account_deletion_ready       снова под блокировкой: ни одного файла аккаунта; обезличенные счётчики — один раз
  6. auth.admin.deleteUser        каскад удаляет все строки, включая запрос
  → «удалено»; на устройстве: аккаунт отмечен удалённым, выход, копия стёрта
```

**Отказ на любом шаге:**
- ответ `503`, `retry: true` и код ошибки;
- запрос остаётся, запись закрыта, в `last_error` записывается код.

Пользователь видит плашку и «Продолжить удаление». «Удалено» показывается только после шага 6.

**Отмена — решение владельца.** Отменить можно только до начала: окно подтверждения, «Отмена». После шага 1 возможно только безопасное завершение: отмены нет.

**Флаг.** `NEXT_PUBLIC_AYRA_ACCOUNT_DELETION` по умолчанию выключен. Владелец включает его после применения 0023.

## 3. Гонка «загрузка ↔ удаление» (ревью, критический блокер)

**Что было.** В первой версии запрет загрузок давала проверка `cloud_sync_enabled()` в правиле вставки. Она видит только то, что зафиксировано к началу оператора `INSERT`. Порядок, при котором файл оставался:
1. загрузка прошла проверку, но ещё не зафиксирована;
2. удаление начинается;
3. список пуст;
4. `ready`;
5. Auth-пользователь удалён;
6. загрузка фиксируется — файл остаётся.

**Доказано контрольным тестом Q0** на PostgreSQL 16 с настоящими транзакциями: на 0023 без блокировки остаётся 1 файл.

**Исправление.**
- **Триггер на `storage.objects`** (`account_deletion_storage_guard`):
  - для аккаунта папки и для загрузившего берёт общую advisory-блокировку аккаунта и держит её до фиксации загрузки;
  - затем отдельным запросом читает, есть ли запрос на удаление, и при запросе отказывает.
- **`account_deletion_begin` и `account_deletion_ready`** берут ту же блокировку исключительно. Следствия:
  - запрос ждёт загрузку, которая уже прошла проверку; её файл попадает в список и удаляется;
  - любая загрузка после запроса видит его и получает отказ — до списка, между списком и `ready`, между `ready` и удалением пользователя;
  - после удаления пользователя загрузку останавливает правило 0005: флаг облака исчез.

**Детерминированные тесты** (PostgreSQL 16, `scripts/test-concurrency.sh`):

| Тест | Порядок | Результат |
|---|---|---|
| Q0 (контроль, без блокировки) | загрузка в полёте → запрос → пустой список → `ready` → удаление пользователя → загрузка фиксируется | **1 файл остался** — гонка была реальной |
| Q1 | то же на 0023 | запрос **не может начаться**, пока загрузка в полёте (таймаут блокировки 0,5 с, ни одного запроса не создано); после фиксации загрузки её файл в списке, удалён, ничего не осталось |
| Q2 | загрузка между пустым списком и `ready` | отказ `account_deletion_in_progress` |
| Q3 | загрузка между `ready` и удалением пользователя; после удаления (старый токен) | отказ; отказ |
| Q4 | строка Журнала в полёте | не переживает аккаунт: фиксируется до каскада или её отвергает внешний ключ |
| P3 | 6 загрузок одновременно с запросом | каждая либо до него (в списке, удалена), либо отказ; ничего не осталось |

Порядок в Q0–Q4 задаёт сам тест, а не время:
- удерживаемая транзакция фиксируется, только когда тест открывает её «шлюз» — строку в `q_gate`;
- в Q4 шлюз открывается, только когда удаление пользователя видно ждущим на блокировке строки.

В первой версии контроль Q0 держал загрузку фиксированные 3 секунды. Под нагрузкой (параллельно шёл полный e2e) процедура не уложилась в них и тест упал (записано в PR). Поэтому фиксированная пауза заменена шлюзом. Ограничение в 60 секунд внутри шлюза только завершает сломанный прогон и порядок не задаёт.

**Ограничение модели.** Заглушка Storage моделирует вставку строки объекта одной транзакцией. На hosted Supabase нужно проверить порядок Storage API (раздел 9):
- если файл кладётся в хранилище до вставки строки, отказ после запроса может оставить файл без строки, невидимый для API;
- создаёт ли hosted-проект триггер на `storage.objects` от имени владельца миграций.

## 4. Запрет записи во время удаления (матрица)

**Один механизм на все пути.** Триггер `BEFORE INSERT OR UPDATE` `account_deletion_guard` стоит на **каждой** таблице `public` с `user_id` (и `profiles.id`) — 30 таблиц на базе со всеми миграциями до 0023, а также `storage.objects`. Он срабатывает при записи через API под RLS, из функций `SECURITY DEFINER`, из маршрутов экономики с service role и от владельца. Тест D8 падает, если у какой-то таблицы с `user_id` его нет: новая таблица из будущей миграции не пройдёт незамеченной.

| Ресурс | Путь записи | Проверка | Тест |
|---|---|---|---|
| профиль (`profiles`) | API, RLS `UPDATE` | триггер | D7 |
| возрастная группа | `set_age_group` (`SECURITY DEFINER`) | триггер на `profiles` и `audit_log` | D7 |
| данные Рынка (`market_user_data`) | API, RLS | триггер | D7 |
| настройки и предпочтения уведомлений | API, RLS; `save_notification_settings` | триггер | D7 |
| Журнал (все `journal_*`) | API, RLS; `cloud_sync_enabled()` | триггер и правило | D2, D7 |
| строки скриншотов | API, RLS | триггер | D7 |
| файлы (`storage.objects`) | Storage API | триггер с блокировкой | D2, Q1–Q3, P3 |
| экономика (`game_*`) | маршруты с service role → функции владельца | триггер | D7 (переход состояния, снимок переноса) |
| флаг облака (`user_features`) | владелец | триггер | D7 |
| решения владельца по достижениям | инструмент владельца | триггер на `game_achievements`, `game_migration_audit` | D7 |
| другие устройства | их ещё не истёкшие токены | всё выше (запись — в базе) + выход на шаге 2 | e2e |
| обновление сессии | сервер Auth | разрешено: это не данные AYRA; другие сессии отозваны на шаге 2, текущая — с пользователем | — |
| копия на устройстве | `localStorage` и IndexedDB | список удалённых аккаунтов: запись в их пространство отбрасывается | unit, e2e |

**Удаления** (`DELETE`) человек может делать и во время процедуры: так он удаляет только свои данные. Каскад при удалении пользователя тоже не блокируется.

## 5. Подтверждение личности

- **Слово** `УДАЛИТЬ` или `DELETE` — в каждом POST, в том числе при продолжении.
- **Пароль** проверяет сервер Auth отдельным клиентом, сессия этой проверки закрывается.
- **Без пароля** — только если **подтверждённый** вход был не раньше 10 минут назад. Время берётся из `amr` проверенного токена, и только для способов, где человек сам подтвердил себя: `password`, `otp` (код из письма), `magiclink`, `email/signup` (регистрация).

| Случай | Результат | Тест |
|---|---|---|
| обновление токена (`TOKEN_REFRESHED`) | `amr` остаётся временем входа; свежий `iat` ничего не доказывает | unit |
| восстановление старой сессии | время входа старое → пароль | unit, e2e |
| регистрация (`email/signup`), вход по паролю, код из письма | засчитывается 10 минут | unit, e2e |
| OAuth, SSO, ссылка восстановления, анонимный вход, неизвестный способ | не засчитывается → только пароль | unit, e2e (OAuth) |
| нет `amr`, сломанный `amr`, плохой токен | только пароль | unit |
| повторный вызов, продолжение | каждый раз заново: слово и подтверждение | unit |

`has_password` из `user_metadata` сервер не учитывает: этот блок человек может менять сам.

## 6. Другие устройства и вкладки

**Удаляющее устройство:**
1. аккаунт отмечается удалённым (`ayra_deleted_accounts`) **до** выхода;
2. выход;
3. стирание копии: Журнал, игра, Фокус, скриншоты в IndexedDB.

Запись в пространство удалённого аккаунта отбрасывается, поэтому вторая вкладка, сохраняя игру при выходе, не возвращает копию (unit, e2e).

**Другое устройство:**
- при следующем открытии сервер Auth отвечает `user_not_found`;
- приложение отмечает аккаунт удалённым, выходит и показывает «Аккаунт… удалён. Его копия ещё хранится в этом браузере» с кнопками «Стереть копию» и «Не сейчас» (e2e).

Ограничение: если токен устройства уже истёк, сервер не отличит удаление от обычного выхода, и предложение не появится. Копия останется до очистки в настройках устройства.

**Две ошибки, найденные e2e-тестом другого устройства (исправлены, с тестами и мутациями):**
1. **Порядок сигналов.** supabase-js может показать выход раньше, чем приложение отметит аккаунт удалённым, и тогда предложение не появлялось. Теперь отметка сама сообщает о себе: событие в этой вкладке и `storage` для других. После «Стереть копию» все экземпляры предложения перечитывают список: страница могла смениться во время стирания (`components/settings/DeletedAccountNotice.test.tsx`, 4 теста).
2. **Гонка переключения пространства** (была на `main` до этого PR). Выход, пришедший, пока переключение в аккаунт ещё сохраняет прежнее пространство, обгонялся этим переключением:
   - аккаунт устанавливался последним и отмечался готовым;
   - приложение при этом было гостем;
   - `isSpaceReady` навсегда оставался `false` — вечный скелет страницы.

   Теперь переключения идут строго по очереди, и готовым отмечается только последнее (`lib/auth/space-switch-order.test.tsx`: без исправления — `guest|not-ready`, с ним — `guest|ready`). Вероятно, это и есть кандидат «вкладка зависла в загрузке» из Б10.

**Межвкладочный выход** — отдельная задача. Его сбой (вкладка зависла в загрузке) на безопасность удаления не влияет:
- запись в базу закрыта триггерами;
- запись в локальную копию удалённого аккаунта отбрасывается;
- удаление выполняет сервер, а не вкладка.

## 7. Приватность и хранение

**Остаются только** `account_deletion_stats` (день, метрика, число) — `requests`, `retries`, `accounts_deleted`, `files_deleted`. Без id, email, путей и текста: 3 колонки (D6).

**Не остаются:** email, профиль, файлы, Журнал, снимки, персональный журнал решений, сам запрос и его список (D6, e2e).

**Решение владельца по системным данным.** Резервные копии Supabase и журнал сервера Auth (`auth.audit_log_entries`, где есть email) не удаляются напрямую: соблюдаются политики Supabase. В окне удаления человеку объясняется: «Резервные копии базы, которые делает облачный сервис, хранятся ограниченный срок и затем удаляются автоматически; восстановить из них ваш аккаунт нельзя. Срок указан в Политике конфиденциальности.» Срок нужно указать в Политике по тарифу проекта: число я не выдумываю.

## 9. Что можно проверить только на отдельном hosted Supabase (до Production)

1. **Триггер на `storage.objects`** создаётся владельцем миграций, а функции 0023 читают `storage.objects` и `owner_id`.
2. **Порядок Storage API при загрузке** (вставка строки и запись файла):
   - что отказ вставки после запроса не оставляет файл без строки;
   - если оставляет — понадобится очистка через Storage API по префиксу папки, отдельной задачей.
3. **Ответ Auth на токен удалённого пользователя** — `user_not_found`, 403 — и порядок проверок (пользователь раньше сессии).
4. **Состав `amr`** на этом проекте для пароля, кода из письма и регистрации.
5. **Пробное удаление** тестового аккаунта с файлами; проверка, что в bucket'е ничего не осталось, а в `auth.users` его нет.
6. **Время выполнения** маршрута на Vercel для аккаунта с тысячами файлов. Если не уложится — «Продолжить».
7. **Срок резервных копий** по тарифу — для Политики конфиденциальности.

Затем владелец применяет 0023 в Production и включает `NEXT_PUBLIC_AYRA_ACCOUNT_DELETION=1`.

## 10. Откат

- Откат 0023 отказывает, пока есть незавершённое удаление: его список — единственная запись о том, что ещё нужно удалить.
- Иначе снимает все триггеры, удаляет таблицы и функции и возвращает `cloud_sync_enabled()` из 0004.
- Удалённые аккаунты не восстанавливаются: это необратимо по замыслу.
