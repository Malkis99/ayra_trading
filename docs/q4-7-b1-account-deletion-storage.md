# Q4.7-Б1 — Удаление аккаунта вместе с файлами Storage

Основа: `main` `2705a92` (merge #226). Миграция — `supabase/migrations/0023_account_deletion.sql` (+ откат). Нигде не применялась. Реальные аккаунты и файлы не трогались.

## 1. Перечень хранилищ (аудит)

**Storage — один bucket.**

| Bucket | Кто создаёт файлы | Путь | Владелец | Правила доступа | Связь с PostgreSQL | Замена и удаление |
|---|---|---|---|---|---|---|
| `journal-attachments` (приватный, 0005) | приложение, только с сессией самого человека (`lib/journal/cloud/attachment-files.ts`) | `<user id>/<attachment id>.<webp\|png\|jpg>` | `owner_id` — ставит **сервер Storage** по сессии загрузившего; папка — правило вставки требует `<auth.uid()>/…` | чтение и вставка только в своей папке (`cloud_sync_enabled()`, лимиты); удаление — только своей папки, через 30 дней после удаления строки или для файла без строки старше 24 ч; замены нет | `journal_attachments.file_path` (строка может отсутствовать: прерванная загрузка) | файлы не заменяются; новый вариант — новый файл |

**Чего нет:**
- аватаров и других загрузок: персонаж рисуется, а не загружается;
- общих (shared) файлов;
- загрузок от имени service role.

Кроме этого bucket'а, `storage.from(...)`, `.upload(` и `.remove(` в коде не используются.

**PostgreSQL.** Каждая таблица с данными человека ссылается на `auth.users` с `ON DELETE CASCADE`:
- профиль: `profiles`, `telegram_identities`, `link_tokens`, `audit_log` (0001);
- `user_features`, все `journal_*` (0004), `journal_attachments` (0005);
- `market_user_data` (0008);
- уведомления (0011);
- все `game_*` с `user_id` (0014–0022): журнал решений, снимки, сверки, достижения.

`game_shadow_diagnostics` колонки `user_id` не имеет: в ней обезличенные диагностические строки. Тест D6 обходит **все** таблицы `public`, где есть `user_id` (и `profiles.id`), и проверяет, что у удалённого аккаунта не осталось ни одной строки.

**Принадлежность файла** определяется не по пути из запроса клиента:
- объект — файл аккаунта, только если его папка равна id аккаунта **и** `owner_id` (ставит сервер Storage) равен тому же id;
- любое расхождение останавливает удаление для проверки владельцем. Это файл в папке, загруженный другим, или файл аккаунта в чужой папке. Такие файлы не удаляются и не пропускаются.

## 2. Архитектура

**Почему не одна транзакция.** Удаление строки `storage.objects` SQL-запросом оставляет сам файл в хранилище. Файлы удаляются только через Storage API, вне транзакции PostgreSQL. Поэтому процедура хранит своё состояние и любой шаг можно безопасно повторить.

```
человек: «Удалить аккаунт» → слово УДАЛИТЬ/DELETE → пароль (или вход ≤ 10 мин назад)
   │
POST /api/account/delete  (сессия → auth.getUser; service key только на сервере)
   1. account_deletion_begin        запрос; с этого момента cloud_sync_enabled() = FALSE: ни записи в Журнал, ни загрузки
   2. auth.admin.signOut(others)    другие устройства выходят (их запросы к экономике и Auth отклоняются)
   3. account_deletion_manifest     серверный список файлов (папка И owner_id), сохраняется ДО удаления;
                                    «удалён» = Storage его больше не содержит (проверяет база, не вызывающий)
   4. Storage API remove(...)       пакеты до 1000; повтор шагов 3–4, пока список не пуст
   5. account_deletion_ready        ни одного файла аккаунта в Storage; обезличенные счётчики — один раз
   6. auth.admin.deleteUser         каскад удаляет все строки, включая сам запрос
   → 200 «удалено»; на устройстве: выход и стирание копии аккаунта
```

**Состояния:** `requested` → `files_listed` → `files_deleted` → (строка уходит вместе с аккаунтом).

**Отказ на любом шаге:**
- ответ `503`, код ошибки и `retry: true`; аккаунт не удаляется;
- запрос остаётся, запись остаётся закрытой;
- код без текста записывается в `last_error`.

Пользователь видит «удаление начато, но не завершено» и кнопку «Продолжить удаление». «Удалено» показывается только после шага 6.

**Флаг.** `NEXT_PUBLIC_AYRA_ACCOUNT_DELETION` по умолчанию выключен: кнопки нет, маршрут отвечает 404, в настройках по-прежнему «Удаление аккаунта (скоро)». Владелец включает флаг после применения 0023. Экономических флагов это не касается.

## 3. Модель авторизации

**Кто удаляет.** Только владелец своей сессии: id берётся из проверенного токена (`auth.getUser(jwt)`), а не из запроса. Защита от IDOR: id в запросе не передаётся вообще.

**Подтверждение:**
1. Слово `УДАЛИТЬ` или `DELETE` — в каждом POST, в том числе при продолжении.
2. Повторное подтверждение личности — одно из двух:
   - пароль: его проверяет сервер Auth отдельным клиентом, сессия этой проверки сразу закрывается;
   - вход не раньше 10 минут назад, по claim `amr` проверенного токена. Обновление токена сохраняет время входа; `iat` для этого не годится. `has_password` из `user_metadata` сервер не учитывает: этот блок человек может менять сам.

**Service key** — только в `app/api/account/delete/route.ts`, на сервере. Шаги 0023 может вызвать только `service_role`. `anon` и `authenticated` не читают таблицы и не вызывают функции (D1, W).

**Несколько устройств:**
- на шаге 2 завершаются все другие сессии;
- их уже выданные токены до истечения ещё действуют в PostgREST, но запись в Журнал и загрузки закрыты на шаге 1, а экономика и Auth требуют живую сессию;
- текущая сессия завершается удалением пользователя.

**Повторные запросы:**
- запрос один на аккаунт: повтор начала только увеличивает счётчик попыток;
- перечень и проверка выполняются под блокировкой строки запроса;
- два одновременных запроса заканчиваются одним удалением: второй, обнаружив, что запрос исчез вместе с аккаунтом, отвечает «удалено».

## 4. Приватность и хранение

**Остаются только обезличенные счётчики** `account_deletion_stats` (день, метрика, число):
- `requests`, `retries`, `accounts_deleted`, `files_deleted`;
- ни id, ни email, ни путей, ни текста — в таблице 3 колонки (D6).

**Не остаются:**
- email и профиль;
- файлы;
- Журнал;
- снимки прогресса;
- персональный журнал решений (`game_migration_audit`);
- сам запрос с его списком файлов.

Это проверено тестами D6 и e2e.

**Вне этой процедуры (нужно решение владельца, раздел 10):**
- **Резервные копии Supabase** (ежедневные, PITR) хранят удалённое до конца своего срока. Немедленно удалить из них нельзя. Нужен текст политики о сроке.
- **`auth.audit_log_entries`** (журнал сервера Auth) содержит email в событиях. Из приложения его не удалить: таблицей владеет сервер Auth.
- **Копии на других устройствах** (localStorage и IndexedDB) стираются только на устройстве, где выполнено удаление. На остальных копия остаётся до очистки в их настройках: удалённо стереть её нельзя.

## 5. Порядок выполнения и частичные ошибки

| Отказ | Что видит человек | Состояние | Повтор |
|---|---|---|---|
| неверное слово, нет подтверждения личности, неверный пароль | ошибка в окне | ничего не начато | после исправления |
| не удалось завершить другие сеансы | «Повторите» | запрос есть, запись закрыта | безопасен |
| Storage удалил часть файлов или не ответил (обрыв сети) | «Не все файлы… Осталось файлов: N» | `files_listed`, `last_error = storage_error` | удаляет оставшиеся |
| Storage не удаляет ничего (раунд без продвижения) | то же | то же | бесконечного цикла нет: остановка |
| в папке чужой файл | «Удаление остановлено для проверки» (409) | `files_listed` или `requested`, ничего не удалено | после проверки владельцем |
| файлы удалены, Auth-пользователь не удалился | «Файлы удалены, но аккаунт… Повторите» | `files_deleted` | удаляет пользователя |
| выход или закрытие вкладки посреди удаления | при следующем входе — «Продолжить удаление» | как было | безопасен |
| два запроса одновременно | оба отвечают «удалено» | — | — |

**Метаданные для поиска файлов не теряются.** Список файлов сохраняется в `account_deletion_objects` до удаления. Сам Auth-пользователь удаляется последним, после проверки базы, что файлов не осталось.

## 7. Ограничения hosted Supabase

- **Файлы удаляются только через Storage API.** Строки `storage.objects` нельзя удалять SQL: файл останется.
- **`owner_id`** ставит сервер Storage. Заглушка в тестах повторяет его поле, а на настоящем Supabase колонку нужно проверить перед применением (раздел 9).
- **`auth.admin.deleteUser` и `auth.admin.signOut`** требуют service key: они вызываются только из маршрута.
- **Лимит запросов** (10 в минуту на аккаунт) хранится в памяти экземпляра, как у остальных маршрутов: на Vercel он не общий.
- **Время выполнения.** Один запрос делает до 25 раундов по 1000 файлов, то есть до 25 000 файлов. Предел Журнала — 400 МБ на аккаунт: при скриншотах по 100–300 КБ это несколько тысяч файлов, несколько раундов. Если запрос не уложится во время функции, «Продолжить» удалит остальное.

## 8. Откат

- **Откат 0023** отказывает, пока есть незавершённое удаление: его список файлов — единственная запись о том, что ещё нужно удалить.
- Иначе он удаляет таблицы и функции и возвращает `cloud_sync_enabled()` из 0004.
- Удалённые аккаунты не восстанавливаются. Это необратимо по замыслу.

## 9. Перед Production (владелец)

1. На отдельной базе Supabase (не Production) применить 0023 и проверить:
   - что у `storage.objects` есть `owner_id`;
   - что владелец миграции может читать `storage.objects`.
2. Пробное удаление тестового аккаунта с файлами на этой базе; проверить, что в bucket'е ничего не осталось.
3. Применить 0023 в Production (владелец), затем включить `NEXT_PUBLIC_AYRA_ACCOUNT_DELETION=1`.
4. Текст политики конфиденциальности: срок резервных копий, журнал сервера Auth, копии на других устройствах.

## 10. Риски и вопросы

1. **Резервные копии и журнал сервера Auth** хранят данные до своего срока. Нужно решение: текст политики, а также удалять ли `auth.audit_log_entries` отдельной процедурой с правами владельца проекта.
2. **Отмена.** После шага 1 отмены нет: аккаунт закрыт для записи, пока удаление не завершится. Нужна ли отмена до удаления первого файла?
3. **Подтверждение личности.** Сейчас это пароль или вход за последние 10 минут. Нужна ли ещё проверка по коду из письма (`reauthenticate`)?
4. **Копии на других устройствах** остаются до очистки там. Показывать на них при следующем открытии «аккаунт удалён — стереть копию»?
5. **Найдено по ходу, вне Б1.** Тест Б10 «две вкладки и другое устройство» один раз упал в общем локальном прогоне: вторая вкладка застряла в загрузке после выхода в другой вкладке. Отдельно — 10 из 10. Код Б1 эту страницу не затрагивает. Это кандидат для отдельного аудита межвкладочного выхода (вы его уже отметили). Логи сохранены.
