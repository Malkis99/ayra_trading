# Q4.2 — Серверная проверка миссий в теневом режиме

**Статус.** Теневой режим: сервер повторяет проверку миссий QH-6.6 по облачному Журналу и сравнивает свой ответ с решением приложения. **Ничего не начисляет и ничего не меняет.**
- XP, Coins, уровень, достижения, хроника и журнал миссий пользователя остаются такими, какими их оставила проверка приложения — при любом ответе сервера и при его отсутствии.
- `game_award_kinds.mission` и `game_sync` не включаются. `cloud_active` не активируется, импорт прогресса не запускается.
- Миграций нет. Сервисный ключ не используется.
- Переключатель `NEXT_PUBLIC_AYRA_MISSION_SHADOW` в production **выключен** (маршрут отвечает 404, приложение ничего не отправляет). Включён только в e2e с fake Supabase.

## 1. Как это работает

```
Приложение: «Проверить» → verifyMission (как раньше: решение, оплата, сохранение под общей блокировкой вкладок)
  └─ после сохранения, не дожидаясь ответа (только если переключатель включён):
     POST /api/game/missions/shadow { missions: [{ id, day, done, source?, reason? }] }
Сервер (app/api/game/missions/shadow → lib/game-server/mission-shadow-handler.ts):
  1. Переключатель → иначе 404. Только POST, только JSON, только со своего сайта (Origin) → иначе 405 / 415 / 403.
  2. Пользователь — только из проверенной сессии Supabase (cookies → auth.getUser на сервере) → иначе 401.
     user_id в теле запроса не принимается: лишнее поле = 400.
  3. Лимит частоты на аккаунт → 429 + Retry-After. Тело не больше 8 КБ → 413. Строгая схема → 400.
  4. Облачный Журнал выключен у аккаунта → 409 cloud_journal_off (Журнал не читается).
  5. Чтение СЕССИЕЙ ПОЛЬЗОВАТЕЛЯ (RLS 0004 + фильтр user_id в каждом запросе): часовой пояс, все заметки
     и сделки (с удалёнными — для проверки копий), планы на сегодня и завтра. Больше 5000 строк → 422.
  6. Игровой день сервера = серверное время в поясе profiles.timezone (как game_day_for в 0014).
  7. Те же правила, что в приложении (lib/missions.ts candidateSources / explainMission), на облачных строках
     и на дне СЕРВЕРА, плюс серверные проверки (раздел 2).
  8. Повторное чтение доказательств: версия или отпечаток изменились, запись удалена → 409 evidence_changed.
  9. Ответ: сравнение по каждой миссии, authorizedForPayout: false, payout: "not_authorized".
Приложение хранит последние 10 ответов только в памяти вкладки (window.__ayraMissionShadow) — для диагностики.
```

**Почему без сервисного ключа.** Теневой проверке нужно только читать свои строки. Сессия пользователя и RLS дают изоляцию аккаунтов на уровне базы. Фильтр `user_id` в коде — второй, независимый барьер. Сервисный ключ понадобится только для начисления в Q4.3: функция `game_apply_reward` доступна лишь `service_role`.

## 2. Что проверяет сервер

| Требование | Как проверяется | Где |
|---|---|---|
| Содержание и обязательные поля | Правила `lib/missions.ts`: длина собственного текста (без заготовки шаблона), направление и уровень, лимиты и пункт чек-листа, полный разбор сделки, полный бэктест | `candidateSources` |
| Соответствие конкретной миссии | Правила миссии + форма источника (`sourceFits`): урок не подтверждает наблюдение, сделка не подтверждает урок | `sourceFits`, флаги `sourceNotConfirmed`, `sourceUnknownForm` |
| Дата игрового дня и пояс | День сервера по `profiles.timezone`; неизвестный пояс → UTC и `timezoneFallback: true`; день приложения другой → флаг `dayDiffers` | `serverGameDay` |
| Импортированные записи | `importBatchId` → не засчитывается (правило приложения) | причина `noteImported` |
| Недопустимые повторы | Копия текста более ранней заметки (любой id, в том числе удалённой); повтор результата бэктеста; одна запись для двух миссий в запросе → `duplicateSource` | `isNewText`, `isNewResult` |
| Удалённые записи | Серверный tombstone (`deleted_at`) важнее записи, которая называет себя живой | `toMissionData` |
| Время записи | **Новое, только сервер:** отметка дня записи (создание заметки, разбор сделки, сохранение / подтверждение / итоги плана) не может быть позже, чем сервер получил эту версию (`updated_at` + 5 мин). Запись «из будущего» → `stampAfterServerWrite` | `dayStamp` |
| Версия и отпечаток | `client_updated_at` (её сравнивает 0014) и sha256 содержимого; повторное чтение перед ответом | `evidenceStable` |
| Чужие записи | Не видны (RLS + фильтр). Ссылка на чужую запись → «не подтверждено» | тесты изоляции |
| Назначение миссии пользователю | **Не проверяется:** у сервера нет состояния игрового дня | `unverified` |

**Чего сервер ещё не может подтвердить** (поле `unverified` в каждом ответе):
- `daySet` — что миссия была в наборе дня и в выбранном режиме;
- `accepted` — что её приняли;
- `dayClaims` — какие записи уже заняты другими миссиями сегодня;
- `paidToday` — что она ещё не оплачена и не набран лимит трёх;
- `dayStarted` — что день не «закрыт» (правило приложения: день не возвращается назад).

## 3. Сравнение

| `comparison` | Значение |
|---|---|
| `agree_done` | Обе стороны засчитали, той же записью |
| `agree_not_done` | Обе не засчитали |
| `client_only` | Приложение засчитало, сервер по облачным данным — нет |
| `server_only` | Сервер засчитал бы, приложение — нет (например, миссию не приняли) |
| `source_differs` | Обе засчитали, но разными записями |

При любом расхождении сервер **ничего не меняет**. Ответ — только диагностика. Его нельзя использовать для оплаты, пока не выполнены условия раздела 6.

## 4. Применимость правил приложения к облачному формату

- **Формат совпадает.** Облачная строка `data` — это та же запись Журнала без полей наград (`JOURNAL_CLOUD_FORBIDDEN_KEYS`). Правила работают на облачных строках без изменений. У строк новой версии схемы (`schemaVersion` больше известной) правила не применяются: они пропускаются и считаются в `skipped`, как в приложении (`decodeRow`).
- **Удаление.** В приложении удаление — это `deletedAt` в записи. В облаке есть ещё серверный `deleted_at`. Сервер доверяет своему tombstone.
- **Копии требуют всех заметок.** Правило «текст новый» сравнивает со всеми прежними заметками, включая удалённые. Сервер читает их все: это ограничивает размер (5000 строк, PLACEHOLDER).
- **Время пишет клиент.** `createdAt`, `reviewedAt`, `firstSavedAt`, `prepConfirmedAt`, `review.completedAt` задаёт устройство. Сервер может проверить только верхнюю границу (не позже собственной записи сервера). Запись, подготовленную заранее и отправленную сегодня с сегодняшним временем, он отличить не может. Нужна отметка первого появления строки на сервере (условие Q4.3).
- **Игровой день.** В приложении день не возвращается назад (`lastQuestDate`). Сервер считает чистый день по поясу, поэтому около полуночи или после смены пояса возможен `dayDiffers`. Правило должно жить на сервере (Q4.3).
- **Отпечаток.** Теневой sha256 сравнивает только свои два чтения. Отпечаток 0014 — `md5(data::text)` от самого Postgres. Оплачивающий маршрут должен брать версию и отпечаток у Postgres.

## 5. Защита

- **Изоляция аккаунтов:** только проверенная сессия; RLS и фильтр `user_id`; ответ содержит только id своих записей и коды.
- **Диагностика без утечек:** текст записей, сообщения базы, адреса и id пользователя в ответ не попадают (тесты). Ошибки — только коды. Сервер ничего не пишет в лог.
- **Частота:** 20 проверок в минуту на аккаунт (PLACEHOLDER). Лимит хранится в памяти экземпляра сервера: на Vercel он действует на экземпляр, а не глобально. Для теневого чтения этого достаточно; для оплаты — нет (условие Q4.3).
- **Кэш:** `Cache-Control: no-store`.
- **Подделка запроса другим сайтом:** только свой Origin.
- **Повторы и две вкладки:** проверка без состояния: одинаковые данные дают одинаковый ответ, ничего не записывается.

## 6. Условия полноценной серверной авторизации начислений (Q4.3)

1. **Серверное состояние игрового дня** (таблица дней): набор дня и режим, принятые миссии, занятые записи, оплаченное, правило «день не возвращается назад». Пишет только сервер.
2. **Принятие миссии через сервер**, чтобы `accepted` было подтверждено.
3. **Отметка первого появления строки Журнала на сервере** (новый столбец, миграция): «сделано сегодня» по серверному времени, а не по времени устройства.
4. **Версия и отпечаток от Postgres** (`client_updated_at`, `md5(data::text)`) передаются в `game_apply_reward`. Функция перепроверяет их под `FOR SHARE` (уже есть в 0014).
5. **Общий лимит частоты** для оплачивающего маршрута (в Postgres), а не в памяти экземпляра.
6. **Переход аккаунта** `local → migration_pending → cloud_active`; приложение перестаёт начислять локально у `cloud_active`.
7. **Статистика расхождений:** сейчас ответы видны только во вкладке. Для решения «можно ли доверять серверу» нужен журнал расхождений без содержимого записей (таблица, миграция) — по вашему решению.
8. **Включение `mission`** в `game_award_kinds` — только вашим решением, после 1–7 и тестов.
9. **Смена часового пояса:** правило, какой день действует после смены пояса (сейчас приложение и сервер могут расходиться).
