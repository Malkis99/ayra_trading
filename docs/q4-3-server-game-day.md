# Q4.3 — Серверный игровой день

**Статус.** Основа серверного игрового дня QH-6 — миграция `supabase/migrations/0015_game_days.sql` (откат: `0015_game_days.down.sql`). Проверяется в CI: PGlite и настоящий PostgreSQL 16. **Не применяется к Supabase.**

**Ничего не включается:**
- `game_sync` выключен, ни один аккаунт не становится `cloud_active`;
- вид начисления `mission` выключен, реальных начислений нет;
- теневой режим в production выключен, отправки диагностики нет;
- приложение работает как раньше: серверный день пока никто не вызывает (маршруты — Q4.4).

0015 требует 0014, которая тоже не применена в production. Применять их можно только вместе, по порядку, вашим решением.

## 1. Модель

| Объект | Что хранит | Гарантии |
|---|---|---|
| `game_accounts.current_day` | Последний открытый игровой день аккаунта (курсор) | День не возвращается назад: часовой пояс не открывает закрытый день повторно |
| `game_days` | Один день аккаунта: статус, пояс при открытии, режим и режим до отдыха, выбор «Разбор сделки / Наблюдение», три миссии (`core`), перенесённые миссии (`carried`), принятые (время), отложенные, дополнительные задания приложения (`bonus`), замены, смены режима, закрытие и снимок результата | PK `(user_id, game_day)`; закрытый день заморожен триггером (даже для владельца); идентичность дня (дата, пояс, время открытия, выбор, версия правил) не меняется |
| `game_mode_missions` | Три миссии каждого режима | Та же таблица, что `missionsForMode` в приложении (тест сравнения) |
| `game_limits.replacements_per_day` | Лимит замен — 2, как `QUEST_REPLACEMENTS_PER_DAY` | Настройка владельца |
| `game_shadow_diagnostics` | Расхождения теневой проверки: категория, миссия, день, версия правил, время | Без id пользователя, записей и текста; только добавление (раздел 6) |

**Права — модель Q4.1 без изменений:**
- всё принадлежит `game_economy_owner`, писать в таблицы напрямую не может никто: ни клиент, ни сервисный ключ, ни ручной SQL администратора (триггер-страж);
- API для серверного маршрута (`service_role`): `game_day_open`, `game_day_set_mode`, `game_day_accept`, `game_day_pass`, `game_day_replace`, `game_mission_status`, `game_apply_reward`;
- клиент только читает свой день через `game_my_day()` (RLS).

**Время — только серверное.** API берёт `now()` базы. Варианты с переданным временем (`*_at`) нужны только тестам и владельцу: ни одна роль API не может их вызвать (тест P1).

**Конфликты устройств.** Каждое изменение дня и каждое начисление берёт одну и ту же блокировку аккаунта (строка `game_profile`). Два устройства обслуживаются строго по очереди, и второе видит уже изменённый день (тест PG-H5).

## 2. Правила дня (как в приложении)

- **Открытие.** День открывает сервер: первый запрос дня закрывает все прежние открытые дни и создаёт новый.
  - Режим при открытии — «торговый» или «учебный»: торговые дни человека знает приложение.
  - Выбор первой учебной миссии делается **один раз** по облачному Журналу: была ли живая сделка до этого дня.
  - Второе устройство получает тот же день, даже если прислало другой режим или другие задания.
- **Смена режима** — то же правило, что `composeSwitchedSet` (каталог 3):
  - оплаченная миссия сохраняет свой слот;
  - свободные слоты берут миссии нового режима;
  - отложенная миссия не предлагается снова;
  - отдых не просит ничего, а возврат из отдыха к прежнему режиму возвращает тот же набор.
  - Совпадение с приложением проверено на **более чем 1000 комбинациях** (`lib/game-day-parity.test.ts`).
- **Принятие** ничего не даёт; повторное принятие сохраняет первое время. Принять можно только миссию из набора дня, не в отдыхе и не оплаченную.
- **Замены** — только дополнительных заданий:
  - миссию нельзя заменить, и миссия не может прийти заменой;
  - лимит 2 в день;
  - нельзя вернуть заменённое задание или показать задание дважды;
  - замена разрешена и после первой награды дня.
- **Закрытие.** Когда открывается следующий день, прежний закрывается навсегда. Снимок фиксирует режим, набор, принятые, отложенные, замены, смены режима, оплаченные миссии, XP и Coins дня.

## 3. Часовой пояс и полночь

**Правило:** игровой день = дата серверного времени в поясе профиля, **но не раньше курсора** (`GREATEST(дата, current_day)`). Неизвестный пояс считается как UTC.

| Ситуация | Что происходит | Тест |
|---|---|---|
| Пояс «вперёд» (UTC → UTC+14 в 13:00 UTC) | Открывается следующий день; прежний закрывается со своими оплатами | Z1, Z3 |
| Обратно в UTC | Закрытый день **не** открывается снова; остаётся следующий | Z2 |
| Тот же день по UTC наступает по-настоящему | Это тот же игровой день: миссия, оплаченная раньше, не оплачивается повторно | Z5 |
| Следующий день | Наступает в полночь по UTC: за реальные сутки — один игровой день, прыжок не дал лишнего дня | Z6, Z7 |
| Пояс «назад» (Тбилиси → Лос-Анджелес) | Держится текущий день, ранний не открывается; следующий — по полуночи нового пояса | Z8–Z11 |
| Полночь | После полуночи вчерашнее не принимается и не оплачивается (`game_day_not_open`); новый день — новое принятие; снимок вчерашнего хранит оплату | N1–N4 |

**Остаточный эффект.** Прыжок поясом вперёд начинает следующий день раньше: до 26 часов, один раз, без повтора. Миссии не дублируются и лишних дней не появляется. Если нужно жёстче (новый пояс действует только со следующей естественной полуночи старого), это отдельное решение (раздел 8, вопрос 2).

## 4. Подтверждение миссии сервером

`game_apply_reward('mission')` после 0015 требует всё, что требовалось в 0014, и дополнительно три новые проверки:

| Проверка | Ошибка | Тест |
|---|---|---|
| День открыт на сервере (это сегодняшний день сервера) | `game_day_not_open` | N1 |
| Миссия в наборе дня для его режима, не отдых | `game_mission_not_assigned` | M4, S4, PG-B, PG-C |
| Миссия принята сегодня | `game_mission_not_accepted` | M3, N4 |
| Уже оплачена | повтор сохранённого результата | M6, Z5, PG-A |
| Запись использована другой миссией | `game_source_used` | PG-B |
| Лимит дня (3) | `game_day_cap`; кроме того, смена режима после трёх оплат не открывает четвёртой миссии | S3–S5, PG-C2 |

`game_mission_status` отвечает на те же вопросы без оплаты: назначена, принята, подходит режиму, оплачена, день заполнен.

**Реальных выплат нет:** вид `mission` выключен; аккаунтов `cloud_active` нет; маршрута, который вызывал бы это начисление, нет.

## 5. Согласованность с Q4.1 и Q4.2

- **0014** не переписана: 0015 заменяет только начисление (`game_apply_reward` → `game_apply_reward_at`) и добавляет проверки дня. Откат 0015 возвращает функцию 0014 байт в байт, и тесты 0014 проходят после отката (блок O).
- Правила не дублируются без нужды:
  - таблица миссий режимов и правило смены режима проверяются против кода приложения;
  - выбор «Разбор сделки / Наблюдение» считается по тем же данным (`createdAt`, иначе `openedAt`, в поясе аккаунта);
  - дополнительные задания и их подбор остаются в приложении: пул зависит от ответов онбординга, которых нет на сервере. Сервер их только записывает и ограничивает замены. За них он не платит: `self_report` остаётся закрытым.
- **Теневая проверка Q4.2** теперь читает серверный день (`game_my_day()`):
  - если у аккаунта открыт серверный день, ответ говорит, назначена ли миссия, принята ли, оплачена ли, заполнен ли день и занята ли запись, а список неподтверждённого пуст;
  - курсор дня учитывается: после смены пояса «назад» сервер остаётся на позднем дне;
  - выплата по-прежнему не разрешена (`authorizedForPayout: false`);
  - без серверного дня (или без 0015) всё как в Q4.2.

## 6. Диагностика расхождений

- **Модель:** `lib/shadow-diagnostics.ts` и таблица `game_shadow_diagnostics`.
- **Строка:** категория (одна из 16: виды сравнения, флаги проверки, проблемы дня), код миссии, игровой день, версия правил, время проверки.
- **Нет** id пользователя, id записей, ключей источников, текста Журнала и секретов (тесты G2, G3 и unit).
- Запись — `game_record_shadow` (только сервер; до 10 строк за вызов, лишние поля отклоняются, только добавление).
- **Отправка не включена:** нигде в приложении и на сервере эти строки не отправляются.

## 8. Ограничения и решения перед Q4.4

1. **Маршруты серверного дня.** Приложение пока не вызывает сервер при открытии дня, смене режима, принятии и замене. Нужны маршруты (сессия → `service_role` → функции 0015) и вызовы из приложения. Без них серверный день существует только в базе.
2. **Правило смены пояса.** Сейчас — «день не возвращается назад». Подтвердите его или выберите более строгое: новый пояс действует со следующей полуночи старого.
3. **Дополнительные задания (self-report).** Сервер не может подобрать их сам: нужны ответы онбординга на сервере. Пока они записываются со слов приложения и не оплачиваются сервером. Решение о серверной оплате самоотчётов — отдельно.
4. **Источник истины при переходе.** Пока аккаунт `local`, день ведёт приложение. Для `cloud_active` — сервер, и приложение должно брать набор дня с сервера, а не строить свой. Это часть переноса (Q4.5) и выключения локальных начислений.
5. **Серверная отметка первого появления записи Журнала** (из Q4.2) по-прежнему нужна, чтобы «сделано сегодня» определялось временем сервера.
6. **Отправка диагностики:** включать ли и когда (таблица готова, отправки нет).
7. **Порядок применения:** 0014 и 0015 вместе, вашим решением, сначала на тестовой копии Supabase.
