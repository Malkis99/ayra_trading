# Синхронизация игрового прогресса между устройствами — техническая спецификация (черновик)

**Статус: документ, не реализация.** Ничего из описанного не сделано. Реализация потребует миграций Supabase — только после отдельного решения владельца.

Основание:
- решение владельца после NEW USER ACCEPTANCE TEST (2026-11-15), п. 6–7;
- правила `AGENTS.md`: экономика решается на сервере, журнал наград только дописывается, награды идемпотентны, есть дневные лимиты, клиенту не доверяем.

## 1. Что есть сейчас и почему это проблема
- **Игровой прогресс** (XP, уровень, Coins, серия, щиты, история заданий, снимки дней, журнал оплаченных источников `missionLedger`) хранится **только на устройстве**: `localStorage`, ключ `ayra:<userId>:ayra_demo_v1`. Экран «Задания» прямо говорит: «Прогресс хранится на этом устройстве».
- **Журнал** (сделки, планы, заметки, бэктесты) **синхронизируется** через облако.
- **Следствие (известное ограничение до Q4).** Каждое устройство оплачивает миссии по записям Журнала текущего игрового дня, в том числе по записям, пришедшим из облака. Если в тот же день открыть второе устройство, оно оплатит те же миссии ещё раз — в своём, отдельном прогрессе. Внутри одного устройства повторов нет: журнал источников, лимит три в день, общая блокировка вкладок. Привязывать награду к устройству **не будем** (решение владельца): человек должен свободно работать на компьютере и телефоне.

## 2. Цель
Один прогресс на аккаунт, на всех устройствах:
1. Единый баланс XP и Coins, уровень, серия, щиты.
2. Единая история выполненных заданий и снимки дней.
3. Единый журнал оплаченных источников: миссия и источник оплачиваются **один раз на аккаунт** за игровой день, а не один раз на устройство.
4. Идемпотентность между устройствами, вкладками, повторами запросов и работой без сети.
5. Никаких начислений задним числом сверх утверждённых правил (QH-6.5, раздел 6.5).

## 3. Принципы
- **Сервер — источник истины.** Клиент присылает *намерение* («проверь миссию X за день D»), а не сумму награды.
- **Журнал наград только дописывается** (append-only). Баланс — это сумма журнала, кэшированная в проекции; в проекции ничего не правится вручную.
- **Идемпотентный ключ каждого начисления:**
  - миссия: `mission:<userId>:<gameDay>:<missionId>`;
  - источник: `source:<userId>:<gameDay>:<sourceKey>` — одна запись Журнала оплачивает одну миссию;
  - самоотчёт, ежедневная награда, разовые награды — свои ключи.

  Повтор с тем же ключом возвращает уже записанный результат и ничего не начисляет.
- **Дневные лимиты на сервере:** не больше трёх основных миссий, 90 XP самоотчётов, лимит Coins — проверяются в той же транзакции, что и вставка.
- **Время** — серверное. Игровой день считается на сервере по поясу аккаунта.
- **Проверка миссии на сервере** по правилам QH-6.2, по записям Журнала, уже лежащим в облаке. Клиентский статус «выполнено» — только отображение.

## 4. Модель данных (предложение)
| Таблица | Назначение | Ключевые поля |
|---|---|---|
| `game_ledger` | Журнал начислений (только вставка) | `id`, `user_id`, `kind` (mission / self_report / daily_reward / first_action / journal_xp…), `game_day`, `quest_id`, `source_key`, `xp`, `coins`, `idempotency_key` UNIQUE, `created_at` (сервер), `device_id` (только для диагностики) |
| `game_profile` | Проекция: баланс и счётчики | `user_id`, `xp_total`, `level`, `coins`, `streak`, `best_streak`, `shields`, `updated_at` |
| `game_days` | Набор и режим дня, снимок закрытого дня | `user_id`, `game_day`, `mode`, `catalog_version`, `core`, `bonus`, `study_first`, `snapshot` (jsonb, пишется один раз) |

Правила доступа (RLS): пользователь читает только свои строки. Вставка в `game_ledger` — только через серверную функцию (RPC) с проверками, напрямую с клиента нельзя.

## 5. Потоки
1. **Миссия.** Запись сохранена в Журнале → синхронизирована в облако → клиент вызывает `claim_missions(game_day)` → сервер:
   - читает набор дня и записи Журнала;
   - применяет правила QH-6.2 и журнал источников;
   - вставляет строки `game_ledger` с идемпотентными ключами в одной транзакции с проверкой лимита три в день;
   - возвращает начисленное.

   Второе устройство получает тот же ответ: повторной оплаты нет.
2. **Самоотчёт и ежедневная награда** — тот же путь через RPC с ключами дня.
3. **Без сети.** Клиент копит намерения с детерминированными ключами и отправляет после восстановления связи. Сервер применяет правила того дня, к которому относится запись, только в пределах окна из раздела 6.5 спецификации QH-6. Длину окна решает владелец.
4. **Смена суток и снимок дня** — на сервере, один раз; клиент только показывает.

## 6. Перенос существующего прогресса (нужно решение владельца)
У одного аккаунта может быть прогресс на нескольких устройствах. Варианты:
- **A.** Основой становится устройство с наибольшим XP. Остальные показываются только для чтения как «история устройства» и в баланс не суммируются.
- **B.** Объединить истории по ключу «день + задание»: одинаковое задание одного дня считается один раз, баланс пересчитывается из объединённого журнала.
- **C.** Перенести только баланс одного устройства, историю — без пересчёта.

Рекомендация — **B** для истории и **A** как запасной вариант при конфликте, но решение за владельцем. Во всех вариантах уже заработанное не отнимается молча: любое расхождение показывается человеку.

## 7. Этапы (предложение)
1. Миссии и таблицы `game_ledger`, `game_profile` в режиме «только запись»: сервер ведёт журнал параллельно с клиентом и сверяет суммы.
2. Сервер начисляет миссии, клиент только показывает.
3. Самоотчёты, ежедневная награда, разовые награды, награды Журнала.
4. Перенос прогресса (раздел 6) и отключение локального начисления.
5. Снимки дней и история с сервера.

## 8. Открытые вопросы владельцу
- Вариант переноса прогресса (A / B / C).
- Длина окна «ожидает подтверждения» после полуночи (QH-6, раздел 6.5).
- Нужен ли гостям (без входа) локальный прогресс с переносом при регистрации — сейчас перенос есть только у Журнала.
