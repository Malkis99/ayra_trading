# PPI / Core PPI и расписание BLS

База main после #151: `dc9cadbcde57fbdbca78b1f59b422d944df58f9b`. Ветка `feat/us-ppi-bls-schedule`.
Согласованный объём: четыре PPI, одно ежедневное чтение официального PPI-расписания, прежний BLS budget
для фактов, план автоматизации остальных источников. Без миграций, новых зависимостей и production-изменений.

## Реальный статус доступа — 06.11.2026

Прямой Node/server GET с существующим честным AYRA User-Agent:

| Адрес | Результат |
|---|---|
| `https://www.bls.gov/schedule/news_release/ppi.htm` | HTTP403, HTML Access Denied, 1323 символа |
| `https://www.bls.gov/news.release/archives/ppi_10152026.htm` | HTTP403, тот же отказ |
| `https://www.bls.gov/schedule/news_release/bls.ics` | HTTP403, тот же отказ |

Ответ BLS ссылается на политику автоматического доступа и предлагает обратиться через
`https://data.bls.gov/forms/opb.htm`. Не установлено, связано ли это с IP или иным правилом защиты.
Публичные данные BLS не требуют платной подписки; API Key не является подтверждённым решением HTML403.
Регистрацию/отдельное разрешение для снятия конкретного отказа может уточнить BLS. Контакт с ведомством не отправлялся.

Через исследовательский web-доступ прочитаны официальные публикации/таблицы BLS. Fixtures — **нормализованные
представления этих опубликованных таблиц**, а не притворный успешный raw server response. Это явно указано
в каждом fixture. Они проверяют поддерживаемую семантическую HTML-разметку и реальные числа/даты.
Полное соответствие реальному raw HTML и успешная автоматическая загрузка из Vercel **не подтверждены**.
Деплой Preview и зелёные тесты сами по себе не являются такой проверкой.

Read-only внешнего fetch из Vercel в существующем приложении нет. Production collector ради проверки не
запускался, диагностические маршруты и доступ к cron-секретам не добавлялись.

### Законные бесплатные альтернативы

1. [Официальный OMB/OIRA календарь 2027](https://www.whitehouse.gov/wp-content/uploads/2026/10/FY2027-PFEI.pdf):
   прямой серверный GET HTTP200, application/pdf, 218990 байт, `%PDF-1.6`. Страница 4 содержит реальные даты
   PPI: 14/12/12/14/13/11/15/10/10/15/12/15 по месяцам января–декабря2027, данные за предыдущий месяц.
   Бесплатный официальный годовой baseline, но не гарантия оперативных переносов BLS. Для постоянной
   автоматизации нужно обнаруживать новые официально опубликованные годовые документы и их исправления,
   не предполагать даты следующего года. Нельзя заменять более свежую версию BLS старым годовым PDF.
2. [Официальная копия публикации BLS на DOL](https://www.dol.gov/newsroom/economicdata/ppi_10152026.pdf):
   GET HTTP200, application/pdf, 1641399 байт, `%PDF-1.7`; существующий PDF reader извлекает часть текста,
   но нужные заголовки/таблицы в его выводе не подтверждены. Для надёжного PDF-адаптера нужна отдельная проверка декодирования.
   Это возможный транспорт датированного BLS-релиза, не источник собственного расписания всех будущих месяцев.

Обе альтернативы проверены read-only и **не подключены как автоматический fallback**: второй запрос после403
нарушил бы согласованный budget, а смена транспорта требует отдельных тестов семантики/версий.
Предлагаемый следующий шаг доступа — проверить разрешённый fetch из Vercel или согласовать замену одного
существующего запроса официальным PDF-транспортом, без обхода блокировок/прокси.

## Четыре показателя и происхождение

Источник факта — [датированный BLS-релиз 15.10.2026](https://www.bls.gov/news.release/archives/ppi_10152026.htm),
период September2026. Table1, группировка FD; m/m — SA, y/y — NSA. Проценты читаются явно, не вычисляются
из округлённых или пересмотренных текущих индексов API. Важность2, США, официальное время America/New_York.

| Code / RU / EN | Строка и код BLS | Факт в примере | Previous |
|---|---|---|---|
| `us_ppi` / PPI, м/м / PPI, m/m | Final demand, FD4 | +1.3% | +0.5%, соседний столбец Table1 |
| `us_ppi_yoy` / PPI, г/г / PPI, y/y | Final demand, FD4 | 6.3% | 5.6%, явная история annual в TableA |
| `us_core_ppi` / Базовый PPI, м/м / Core PPI, m/m | Final demand less foods and energy, FD49104 | +0.7% | +0.2%, Table1 |
| `us_core_ppi_yoy` / Базовый PPI, г/г / Core PPI, y/y | Та же FD49104 | 5.0% | Только подтверждённый initial предыдущего месяца из своей БД; иначе NULL |

Для последней строки первая публикация августа2026 даёт4.6%, но это **не** утверждение о пересмотренном
августовском значении в сентябрьском release. Такой previous хранит отдельный `previous_source` с периодом,
URL, временем и `basis=initial-prior-release`. Для явно опубликованного previous — `basis=reported-in-release`.
Нет дополнительного запроса ради previous. Отсутствующие данные остаются NULL, в UI — существующее тире.

Важное реальное различие vintage: август первоначально дал headline m/m +0.4%, а сентябрьский release
указывает пересмотренный previous +0.5%. Старый actual августа этим previous не заменяется.
BLS допускает пересмотры PPI четыре месяца, сезонных факторов — до пяти лет; текущий API не доказывает initial.
`result_meta` содержит период, FD-серию, единицы, SA/NSA, URL, официальное embargo-время,
`vintage=release`, подтверждённое `(p)` / `estimate_status=preliminary`. Время скачивания не считается версией.
Календарная стадия `regular` сохраняется ради совместимости существующего месячного события;
предварительный характер оценки записан отдельно, она не называется final.

Проверяются caption/период, годовой диапазон, соседние месяцы, группы FD4/FD49104, единицы/сезонность,
пометка preliminary текущих столбцов, дата релиза. Goods-only FD413 и FD49116 не становятся Core PPI.
Исправленная/reissued публикация с явной пометкой требует review. Незаметную замену архива до первого
скачивания невозможно доказательно исключить; уже записанный initial не пересматривается из позднего payload.

## Расписание, хранение и запросы

Один GET [официальной таблицы PPI](https://www.bls.gov/schedule/news_release/ppi.htm) в существующем daily
scope schedules. Проверенные даты: 13.11/15.12.2026, 14.01/12.02/12.03/14.04/13.05/11.06/15.07/
10.08/10.09/15.10/12.11/15.12.2027; 08:30 ET. Период читается из Reference Month, а не выводится
из близости даты. Граница будущего года не зашита в адаптере. Новая опубликованная строка создаёт четыре
события. Пока ведомство не опубликовало следующий период, дата не генерируется.

Один GET максимум за UTC-день, включая неудачу. Журнал `bls-ppi-schedule` ограничивает повторные вызовы;
сохранённые события служат постоянным последним известным расписанием. При первом запуске существующий
проверенный ручной список даёт безопасный bootstrap четырёх метрик; затем статический PPI-список не
перезаписывается ежедневно и не откатывает принятый официальный перенос. После потери старого журнала
повторный bootstrap всё равно проходит защиту0012 и не имеет права затереть конфликтующие версии.

Старый `us_ppi`, DB title Producer Price Index, ID, hidden/history и значения сохраняются. Стабильный ключ
source/country/code/reference_period/regular не меняется при переносе. Новые UID автоматически не заменяют
существующие period-ключи. Здесь используется таблица с явными периодами, без выдуманного официального UID.
Подтверждённый Last Modified Date страницы может дать грубую дневную версию. Конфликт без сравнимой
версии, включая изменения в тот же день, сохраняет прежнее событие и диагностику0012. HTML не даёт надёжный
STATUS отмены: исчезновение/непонятная строка не удаляет и не отменяет запись. Reviewed corrections исходного
списка распространяются на все четыре показателя; отмена/восстановление проверяются с прежней версией baseline.

HTTP403/404/429, сеть, timeout, HTML ошибки или изменившаяся структура не повреждают сохранённые события.
Диагностика только в закрытом market_feed_runs, технических сообщений в интерфейс не добавлено.
CPI/PPI/API делят прежний BLS retry slot: один запрос факта за интервал, выбирается менее недавно
исполнявшаяся группа, ошибки не блокируют остальные. BLS API остаётся для NFP/unemployment/JOLTS;
их алгоритмы не менялись. PPI исключён из API-подстановок initial/previous и автоматических revisions.

## Проверка и ввод в работу

Новая миграция не нужна. Локальный `ppi-db.test.ts` использует настоящую RPC0012 в PGlite,
проверяет четыре строки, provenance, повтор, старый ID/hidden, отказ изменённому факту и сохранность при NULL.
Существующие legacy API-значения не удаляются и не переименовываются в initial; конфликты остаются для review.
Полные команды/ошибки: `market-us-ppi-checks.md`; итог CI — в Draft PR.

Проверить после review/merge: статус0012 по прежней инструкции, затем штатный daily job и
`bls-ppi-schedule`. При403 существующие даты остаются, runtime автоматизация не подтверждена.
При успешном источнике проверить четыре строки за один период, новые будущие месяцы и соответствие
официальному расписанию; затем штатный release job `bls-ppi-release` и provenance. Production collector
вручную ради демонстрации не запускать. Никакие production SQL/cron/env этим PR не менялись.
