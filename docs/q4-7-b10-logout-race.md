# Q4.7-B10 — Гонка выхода из аккаунта и изоляция пространств

Основа: `main` `d8b5257`. Блокер Б10 из `docs/q4-7-owner-decisions-launch-blockers.md`.

## 1. Симптом

Тест `e2e-supabase/economy-session-stale.spec.ts:142` иногда падал:
- после нажатия «Выйти» сессия заканчивалась, карточка аккаунта показывала «Гость»;
- но страница оставалась на `/settings/account`, перехода на `/login` не было.

**Частота до исправления (локально):**
- 1 из 15 на `d8b5257`;
- 1 из 30 на `65c889e`, то есть до Q4.6;
- 2 из 40 в диагностическом повторе с журналом событий.

## 2. Причина (доказана журналом событий)

`AuthProvider.updateToAuthenticated` асинхронный:
1. ставит `user`;
2. **ждёт** чтения профиля (`loadProfile`);
3. только потом ставит `authState = "authenticated"`.

Ни перед ожиданием, ни после него он не проверял, жива ли ещё сессия, ради которой был вызван.

**Порядок событий в упавших прогонах** (временный отладочный вывод в `AuthProvider` и `Shell`, в репозиторий не попал; оба зависания одинаковы):

```
268ms onAuthStateChange TOKEN_REFRESHED           ← приложение обновило токен (метка экономики устарела, 401 session_stale)
268ms updateToAuthenticated start                  ← ждёт GET /rest/v1/profiles
277ms signOut start                                ← пользователь нажал «Выйти»
282ms > POST /auth/v1/logout?scope=local
282ms < 200 /rest/v1/profiles
285ms < 204 /auth/v1/logout
285ms onAuthStateChange SIGNED_OUT → updateToGuest ← authState = guest, user = null
287ms updateToAuthenticated -> authenticated       ← ЗАПОЗДАВШЕЕ продолжение: authState = authenticated
290ms shell {authState: authenticated, user: null, isSpaceReady: true}
8301ms по-прежнему /settings/account
```

**Результат:** `authState = "authenticated"` при `user = null`. `Shell` перенаправляет на `/login` только гостя (`isGuest`). Поэтому перенаправления нет, а карточка показывает «Гость», потому что `user` пуст.

**Последствие хуже зависшего экрана — утечка данных между пространствами (доказано тестом):**
- `loadProfile` записывает профиль **ушедшего** аккаунта A;
- `Shell` видит «вошёл, профиль загружен» и вызывает `syncCloudNickname`;
- никнейм A записывается **в игру гостя** (`ayra_demo_v1` без префикса аккаунта);
- при первом входе другого аккаунта B приложение предлагает этот «гостевой» профиль, то есть никнейм A, на шаге выбора профиля. Онбординг B идёт не тем путём.

**Гипотеза о позднем переключении пространства опровергнута:** в момент зависания `isSpaceReady = true`, активное пространство — гостевое, как и должно быть. Ломается состояние авторизации, а не хранилище.

**XP и Coins не утекают:** игра гостя получает только никнейм. Сохранение аккаунта A не меняется — тест сравнивает его до и после выхода.

## 3. Исправление (одно место, `lib/auth/auth-context.tsx`)

У `AuthProvider` уже есть `AuthGeneration` (Q4.5-2). Он отличает текущую сессию от прошлой:
- обновление токена той же сессии поколение не меняет;
- выход, другой аккаунт или новый вход того же аккаунта начинают новое поколение;
- `signOut` вызывает `observeSession(null)` до запроса к серверу авторизации.

**Изменения:**
- `updateToAuthenticated(u, generation)` получает поколение сессии, в которой вызван (из `getSession` и `onAuthStateChange`). После чтения профиля он ничего не применяет, если поколение уже не текущее.
- `loadProfile(userId, stillCurrent)` не записывает профиль, ошибку или статус, если сессия кончилась, пока шло чтение.

**Без изменений:**
- mock-режим: поколение там не передаётся, поведение прежнее;
- `refreshProfile` и сохранение никнейма.

**Что не менялось вообще:**
- выход по-прежнему `signOut({ scope: "local" })`, завершается только сессия этого устройства;
- маршрут `/logout`, каналы вкладок, `AppStorage`, `GameProvider`;
- экономика, миграции, Q4.6, Market;
- таймауты, повторы и ожидания в существующих тестах.

## 4. Проверенные гонки

| Сценарий | Как проверено | Итог |
|---|---|---|
| Выход, когда ответ профиля от обновления токена приходит позже выхода | новый тест 1 (ответ удерживается до конца выхода) | `/login`, гость без данных A, сохранение A не изменилось, повторный вход открывает A |
| A → гость → B после такого ответа A | новый тест 3 | B получает только свой профиль и сохранение. Без исправления падает 5 из 5 |
| Две вкладки и другое устройство | новый тест 2 | обе вкладки уходят на `/login`. Другое устройство остаётся с живой сессией: сервер просит его обновить токен, а не «не вошёл». Вызов выхода — только `local` |
| Поздний ответ профиля при загрузке страницы (`getSession` и `INITIAL_SESSION`) | диагностика с удержанием ответов на 0, 20 и 60 мс после выхода | сбоя нет и до исправления. Теперь такой ответ тоже отбрасывается |
| Поздний `getUser` или `refreshSession` при загрузке | уже защищено в Q4.5-2 (`isCurrent(generation)`) | без изменений |
| Поздний ответ игрового API (`session_stale`) после выхода | `RequestScope` и `stillIn` (Q4.5-2). В журналах 401 приходят после выхода и ничего не меняют | без изменений |
| Выход без задержек, выход → вход того же аккаунта, A → гость → B | исходный тест `:142` | 60 из 60 |

**Оставшиеся места того же вида** (не исправлялись, причина не доказана):
- ответ профиля в межвкладочном `AUTH_SIGNED_IN`;
- `setAuthState("authenticated")` после ожиданий при регистрации.

Первое может вернуть на экран профиль, но не `authState`. Второе требует выхода посреди регистрации. Если нужно, их можно закрыть тем же поколением отдельной задачей.

## 5. Тесты

- **`e2e-supabase/auth-logout-race.spec.ts`** (3 теста). Ответ профиля удерживается через `page.route` и отдаётся только после выхода. Обновление токена вызывается честно: меняется состояние аккаунта, приложение получает фокус и само обновляет сессию.
- **Мутационная проверка** (исправление убрано, приложение пересобрано):
  - тест 1 — **5 из 5 падают**: 4 раза никнейм A в игре гостя, 1 раз зависшее перенаправление;
  - тест 3 — **5 из 5 падают**: онбординг B уходит не туда, потому что гостю достался никнейм A;
  - тест 2 без исправления проходит: он проверяет поведение вкладок и устройств, а не саму гонку.

## 7. Выход на других устройствах

Не изменился: `signOut({ scope: "local" })` и маршрут `/logout` не трогались. Тест 2 проверяет:
- сервер получил только вызов `local`;
- у аккаунта осталась одна живая сессия — сессия другого устройства;
- другое устройство обслуживается.
