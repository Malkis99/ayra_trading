## 0. Что есть сейчас и что меняется

**Сейчас (T7b-3):**
- запись сначала сохраняется локально, затем изменённые записи сразу уходят в облако;
- если отправка не удалась, запись уйдёт только при следующем её изменении;
- при открытии Журнала изменения забираются из облака, побеждает более новая версия — молча.

**После T7b-4:**
- **Очередь изменений (outbox).** Мгновенная отправка заменяется очередью с повторами.
- **Порядок обмена.** Сначала забираем изменения из облака, затем отправляем свои. Так конфликт виден до отправки.
- **Базовая версия.** У каждой записи помним версию, которая последней совпадала с облаком. По ней отличаем «изменили только здесь» и «изменили только там» от настоящего конфликта (изменили и там, и там).
- **Конфликт** — диалог, без молчаливой потери.
- **Первая загрузка.** Пока владелец не нажал кнопку первой загрузки, ничего из уже накопленного не отправляется.
- **Значок состояния** в шапке.

## 1. Очередь изменений

### 1.1 Где хранится

- **На устройстве**, в пространстве аккаунта (AppStorage):
  - ключ `ayra:<userId>:ayra_sync_outbox`;
  - у каждого аккаунта своя очередь;
  - у гостя очереди нет.
- **Что хранится:** не копия записи, а ссылка `{ table, id, enqueuedAt, attempts, nextAttemptAt, lastError }`. При отправке берётся **текущая** версия записи из локального журнала:
  - десять правок одной сделки — одна запись в очереди и одна отправка;
  - очередь остаётся маленькой (сотни байт на запись).
- **Рядом в том же пространстве:**
  - `ayra_sync_base` — базовые версии записей (`table:id → updatedAt`, последняя версия, совпавшая с облаком);
  - `ayra_journal_cloud_cursor` — курсор забора, уже есть с T7b-3;
  - `ayra_sync_conflicts` — нерешённые конфликты, обе версии целиком;
  - `ayra_sync_state` — отметка «первая загрузка завершена», время последнего успешного обмена.

### 1.2 Отправка и повторы

- **Когда отправляем:**
  - через 1 с после последней правки (несколько быстрых правок — одна пачка);
  - при возврате на вкладку;
  - при событии `online`;
  - по таймеру повтора.
- **Пачки:** до 100 записей на таблицу за запрос (`PLACEHOLDER`).
- **Пауза между повторами нарастает:** 1 с → 5 с → 30 с → 2 мин → затем каждые 5 мин (`PLACEHOLDER`, как в плане T7b). К паузе добавляется случайный разброс ±20%, чтобы много устройств не стучались одновременно. Число попыток не ограничено, запись из очереди не выбрасывается.
- **Ошибки:**

  | Ответ | Что делаем |
  |---|---|
  | нет сети, таймаут, 5xx | повтор по расписанию, статус «оффлайн» / «ошибка» |
  | 401 (сессия истекла) | обновить сессию и повторить один раз; не вышло — статус «ошибка», текст «Войдите снова» |
  | 403 (флаг выключен на сервере) | остановить отправку, **очередь сохранить**; статус скрыт (флаг выключен), журнал работает локально |
  | запись отклонена (слишком большая, время из будущего) | запись помечается «не отправлена», в очереди не крутится; видна в панели состояния с причиной |

- **Проверка результата.** Ответ upsert возвращает сохранённое на сервере `data.updatedAt`. Если сервер оставил другую версию (наша оказалась старее), это не «успех», а конфликт (раздел 2). Сейчас такой случай проходит молча.
- **Одна вкладка отправляет.** Отправляет и забирает только вкладка-«лидер» — та же аренда, что у знакомства: 15 с с продлением каждые 5 с, ключ в пространстве аккаунта. Остальные вкладки пишут в общую очередь и получают изменения через событие хранилища.

### 1.3 Закрытие вкладки

- Очередь уже на диске, поэтому при закрытии вкладки ничего не теряется.
- На `pagehide` вкладка-лидер отпускает аренду, и отправку подхватывает другая открытая вкладка.
- Если других вкладок нет, отправка продолжится при следующем открытии сайта этим аккаунтом на этом устройстве.
- Специальной «отправки при закрытии» нет: браузер её не гарантирует.

### 1.4 Смена аккаунта

- Движок привязан к одному `userId`. При смене пространства (вход, выход, другая вкладка сменила аккаунт):
  1. срабатывает существующий `flushSpace`: попытка отправить очередь, не дольше 3 с (`PLACEHOLDER`);
  2. остановка таймеров, отмена запросов в полёте (`AbortController`), отпуск аренды;
  3. для нового аккаунта запускается новый движок со своей очередью.
- Неотправленное **остаётся в очереди старого аккаунта** на этом устройстве и уйдёт, когда тот аккаунт снова войдёт здесь.
- Подробнее о защите — раздел 5.

## 2. Диалог конфликта

### 2.1 Когда это конфликт

Для каждой записи, пришедшей из облака:

| Изменено здесь (есть в очереди) | Изменено в облаке (версия ≠ базовой) | Что делаем |
|---|---|---|
| нет | да | берём облачную, молча |
| да | нет | отправляем свою, молча |
| да | да, и версии одинаковые | ничего (уже совпадают) |
| **да** | **да, версии разные** | **конфликт → диалог** |

- **Часы не решают конфликт.** «Кто новее» используется только там, где запись изменили с одной стороны, а это определяется по базовой версии, а не по часам. Поэтому сбитые часы одного устройства не приводят к молчаливой потере.
- **Удаление против правки** — тоже конфликт: на одном устройстве запись удалили, на другом изменили.

### 2.2 Что происходит до решения

- Конфликтная запись **не отправляется**: она вынимается из очереди и попадает в `ayra_sync_conflicts`, где хранятся обе версии.
- В интерфейсе показывается **версия этого устройства** — пользователь видит то, что сам ввёл.
- **Остальные записи синхронизируются как обычно**: один конфликт не останавливает обмен.

### 2.3 Когда показывается

- **Автоматически, один раз при открытии Журнала**, если есть нерешённые конфликты. Посреди ввода сделки диалог не всплывает: если открыт ящик сделки или другой диалог, ждём его закрытия.
- **В любой момент** — через значок состояния («Нужен выбор») и в настройках.
- Можно отложить кнопкой «Решить позже». Значок остаётся, пока всё не решено.

### 2.4 Как выглядит

- **Одна запись** — сравнение ключевых полей рядом, «Это устройство» и «Облако». Отличающиеся поля подсвечены.

  | Тип | Поля для сравнения |
  |---|---|
  | сделка | инструмент, направление, результат ($ / R), счёт, дата, заметка, время изменения |
  | заметка | заголовок, начало текста, время изменения |
  | план дня / недели | дата, первые пункты, заметка, время изменения |
  | счёт, стратегия | название, тип / правила (кратко), время изменения |

  Для удалённой стороны вместо полей — «Удалено <дата>».
- **Несколько записей** — список, у каждой свой выбор. Внизу:
  - «Для всех: оставить это устройство»;
  - «Для всех: взять из облака».
- **Варианты:**
  - **«Оставить это устройство»** — локальная версия получает новое время изменения и уходит в облако, облачная заменяется.
  - **«Взять из облака»** — облачная версия заменяет локальную. Если в облаке запись удалена, она исчезает и здесь.
  - **«Решить позже»** — ничего не меняется.

### 2.5 Тексты (в словари ru/en)

| Ключ | RU | EN |
|---|---|---|
| `sync.conflict.title` | Запись изменена на двух устройствах | This entry was changed on two devices |
| `sync.conflict.titleMany` | Записи изменены на двух устройствах: {count} | Entries changed on two devices: {count} |
| `sync.conflict.body` | Эту запись изменили и здесь, и на другом устройстве. Выберите, какую версию сохранить. Вторая будет заменена. | This entry was changed here and on another device. Choose which version to keep. The other one will be replaced. |
| `sync.conflict.thisDevice` | Это устройство | This device |
| `sync.conflict.cloud` | Облако | Cloud |
| `sync.conflict.keepDevice` | Оставить это устройство | Keep this device |
| `sync.conflict.takeCloud` | Взять из облака | Take from cloud |
| `sync.conflict.keepDeviceAll` | Для всех: оставить это устройство | For all: keep this device |
| `sync.conflict.takeCloudAll` | Для всех: взять из облака | For all: take from cloud |
| `sync.conflict.later` | Решить позже | Decide later |
| `sync.conflict.deletedAt` | Удалено {date} | Deleted {date} |
| `sync.conflict.changedAt` | Изменено {date} | Changed {date} |
| `sync.conflict.done` | Готово. Выбранные версии сохранены. | Done. The chosen versions are saved. |

## 3. Первая загрузка локальных данных в облако

### 3.1 Правило

- Уже накопленные на устройстве данные уходят в облако **только по кнопке владельца аккаунта**.
- До нажатия:
  - правки на этом устройстве тоже не отправляются, они копятся в очереди;
  - изменения из облака не применяются автоматически (кроме случая «на устройстве пусто», см. 3.4).
- Иначе первая же правка выгрузила бы журнал по кусочкам.

### 3.2 Где кнопка

- **Настройки → «Данные на этом устройстве»** — новый блок «Облако» (виден только при включённом флаге).
- Значок состояния в шапке в этом режиме показывает «Ждёт первой загрузки» и ведёт в этот блок.

### 3.3 Предварительный показ

Перед загрузкой — экран с цифрами, всё посчитано по живым записям (удалённые не загружаются и не считаются):

```
Загрузить журнал в облако
С этого устройства будет загружено:
  Счета ............ 2
  Сделки ........... 1 240
  Стратегии ........ 3
  «Не вошёл» ....... 18
  Планы дня/недели . 41
  Заметки .......... 27
  История импорта .. 4
Примерно 3,1 МБ. Скриншоты пока не загружаются (отдельный шаг).
Не поместятся (слишком большие): 0
[Загрузить]  [Отмена]
```

- **Если в облаке уже есть данные** (второе устройство) — три колонки, раздел 3.4.

### 3.4 В облаке уже есть данные

Перед показом скачивается **список** облачных записей (`id` и время изменения, без содержимого). Затем всё сопоставляется по `id`:

| Случай | Что показываем | Что делаем |
|---|---|---|
| в облаке пусто | «Будет загружено: …» | загрузка |
| на устройстве пусто, в облаке есть | — (кнопка не нужна, ничего не выгружаем) | **автоматическая загрузка на устройство** с прогрессом |
| есть и там, и там | «Только на этом устройстве: N (будут загружены) · Только в облаке: M (будут скачаны) · Есть в обоих местах и отличаются: K» | загрузка + скачивание; K отличающихся → диалог конфликта (раздел 2) списком с кнопками «для всех» |

- **Одинаковые записи** (тот же `id` и то же содержимое) не трогаются.
- **Возможные дубли.** Одна и та же сделка, введённая вручную на двух устройствах, получает разные `id`. Объединение даст две сделки. В предварительном показе — предупреждение: «Если вы вносили одни и те же сделки на двух устройствах, после объединения они могут повториться». Импортированные сделки с одинаковым ключом импорта (`importKey`) склеиваются автоматически — тот же ключ уже защищает от дублей при импорте.

### 3.5 Прогресс и отмена

- **Загрузка пачками по 100 записей.** Полоса: «Загружено 340 из 1 240».
- **«Отменить»** останавливает загрузку после текущей пачки.
  - Уже загруженное остаётся в облаке — это безопасно, запись идемпотентна.
  - Кнопка меняется на «Продолжить загрузку». Повторная загрузка не создаёт дублей (upsert по `id`).
- **Закрыли вкладку или пропала сеть** — то же, что отмена: при следующем открытии «Продолжить загрузку».
- **После успешной загрузки:** «Готово: журнал в облаке», отметка «первая загрузка завершена», дальше обычная синхронизация.
- Во время загрузки журналом можно пользоваться. Новые правки попадают в очередь и уйдут после загрузки.

| Ключ | RU | EN |

| `sync.upload.lead` | С этого устройства будет загружено: | This device will upload: |

| `sync.upload.noAttachments` | Скриншоты пока не загружаются (отдельный шаг). | Screenshots are not uploaded yet (separate step). |

## 4. Значок состояния синхронизации

- **Виден только** у вошедшего пользователя с включённым флагом. Гость и аккаунты без флага — никаких изменений в шапке.
- **Место:** в шапке слева от колокольчика (порядок станет: монеты → облако → колокольчик → чип плана). На мобильном — там же, только иконка.
- **Иконки lucide-react** (в установленной версии есть `Cloud`, `CloudOff`, `CloudUpload`, `RefreshCw`, `AlertCircle`), только токены дизайна; золото не используется — оно только для достижений.

| Состояние | Иконка | Подпись (RU / EN) | Когда |
|---|---|---|---|
| синхронизировано | `Cloud` | Сохранено в облаке / Saved to cloud | очередь пуста, последний обмен успешен |
| идёт | `RefreshCw` (вращение только без reduced motion) | Синхронизация… / Syncing… | идёт отправка или забор |
| оффлайн | `CloudOff` | Нет сети — изменения сохранены на устройстве / Offline — changes are saved on this device | `navigator.onLine = false` или сеть недоступна |
| ошибка | `Cloud` + значок `AlertCircle` | Не удалось синхронизировать / Sync failed | ошибка сервера, сессия, отклонённые записи |
| нужен выбор | `Cloud` + точка с числом | Нужен выбор: {count} / Choice needed: {count} | есть нерешённые конфликты |
| ждёт первой загрузки | `CloudUpload` | Журнал ещё не в облаке / Journal not in the cloud yet | флаг включён, первая загрузка не сделана |

- **Нажатие открывает небольшую панель:**
  - состояние и время последней синхронизации («2 мин назад»);
  - сколько изменений ждёт отправки;
  - записи «не отправлены» с причиной (слишком большая / неверное время устройства);
  - кнопки «Повторить сейчас», «Решить конфликты», «Настройки облака».
- **Доступность:** кнопка с `aria-label` = подпись состояния; смена состояния объявляется через `aria-live="polite"`, но не чаще раза в 10 с.

## 5. Выход из аккаунта и смена аккаунта

**Цель:** данные одного аккаунта никогда не попадают в другой — ни на устройстве, ни в облаке.

### 5.1 Что уже защищает (T7a, T7b-3)

- Пространства AppStorage: у каждого аккаунта свои ключи, у гостя свои.
- Запрос в облако идёт, только если сессия Supabase принадлежит тому же аккаунту, что открыт на устройстве.
- Забор не пишет данные, если за время запроса сменилось пространство.
- RLS на сервере: даже ошибка клиента не позволит записать чужому `user_id`.

### 5.2 Что добавляет T7b-4

1. **Движок на одного пользователя.** Очередь, базовые версии, курсор и конфликты читаются и пишутся с явным `userId`, а не из «текущего пространства». После смены аккаунта старый движок не может ничего записать.
2. **Перед каждой пачкой** — повторная проверка: активное пространство и сессия = `userId` движка. Не совпало — остановка без записи.
3. **Выход:** `flushSpace` пытается отправить очередь, не дольше 3 с. Не успел — изменения ждут на этом устройстве в пространстве аккаунта.
4. **«Выйти и удалить данные аккаунта с устройства»:**
   - если очередь не пуста или есть нерешённые конфликты — предупреждение: «{count} изменений ещё не в облаке. Если удалить данные сейчас, они пропадут.»;
   - кнопки «Подождать отправку» (пробует ещё 30 с с прогрессом) и «Удалить всё равно»;
   - вместе с данными удаляются очередь, базовые версии, курсор и конфликты этого аккаунта.
5. **Другая вкладка сменила аккаунт** (событие пространства) — эта вкладка останавливает движок так же, как в пункте 3, и перезапускается под новым аккаунтом.
6. **Перенос данных гостя в аккаунт** (уже есть, C1): перенесённые записи считаются **локальными данными аккаунта, ещё не загруженными**. Они уходят в облако только через первую загрузку (раздел 3) или, если она уже была, через обычную очередь. Автоматического переноса гостя в облако нет.

### 6.2 Поправка «сбитые часы»

- Время изменения записи при правке = `max(сейчас, время версии из облака + 1 мс)`. Тогда правка, сделанная после получения облачной версии, всегда «новее» её, даже если часы устройства отстают.
- Это небольшая правка локального репозитория, включена в PR 4b.

### 6.3 Что чем проверяем

| Уровень | Что |

| **Юнит-тесты (Vitest, моки)** | очередь: склейка правок, повторы и паузы (фейковые таймеры), ошибки 401/403/5xx, отклонённые записи; таблица 2.1 для всех вариантов; удаление против правки; сбитые часы (S7, S8); привязка к `userId` и остановка при смене пространства; аренда вкладки; расчёт предварительного показа и сопоставление по `id`; отмена и продолжение загрузки |

### 6.4 Риски

- **Дубли после объединения двух устройств.** Предупреждение в предварительном показе. Ручное удаление дублей остаётся за пользователем.
- **Рост хранилища на устройстве:** очередь и базовые версии — около 100 байт на запись. Конфликты хранят обе версии, но их обычно мало.
- **Курсор по `updated_at`** может пропустить строки, если транзакции на сервере завершаются не по порядку. Это закрывает перекрытие 60 с из T7b-3.
- **Вложения не синхронизируются до шага 0005.** На втором устройстве у сделки будет «скриншот недоступен на этом устройстве». Текст для этого — в PR 4c.
