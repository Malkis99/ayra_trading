# WATCH-1B.1 — серверная основа облачных приоритетов

Статус: подготовлено для ревью; **production SQL не применён**, UI приоритетов отсутствует.
База ветки — main `673f85134bab4e130e026191fac60ffe64f33440` (Merge #212).
На момент выбора номера main содержит миграции до 0016, открытый #205 (Q4.5.1) SQL не добавляет.
Свободный номер — **0017**. Перед ручным применением повторно проверить актуальные main и PR.

## Хранение и совместимость

Одна строка `public.market_user_data`, PK `(user_id, id)`, `id='watchlist_meta'`.
Новых таблиц/RPC/политик RLS/прав нет. Расширяется только допустимый ID и существующий
INVOKER-триггер `market_row_before_write`; ветка старых ID сохраняет правила 0008.

```json
{
  "id": "watchlist_meta",
  "version": 1,
  "revision": 2,
  "updatedAt": "2026-11-21T10:00:00Z",
  "entries": {
    "eurusd": {
      "priority": false,
      "revision": 2,
      "operationId": "00000000-0000-0000-0000-000000000002"
    }
  }
}
```

Это пример контракта, не запись пользователя. `updatedAt` внутри JSON, `updated_at` и
`client_updated_at` метаданных устанавливает сервер одним `clock_timestamp()`; клиентские часы
не участвуют в разрешении конфликтов. Revision — положительное целое до `Number.MAX_SAFE_INTEGER`.
На вставке общая и все начальные ревизии равны 1, на изменении общая и изменённые entry-ревизии
увеличиваются ровно на 1. Пустой UPDATE без изменений entries отклоняется.

`false` — явное снятие приоритета, не удаляется. Неизвестные поля верхнего уровня и entries,
неизвестные стабильные ID сохраняются буквально; триггер запрещает их удалять/изменять
попутно. SQL допускает будущие ID `[a-z0-9]{1,32}`, команды текущего клиента — только ID каталога.
Контракт более новой версии читается как opaque/unsupported: V1 не пишет поверх него.
Лимит всей JSONB-записи остаётся **16384 байт серверного JSON-текста**, включая UTF-8 и timestamp.
Превышение — отказ, не усечение или удаление старых entries.

Старые клиенты игнорируют отдельную неизвестную строку при merge и отправляют только известные
ID. Они не удаляют метаданные и не меняют формат `watchlist`. Канонический порядок, лимит 30,
Chart Notes, настройки и список инструментов этим этапом не меняются.

Удаление инструмента из списка не удаляет метаданные или заметки. При будущем повторном
добавлении действует сохранённое true/false; UI-фильтр будущего WATCH-1B должен пересекать
приоритеты с текущим Watchlist, не возвращать удалённые инструменты в список автоматически.

## CAS, идемпотентность и аккаунты

1. Создать UUID операции **один раз**, привязать к userId, InstrumentId и expectedEntryRevision.
2. Проверить текущую сессию/активный аккаунт и `user_features.cloud_sync`.
3. Прочитать только собственную `watchlist_meta`, сохранив неизвестные поля.
4. При отсутствии строки — INSERT с явным `user_id`; конкурентный 23505 вызывает перечитывание.
5. При наличии — PATCH с фильтрами user_id, id и `data->>revision=expectedRevision`,
   `select(data)` / `return=representation`. PostgreSQL сериализует конкурирующие UPDATE,
   повторно проверяя WHERE после блокировки строки. **Ноль строк — не подтверждение.**
6. Разные инструменты можно перебазировать, если entry-revision целевого инструмента не изменилась.
   При изменении той же записи вернуть conflict, не выбирать победителя по времени.
7. Максимум три цикла read/CAS; после исчерпания — pending/contended, операция остаётся у caller.
   Транспортная ошибка записи допускает одно контрольное чтение. Сохранение подтверждается
   только совпадением operationId, ожидаемой entry-revision+1 и значения priority.

Идемпотентность хранится в последней операции **каждого** инструмента. Повтор после изменения
другого инструмента подтверждается без записи. Если более новая операция того же инструмента
уже заменила receipt, старая операция получает conflict и не применяется повторно. Это не
бесконечный журнал всех operationId. Повторять старую команду с новой expectedEntryRevision
нельзя: новое явное действие получает новый UUID.

Быстрые последовательные команды caller должен сериализовать (или объединять до отправки).
Основа не угадывает порядок независимых устройств. `acceptConfirmedMeta` не принимает поздний
ответ с меньшей общей revision и фиксирует неоднозначность одинаковой revision с разным JSON.
Постоянная offline-очередь и её UI не добавлены: helper возвращает pending, будущий caller обязан
сохранить намерение в пространстве исходного аккаунта, не подтверждать облачное сохранение.

Каждый обмен подписан на смену пространства, проверяет владельца после каждого await и
снимает подписку в finally. A→B→A также инвалидирует обмен. При отмене ответ не применяется.
Уже отправленный запрос может законно завершиться **для A**; явный owner в payload и RLS не
позволят записать его как B при смене JWT. Между отдельными локальными записями обычной
Market-синхронизации также повторно проверяется аккаунт. Guest не получает строки A.

Новая основа не вызывает запросы автоматически и не меняет облачную модель Watchlist.
Обычная синхронизация получает лишь защиту владельца/асинхронных ответов; работает и **до 0017**.

## Безопасность и пересечение с Claude

RLS 0008 остаётся: SELECT только своё, INSERT/UPDATE только своё при cloud_sync=true.
Anon не читает; authenticated не может DELETE или писать server columns. Service-role
не используется клиентом. Смена владельца/ID запрещена существующим триггером.

В `e2e/fake-supabase/server.mjs`, с которым также работает #205, изменён только whitelist
полей Market POST: разрешён существующий в SQL столбец user_id с обязательной проверкой
совпадения с авторизованным пользователем. Journal/Quests/economy не меняются.
При обновлении main сохранить обе независимые правки; не перезаписывать файл целиком.

## Ручное применение (только после отдельного разрешения)

1. Проверить CI и SHA PR, отсутствие конкурирующей 0017, сравнить файл с утверждённым diff.
2. Сделать штатную резервную копию средствами владельца; не экспортировать токены/личные данные в PR.
3. В read-only проверке подтвердить 0008: PK, id/data-check, RLS/policies, column grants,
   определение `market_row_before_write`, cloud_sync_enabled; отсутствие конфликтующей реализации.
   История migrations может не отражать ранее вручную применённые SQL — сверять объекты.
4. Зафиксировать число и контрольный снимок существующих строк, ACL и policies безопасно внутри БД.
5. Выполнить **весь** `supabase/migrations/0017_watchlist_meta.sql` в одной транзакции
   (файл уже содержит BEGIN/COMMIT). При ошибке — ROLLBACK, не исправлять production на ходу.
   lock_timeout=5s / statement_timeout=30s ограничивают ожидание; при занятости повторить позже.
6. Из нового соединения проверить расширенный check, INVOKER, те же policies/ACL и сохранность
   существующих строк. Сам файл не пишет ни одной пользовательской строки и не создаёт приоритетов.
7. Функциональные мутации проводить только на отдельном согласованном тестовом аккаунте,
   не на реальных пользователях. На этом этапе приоритетный UI ещё не включается.

CI выполняет SQL только на PGlite/одноразовом PostgreSQL. GitHub Actions, package scripts и
Vercel Build не содержат db push/migration deploy/production SQL. Supabase Git Integration,
по подтверждению владельца, выключена; эта работа её не включает. Merge не является разрешением
на production SQL. Дальнейшее UI-подключение — отдельный этап.

## Откат без потери данных

Предпочтительно откатить код и оставить additive 0017/`watchlist_meta`: старые клиенты безопасны.
`0017_watchlist_meta.down.sql` восстанавливает старый check/триггер **только если метаданных нет**.
При любой строке watchlist_meta он прерывается с `market_meta_rollback_requires_preservation`,
не удаляя данные. Не обходить защиту DELETE; структурный откат с существующими метаданными
требует отдельного согласованного плана архивирования/восстановления. Rollback не удаляет таблицу.
