# Синхронизация языка RU/EN

Область: только язык интерфейса, существующие `profiles.locale` и клиентская синхронизация.
База ветки: main после merge #152 (`de2fb3e9313465e12378c01e0cd1018ec58bdc3e`).
SQL, RLS, миграции, production и правила часового пояса не изменяются.

## Подтверждённая причина

На устройстве без явного выбора языка `localLang=null`. Первоначальное облачное значение RU
приводило к `none`, но не сохранялось как baseline: старый `settle` требовал непустой локальный язык.
Затем первый выбор EN не становился dirty, поскольку прежний эффект требовал `synced !== null`.
Интерфейс переключался, но PATCH locale не происходил. Параллельный обмен журнала иногда
сохранял EN и случайно скрывал ошибку в обычном e2e.

На неизменённом main диагностический сценарий, дожидающийся завершения первого обмена,
воспроизвёл:

```text
Error: expect(received).toBe(expected) // Object.is equality
Expected: "en"
Received: "ru"
- Timeout 20000ms exceeded while waiting on the predicate
```

Команда исходного сценария:
`npx playwright test -c playwright.supabase.config.ts sync-sessions-locale.spec.ts --grep "the language chosen"`.
Диагностическая копия запускалась с конфигурацией в `work/`, меняла только ожидание перед
первым English и запись запросов. Теперь постоянная регрессия явно проверяет baseline RU перед кликом,
без увеличения таймаутов. См. исходную диагностику `docs/market-us-cpi-checks.md`.

## Решение

- Первый успешный профильный обмен сохраняет baseline, включая облачный RU без локального выбора.
- Явный выбор пользователя сохраняется немедленно: account-scoped `ayra_locale_sync`, `pending`, `dirty`,
  монотонная локальная `revision`, `changedAt`. Совместимость со старой записью сохраняется.
- Изменения из облака отделены от пользовательских: `setLanguage(value, "cloud")` не создаёт новую отправку.
- Запросы сериализованы; быстрые переключения объединяются. Подтверждение старого PATCH обновляет
  baseline, но не очищает более новое ожидающее изменение и не меняет интерфейс.
- Устаревший ответ другой сессии или после выхода не применяется.
- Ошибка GET/PATCH сохраняет локальный язык и dirty. Нового подтверждения сохранения языка не показываем.
  Повторная попытка — при следующем разрешённом обмене, новом выборе или следующем открытии в auto;
  бесконечного фонового повторения и polling нет.

## Режимы

**Автоматический:** новый явный выбор отправляется сразу при включённом облаке и готовом аккаунте.
Если во время запроса сделан другой выбор, после завершения отправляется последнее ожидающее значение.

**Ручной:** выбор остаётся локально, в том числе после перезагрузки. Обмен профиля запускается
существующей явной командой «Синхронизировать», через новое завершение обмена журнала.
Выбор, сделанный после этой команды, не получает автоматического разрешения на отправку:
для него нужна следующая команда. Вход/рендер сами по себе не включают auto.

Часовой пояс использует прежние `decideTimezone`, baseline, dirty и разрешения обмена;
отдельная автоматическая отправка языка не обновляет часовой пояс.

## Проверка владельцем

1. Включить облако и автоматический режим. После первого обмена выбрать English, перезагрузить страницу.
2. На другом устройстве войти в тот же аккаунт: должен появиться EN. Выбрать русский, выполнить обмен на первом устройстве.
3. В ручном режиме выбрать другой язык: облако меняется только после команды синхронизации.
4. При недоступной сети язык остаётся на устройстве; после восстановления выполнить синхронизацию.
5. Быстро переключить RU/EN несколько раз: после завершения отправки должен сохраниться последний выбор.

## Ограничения

Локальная revision защищает порядок действий одного устройства, а не является новой серверной версией.
Одновременное редактирование на независимых устройствах без связи не получает глобальной гарантии
порядка действий: используется существующий профиль и порядок принятых сервером запросов.
Для обычной последовательной синхронизации двух устройств есть браузерная регрессия.
Облачный индикатор журнала продолжает описывать журнал; новую общую систему статусов профиля не добавляем.
Новые секреты и реальные пользовательские данные для проверок не требуются: e2e использует fake Supabase.
После PR — остановка и решение владельца; JOLTS и дальнейшие источники остаются следующим отдельным этапом.

## Обнаруженные падения при разработке

Новый тест `Locale sync request ordering > failed PATCH keeps local EN pending; explicit retry saves it`
первоначально выполнялся в auto. Команда:
`npx playwright test -c playwright.supabase.config.ts sync-sessions-locale.spec.ts timezone-cloud.spec.ts`.

```text
Error: expect(received).toBe(expected) // Object.is equality
Expected: 1
Received: 2
- Timeout 5000ms exceeded while waiting on the predicate
```

Трассировка подтвердила: после автоматической попытки отдельное завершение обмена журнала
запустило следующий разрешённый профильный обмен. Это не бесконечный цикл и не retry PATCH внутри SDK.
Для проверки строго одного явного разрешения сетевой e2e выделен в ручной режим: до команды 0 PATCH,
после первой команды ровно 1 неуспешный PATCH, затем отдельная команда и успешное подтверждение.
Точное ожидание одного запроса сохранено. Auto-ошибки проверяются тестами компонента с управляемыми
ответами. Дополнительно защищён отдельный случай позднего React-эффекта после ошибки: та же revision
не получает повторную автоматическую попытку только из-за рендера.
