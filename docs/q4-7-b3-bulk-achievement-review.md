# Q4.7-Б3 — Пакетное рассмотрение исторических достижений одного аккаунта

Основа: `main` `61ed903` (merge #225). Новая миграция — `supabase/migrations/0022_game_achievement_bulk_review.sql` (+ откат). Нигде не применялась.

## 1. Что это и чего здесь нет

**Что это.** Владелец за одну операцию принимает несколько достижений **одного** аккаунта, которые сервер не может доказать сам: `pending_review` → `legacy_accepted`.
- Только инструмент владельца (`scripts/migration-admin.mjs`, роль `game_migration_admin`), публичного API нет.
- Каждое достижение выбирает человек, всё решение — одна транзакция с полным аудитом.

**Чего никогда не бывает:**
- `verified` руками;
- принятие `rejected`;
- изменение `verified`;
- достижение, о котором есть разногласия устройств (разные ранги, разные боссы);
- несколько аккаунтов в одной операции;
- id, которого у аккаунта нет;
- XP или Coins: достижения их не дают, а операция не трогает журнал наград и профиль.

## 2. Модель доверия

- **Права проверяет база, а не инструмент.**
  - Функции `SECURITY DEFINER`, владелец — `game_economy_owner`, `EXECUTE` только у `game_migration_admin`.
  - `anon`, `authenticated` и `service_role` вызывать их не могут — тест B4.
  - Таблицу достижений и журнал напрямую не пишет никто, кроме владельца экономики: роль инструмента получает `permission denied` — тест B4c.
- **Инструмент только показывает и спрашивает подтверждение.** Всё, что он присылает (список, версии, операцию, причину), база перепроверяет под блокировками.
- **Версия строки.** Предпросмотр отдаёт `md5` каждой строки достижения: статус, источник, деталь, свидетельства, заявившие снимки, правила, сверка, решение. Решение принимается только по той версии, которую видел человек. Если строка изменилась после просмотра, база отказывает (`game_mig_review_stale`) и требует новый просмотр.

## 3. Применимость: до и после активации

**B. `cloud_active` — работает сейчас.** Строки достижений появляются только при активации: в той же транзакции (0020) или позже через `transfer-achievements`. Решение принимается по записанным строкам активированного аккаунта, и полномочия здесь те же, что у существующего решения по одному достижению (`decide-achievement`, 0020). Новых прав не добавлено.

**A. `migration_pending` — не поддерживается, нужна отдельная модель.** До активации строк ещё нет: план считается на лету из снимков, и пока окно открыто, он может измениться (новый снимок, другой остаток).
- Предпросмотр показывает этот план с пометкой «информация, решение невозможно».
- Пакетная операция отказывает: `game_mig_not_active`.

**Предложение для сценария A (не реализовано, нужно ваше решение).** Таблица «предварительных решений»:
- (аккаунт, id достижения, версия плана, решение, причина, автор);
- активация применяет решение только если план для этого id совпал по версии, иначе возвращает его на рассмотрение;
- те же права и тот же аудит.

Плюсов перед текущим порядком «сначала активация, потом решение» немного: достижения в `pending_review` и так видны человеку как «ждёт проверки». Рекомендую оставить сценарий B.

## 4. Порядок команд

```
# 1. просмотр (ничего не меняет)
node scripts/migration-admin.mjs achievements-review <user>

# 2. решение по выбранным id
node scripts/migration-admin.mjs achievements-accept <user> --ids author,plans7 --actor <кто> --reason "<почему, ≥ 10 символов>"
#    → печатает полный просмотр, операцию (UUID) и точный список изменений: id: pending_review → legacy_accepted
#    → спрашивает id аккаунта, затем тот же список id (или --confirm <user> --confirm-ids author,plans7)
#    → одна транзакция в базе

# 3. повтор той же операции после сбоя связи — безопасен
node scripts/migration-admin.mjs achievements-accept <user> --ids author,plans7 --operation <UUID из шага 2> …
```

**Предпросмотр (`game_mig_achievement_review`) показывает:**
- аккаунт и состояние;
- активированную сверку и время записи достижений;
- можно ли сейчас решать, а если нельзя — почему;
- по каждому достижению:
  - id и семью;
  - статус и источник;
  - правило из каталога, то есть название условия;
  - вид доказательства — почему не доказано;
  - записанную деталь и свидетельства;
  - каждый заявивший снимок: есть ли он, статус, время, устройство и **что именно он заявил**;
  - **разногласия устройств** — все значения, без выбора;
  - кем и почему уже решено;
  - версию;
- список принимаемых сейчас: `pending_review` без разногласий.

**Список выбирает человек:**
- «принять всё ожидающее» нет;
- неуказанное в `--ids` остаётся как есть — это и есть исключение достижения из пакета;
- подтверждение двойное: id аккаунта и тот же список id.

## 5. Что проверяет база (`game_mig_bulk_accept_achievements`)

**Запрос:**
- автор есть, причина не короче 10 символов (плейсхолдер);
- id операции и сверки заданы;
- список — от 1 до 64 элементов (плейсхолдер), без повторов, у каждого корректные id и версия.

**Порядок:**
1. **Одна операция на аккаунт в момент времени.** Advisory-блокировка по аккаунту: двое администраторов ждут друг друга.
2. **Повтор.** Операция с этим id уже выполнена: тот же аккаунт и тот же список — ответ `replay: true`, ничего не меняется и в журнал не пишется. Другой список или аккаунт — `game_mig_operation_mismatch`.
3. **Запись операции в журнал — первой.** Она берёт строку пользователя так же, как удаление аккаунта, поэтому с удалением нет взаимной блокировки. Удалённый аккаунт → `game_mig_no_such_account`.
4. **Аккаунт.** Он `cloud_active`, его достижения записаны, активирована именно та сверка, которую видел человек.
5. **Строки.** Блокируются в одном порядке по id. Каждая должна существовать у этого аккаунта, иметь статус `pending_review`, совпадать по версии и не иметь разногласий устройств.
6. **Любой отказ — отказ всей операции** (`game_mig_achievement_verified` / `_rejected` / `_decided` / `_conflict` / `game_mig_review_stale` / `game_mig_no_such_achievement`): ничего не принято и ничего не записано.
7. **Принятие и аудит.** `legacy_accepted` с автором, временем и причиной. Аудит:
   - запись `achievements_bulk_accepted` — операция, сверка, список, число, причина;
   - запись `achievement_decided` на каждое достижение — было `pending_review`, стало `legacy_accepted`, причина, операция, просмотренная версия.

   В журнале БД (`db_user`) записывается реальный вход в базу.

## 6. Особые достижения

| id | Почему не доказывается сервером | В пакете |
|---|---|---|
| `firstPlan`, `firstReview`, `plans7` | до #225 устройство их не открывало; правило сервера — только флаг устройства (0021) | можно принять человеком |
| `firstPropRules` | до #225 не сохранялось на устройстве | можно |
| `firstScreenshot` | засчитанный скриншот сервер не видит | можно |
| `author`, `propDisciplined5` | только на устройстве | можно |
| `category:<id>` (ранг пути) | доказывается только оплаченным личным квестом | можно, **если устройства согласны**; разные ранги → отказ |
| `week:<понедельник>` | только на устройстве | можно, **если устройства согласны**; разные боссы → отказ |

**Решение владельца по #225:**
- Старые `firstPlan`, `firstReview` и `plans7` могут открыться на устройстве с опозданием, при следующем сохранении плана, если исходные условия выполнены.
- Дополнительных XP и Coins это не даёт.
- Такое локальное открытие не доказательство для сервера: в 0021 эти достижения `device_only`, сервер ни на какое исправление клиента не смотрит.

## 7. Откат и восстановление

- **Откат 0022** удаляет только функции. Принятые решения остаются: это обычные строки `legacy_accepted` с журналом, такие же пишет решение по одному достижению из 0020. Ничего не удаляется и не переписывается — тест V.
- **Сбой посреди операции** откатывает всю транзакцию. Повтор с тем же `--operation` безопасен:
  - если первая попытка успела выполниться — `replay`;
  - если нет — выполнится один раз.
- **Ошибочное решение.** Отдельной отмены в пакете нет. Решение по одному достижению (0020) может вернуть `pending_review` или поставить `rejected` с причиной и записью в журнал. Вопрос 2 ниже.

## 9. Риски и вопросы

1. **Сценарий A** (до активации) не поддерживается, предложение — в разделе 3. Нужен ли он?
2. **Решение по одному достижению из 0020** по-прежнему разрешает пересмотр `rejected` и не проверяет разногласия устройств: оно примет запись с рангом, который план выбрал как высший. Ужесточить его так же, как пакет?
3. **Разногласия устройств** сейчас можно решить только одиночной командой. Отдельной процедуры «выбрать ранг или босса явно» нет. Нужна ли она?
4. **Плейсхолдеры:** 64 достижения в операции, причина от 10 символов.
5. **Владелец базы** технически может обойти любые проверки. Защита рассчитана на ошибки, а не на злой умысел, как и в Q4.6.
