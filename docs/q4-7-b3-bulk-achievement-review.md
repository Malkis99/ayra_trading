# Q4.7-Б3 — Рассмотрение исторических достижений одного аккаунта

Основа: `main` `61ed903` (merge #225). Миграция — `supabase/migrations/0022_game_achievement_bulk_review.sql` (+ откат). Нигде не применялась.

## 1. Что это и чего здесь нет

**Что это.** Владелец решает по достижениям одного аккаунта, которые сервер не может доказать сам:
- по одному — команда `decide-achievement`;
- или несколько за одну операцию — `achievements-accept`.

Это только инструмент владельца (`scripts/migration-admin.mjs`, роль `game_migration_admin`), публичного API нет. **У обоих путей одна политика безопасности в базе:** `game_mig_achievement_refusal`.

**Чего никогда не бывает ни одним путём:**
- `verified` руками и изменение `verified`;
- принятие или повторное решение по `rejected` (пересмотр отклонённых — отдельная будущая процедура);
- изменение уже принятого решения;
- возврат в `pending_review`;
- принятие при разногласиях устройств: разные ранги одного пути или разные боссы одной недели (лучший не выбирается);
- несколько аккаунтов в одной операции;
- id, которого у аккаунта нет;
- XP или Coins: журнал наград и профиль не трогаются.

## 2. Решения владельца (финальное ревью Б3)

1. Принятие до активации не нужно: только `cloud_active`.
2. У одиночного и пакетного пути одна политика безопасности.
3. Разногласия рангов и боссов автоматически не разрешаются, сейчас — отказ. Процедура явного выбора — отдельно, если понадобится.
4. Лимит 64 достижения за операцию утверждён.
5. Минимум 10 символов причины утверждён как технический порог. Причина должна быть по существу — это обязанность оператора.
6. Пересмотр `rejected` — только отдельная будущая процедура. Текущие команды не позволяют этого даже неявно.

**Решение по #225:**
- Старые `firstPlan`, `firstReview` и `plans7` могут открыться на устройстве с опозданием, при следующем сохранении плана, если исходные условия выполнены.
- Без XP и Coins.
- Это не доказательство для сервера: в 0021 они `device_only`.

## 3. Все пути изменения достижения и их ограничения

| Путь | Кто вызывает | Что может | Ограничения |
|---|---|---|---|
| `game_mig_record_achievements` (0020) | только внутри активации и переноса (роль инструмента вызвать не может — тест B8a) | вставить строки плана | `ON CONFLICT DO NOTHING`: записанную строку не меняет никогда |

## 4. Модель доверия

- **Права проверяет база, а не инструмент.**
  - Функции `SECURITY DEFINER`, владелец — `game_economy_owner`.
  - `EXECUTE` только у `game_migration_admin`. `anon`, `authenticated` и `service_role` вызывать их не могут.
- **Инструмент только показывает и спрашивает подтверждение.** Всё, что он присылает, база перепроверяет под блокировками.
- **Версия строки.** Предпросмотр отдаёт `md5` строки достижения. Пакетное решение принимается только по просмотренной версии. Одиночное решение сравнивает строку до записи в журнал и после блокировки. Если строка изменилась, приходит `game_mig_review_stale`.

## 5. Порядок команд

```
node scripts/migration-admin.mjs achievements-review <user>                      # просмотр, ничего не меняет
node scripts/migration-admin.mjs achievements-accept <user> --ids a,b --actor <кто> --reason "<почему>"
#   → полный просмотр, id операции, точный список изменений; подтверждение id аккаунта и того же списка
node scripts/migration-admin.mjs achievements-accept <user> --ids a,b --actor <кто> --reason "<почему>" --operation <id>
#   → повтор после потери ответа: отправляется СОХРАНЁННЫЙ запрос этой операции (game_mig_bulk_operation) → replay
node scripts/migration-admin.mjs decide-achievement <user> <id> <legacy_accepted|rejected> --actor <кто> --reason "<почему>"
```

**Предпросмотр показывает:**
- аккаунт, состояние, сверку и можно ли решать;
- по каждому достижению:
  - правило (название условия), вид доказательства, источник;
  - свидетельства и записанную деталь;
  - каждый заявивший снимок и что он заявил;
  - разногласия устройств — все значения;
  - решения;
  - версию;
- список принимаемых сейчас;
- до активации — только план, без возможности решения.

**Исключение.** Неуказанное в `--ids` остаётся как есть. Варианта «принять всё ожидающее» нет.

## 6. Идемпотентность (контракт)

1. **Один id операции — один запрос.** Отпечаток запроса — `md5` от:
   - аккаунта;
   - сверки;
   - id достижений с просмотренными версиями (по порядку id);
   - автора (без пробелов по краям);
   - причины.

   Он хранится в записи операции в журнале вместе со списком и версиями.
2. **Тот же запрос снова** — `replay: true`, ничего не меняется и ничего не пишется. После успеха строки закономерно изменились (статус, версия), но отпечаток сохранён: он сравнивается не со строками.
3. **Тот же id с любым отличием** — `game_mig_operation_mismatch`, ничего не меняется. Отличием считается другой аккаунт, сверка, список, версия, автор или причина.
4. **Повтор после потери ответа.** Инструмент читает сохранённый запрос (`game_mig_bulk_operation`) и отправляет его как есть. Если первая попытка не дошла до записи, запроса нет, и операция выполняется один раз.
5. **Параллельные вызовы.** Порядок блокировок всегда один и тот же:
   1. advisory-блокировка id операции;
   2. advisory-блокировка аккаунта (её же берёт одиночное решение);
   3. проверка повтора;
   4. запись в журнал (строка пользователя — как при удалении);
   5. аккаунт;
   6. строки по порядку id.

   Последний рубеж — уникальный индекс `game_migration_audit_bulk_operation` по id операции.
6. **Удаление аккаунта.** Записи журнала удаляются каскадом, поэтому повтор после удаления получает `game_mig_no_such_account`, а не `replay`.

## 7. Применимость

- **`cloud_active`** — единственный сценарий. Строки достижений появляются только при активации.
- **`migration_pending`** — решения невозможны (`game_mig_not_active`). Предпросмотр показывает план как информацию. По решению владельца отдельная модель для этого сценария не нужна.

## 8. Откат и восстановление

- **Откат 0022:**
  - удаляет просмотр, пакетное решение, общую политику, чтение операции и индекс;
  - **возвращает `game_mig_decide_achievement` в точности как в 0020**, то есть со старой, более слабой политикой.

  Принятые решения остаются: ничего не удаляется и не переписывается. Откатывать 0022 после начала реальных решений не стоит — исправлять вперёд.
- **Сбой посреди операции** откатывает всю транзакцию. Повтор с `--operation` безопасен (раздел 6).
- **Ошибочное решение** текущими командами не отменяется: решённая строка не меняется. Это нужно учитывать до решения: предпросмотр, двойное подтверждение.

## 9. Тесты

**`supabase/tests/game_achievement_bulk_review.sql`.** Аккаунты проходят настоящий путь до активации.
- **B1 — просмотр.**
- **B2 — 15 отказов пакета:** пустой список, причина, автор, версия, повтор id, неизвестный и чужой id, чужая сверка, `verified`, ранги, боссы, другая сверка, `migration_pending`.
- **B3 — принятие:** одно и несколько, исключение, повтор, решённое, `rejected` после просмотра, история, XP и Coins.
- **B4 — права:** просмотр, пакет, чтение операции, одиночное решение, политика.
- **B5 — удалённый аккаунт.**
- **B6 — одиночная команда:** `rejected` (принять, решить снова), разногласия рангов, разногласия боссов, решённое, возврат в `pending_review`, `verified` руками, короткая причина, `verified` (принять или отклонить), неизвестный id. Ничего не меняется и не пишется. Допустимые решения (принять ожидающее, отклонить спорное) работают с аудитом. Пакет против того же `rejected` — отказ. XP и Coins не меняются.
- **B7 — контракт идемпотентности:** тот же id с другой сверкой, автором, причиной, версиями, списком или аккаунтом — отказ. Точный повтор после изменения строки — `replay`. Тот же автор с пробелами — `replay`. Ничего не записывается. Отпечаток хранится. Сохранённый запрос повторяется. Неизвестная операция — пусто.
- **B8 — `verified` ни одним путём:** внутренние функции недоступны, перенос — `replay`, строка не изменилась.

**Мутационная проверка** (PostgreSQL 16) — каждый мутант пойман:

| Мутация | Где упал тест |
|---|---|
| политика пропускает `rejected` | B3g |
| политика забывает о разногласиях | B2l |
| одиночная команда без общей политики | B6a |
| повтор сверяет только аккаунт | B3e |
| отпечаток без автора и причины | B7c |

Мутанты первой версии (конфликт, версия, повтор, `verified`) тоже пойманы.

**Параллельный доступ `scripts/test-concurrency.sh` O0–O6** (PostgreSQL 16):
- **O1:** 5 операций на одно и то же → 1 принята.
- **O2:** одна операция ×5 → 1 решение + 4 повтора.
- **O3:** удаление против 4 пакетов — взаимной блокировки нет.
- **O4:** пакет против одиночного решения — одно решает, другое отклонено целиком.
- **O5:** один id операции с двумя разными запросами одновременно → ровно одно решение.
- **O6:** удаление против 3 одиночных решений — взаимной блокировки нет, ничего не осталось.

**Инструмент T15a–h:** просмотр; неверное подтверждение аккаунта или списка; короткая причина; `verified` в списке; принятие с XP и Coins 125/62; повтор с `--operation` → `replay`; тот же id с другой причиной → отказ.

**PGlite, блок V:** 0022 дважды; тесты 0022, 0021, 0020, 0019, 0018; права; откат сохраняет решения.

## 10. Остаточные риски

1. **Откат 0022 возвращает слабую одиночную команду 0020.** Решение — исправлять вперёд, а не откатывать.
2. **Ошибочное решение текущими командами не отменить.** Пересмотр — отдельной процедурой, как и для `rejected`.
3. **Разногласия устройств сейчас решаются только отклонением.** Процедуры явного выбора ранга или босса нет (решение владельца 3).
4. **Владелец базы** технически может обойти любые проверки. Защита рассчитана на ошибки, а не на злой умысел.
