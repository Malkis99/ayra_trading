# Q4.4 — API серверного игрового дня и безопасная интеграция приложения

**Статус.** Серверные маршруты игрового дня и проверки миссии, переключение источника истины в приложении, первое серверное появление записи Журнала. Миграция `supabase/migrations/0016_game_day_api.sql` (откат: `0016_game_day_api.down.sql`) **не применяется к Supabase**.

**Ничего не включается:**
- 0014, 0015 и 0016 не применены к Supabase; `game_sync` выключен, ни один аккаунт не `cloud_active`;
- вид начисления `mission` выключен в базе, а маршрут проверки дополнительно не вызывает начисление без `AYRA_SERVER_MISSION_PAYOUTS=1` (не задан нигде);
- переключатель `NEXT_PUBLIC_AYRA_SERVER_ECONOMY` в production выключен: маршруты отвечают 404, приложение ничего не запрашивает;
- `mission shadow` в production выключен (как в Q4.2).

**Сегодня у всех аккаунтов режим `local`, и приложение работает ровно как раньше** (e2e: mock auth и «реальный Supabase без миграций»).

## 1. Серверный API

Все маршруты:
- пользователь — **только** из проверенной сессии Supabase (cookies → `auth.getUser` на сервере);
- функции базы вызываются сервисным ключом (только в `app/api/**/route.ts`, защита T7a), с `p_user` из сессии и **временем базы** (`now()`);
- тело строгое: поле `user_id`, `day`, время, режим открытия или сумма отклоняют **весь** запрос (400);
- только свой сайт (Origin) — иначе 403; лимит частоты на аккаунт — 429;
- ошибки — коды; сообщения базы, адреса и id наружу не выходят.

| Маршрут | Тело | Функция базы | Что делает |
|---|---|---|---|
| `GET /api/game/day/status` | — | `game_day_status` | Состояние аккаунта, флаг, серверный день, открытый день и положение каждой миссии; для неоткрытого дня — режим, в котором он откроется |
| `POST /api/game/day/open` | `{ extras }` | `game_day_open` | Открывает сегодняшний день **в режиме сохранённых торговых дней** |
| `POST /api/game/day/mode` | `{ mode, extras? }` | `game_day_set_mode` | Смена режима (правило слотов 0015) |
| `POST /api/game/day/accept` | `{ mission }` | `game_day_accept` | Принятие (повтор — то же время) |
| `POST /api/game/day/pass` | `{ mission }` | `game_day_pass` | «Не сегодня» для миссии |
| `POST /api/game/day/replace` | `{ from, to }` | `game_day_replace` | Замена дополнительного задания |
| `POST /api/game/day/trading-days` | `{ days }` | `game_set_trading_days` | Торговые дни — **со следующего игрового дня** |
| `POST /api/game/missions/verify` | `{ mission }` | `game_day_status`, `game_journal_for_check`, (`game_apply_reward`) | Полная серверная проверка миссии (раздел 5) |

**Причины отказа** (поле `error`):
- состояние: `account_not_active`, `day_not_open`, `day_closed`, `day_rest`;
- миссии: `mission_not_assigned`, `mission_not_accepted`, `mission_paid`, `day_cap`;
- замены и задания: `replacement_limit`, `not_replaceable`, `not_offered`, `bad_extras`;
- записи Журнала: `evidence_changed`, `source_used`;
- начисления: `sync_paused`;
- доступ и запрос: `not_signed_in`, `cross_origin`, `rate_limited`, `bad_request`;
- сервер: `server_economy_unavailable` (миграции не применены), `server_error`.

## 2. Проверка режима и дополнительных заданий (0016)

- **Торговые дни на сервере** (`game_accounts.trading_days`):
  - день открывается в режиме, который они дают (`trading` в торговый день, иначе `study` — как `defaultModeFor`; проверено для всех дней недели);
  - **клиент режим открытия не называет**;
  - изменение действует со следующего игрового дня, поэтому сегодняшний набор не пересоздаётся;
  - режим в течение дня меняется как в приложении (`game_day_set_mode`), по правилу слотов 0015: оплаченное остаётся, четвёртой миссии не появляется.
- **Каталог дополнительных заданий** (`game_extra_quests`):
  - сгенерирован из `lib/quests.ts`; совпадение с приложением проверено тестом;
  - при открытии и смене режима принимаются только задания режима, не больше двух, без повторов, никогда не миссия и не её «двойник» (`q_backtest`);
  - замена — только задание с самоотметкой из пула режима, с XP не больше заменяемого, не показанное сегодня, в пределах лимита 2;
  - задания выбирает приложение (по ответам онбординга, которых нет на сервере), сервер проверяет допустимость.
- **Дополнительные задания сервером не оплачиваются:** вид `self_report` закрыт.

## 3. Источник истины

| Режим | Кто ведёт день | Награды | Интерфейс |
|---|---|---|---|
| `local` (все сегодня) | Устройство (GameStore, без изменений) | На устройстве, как раньше | Без изменений |
| `migration_pending` | Устройство | **Нигде**: любое изменение с наградой (XP, уровень, Coins, достижение, новое «выполнено», оплаченный личный квест) отклоняется целиком | Плашка «Прогресс переносится в облако…»; «Проверить» — «начисления приостановлены» |
| `cloud_active` + `game_sync` выкл. | **Сервер** | Нигде (пауза) | «Игровой день ведёт сервер. Серверные начисления сейчас приостановлены» |
| `cloud_active` + `game_sync` вкл. | **Сервер** | Только сервер: пока выплаты выключены, ответ «серверные начисления ещё не включены» | «…Начисления наград на сервере ещё не включены» |

- **Только вперёд.** Режим хранится в пространстве аккаунта на устройстве (`ayra_economy_mode`). Устройство, однажды увидевшее `migration_pending` или `cloud_active`, не возвращается к `local` — ни при ошибке, ни офлайн, ни при выключенном переключателе (тесты unit и e2e).
- **Для `cloud_active`:**
  - приложение не строит свой день: открытие, режим, принятие, «не сегодня» и замена идут на сервер;
  - ответ сервера копируется на устройство (`lib/server-day-mirror.ts`): набор, режим, принятые, отложенные, замены;
  - **XP, Coins и уровень не копируются** — они придут из серверной проекции при переносе (Q4.5);
  - день устройства никогда не уходит назад.
- **Обрыв сети:** действие не применяется, плашка «Нет связи с сервером…», повтор работает (принятие идемпотентно).
- **Две вкладки и два устройства:** сервер обслуживает их по очереди (блокировка 0015), а вкладка получает день сервера при открытии, фокусе и после каждого действия.

## 4. Первый серверный след записи Журнала (0016)

- **`first_seen_at`** на `journal_trades`, `journal_day_plans`, `journal_week_plans`, `journal_notes`, `journal_no_trades`.
- Ставится триггером при **первой** вставке строки — **временем сервера**; переданное значение заменяется.
- При любом обновлении (новая версия, повтор синхронизации, отметка удаления, импорт, старая версия) **не меняется**. Подменить его не может никто:
  - у клиента нет права на столбец;
  - у владельца тоже нет;
  - триггер всё равно восстанавливает значение.
- **Строки, существовавшие до 0016, — `NULL` («неизвестно»):** они никогда не считаются «сделанными сегодня» на сервере.
- **Импортированная запись** получает свой след, как любая. В миссиях она не участвует (`importBatchId`).
- **Конкурентно:** 10 устройств создают одну заметку одновременно → одна строка, один след; 5 параллельных обновлений (даже с попыткой задать след) его не сдвигают (PG-J1).

## 5. Защита наград: полная серверная проверка миссии

`POST /api/game/missions/verify` проходит всю цепочку будущего начисления:
1. **Серверный день:**
   - аккаунт `cloud_active`;
   - день открыт;
   - миссия в наборе режима, принята, не оплачена;
   - день не заполнен;
   - `game_sync` включён.
2. **Записи Журнала так, как их хранит Postgres** (`game_journal_for_check`):
   - версия `client_updated_at`;
   - отпечаток `md5(data::text)` — **тот же, что сравнивает `game_apply_reward`**;
   - первый след.
3. **Правила миссии приложения** (`lib/missions.ts`) на **дне сервера:** содержание, обязательные поля, свой текст без заготовок, копии, импорт, удаление, тип записи.
4. **Серверные проверки:**
   - отметка дня записи не позже, чем сервер её получил;
   - запись, засчитываемая созданием (заметка, план, сделанный сегодня, план на завтра), **впервые появилась на сервере в этот день**;
   - запись, засчитываемая обновлением (разбор сделки, разбор дня, подтверждение плана), **сохранена на сервере в этот день**.
5. Только при `AYRA_SERVER_MISSION_PAYOUTS=1` (не задан) — `game_apply_reward` с **точно этими** версией и отпечатком. Функция перепроверяет их под блокировкой строки; занятая запись — пробуется следующая.

**Пока выплаты выключены**, ответ — `{ paid: false, confirmed: true, reason: "payout_disabled" }` после полной проверки. Даже если включить переключатель маршрута, база откажет: вид `mission` выключен (`kind_disabled` → тот же ответ).

**Согласованность с `game_apply_reward` проверена на настоящем PostgreSQL** (PG-J2): версия и отпечаток из `game_journal_for_check` принимаются начислением, любой другой отпечаток отклоняется (`game_evidence_changed`).

## 7. Известные ограничения перед Q4.5

1. **Перенос прогресса** (Q4.5): XP, Coins, уровень и история из устройства в серверный журнал начислений, проекция на экране для `cloud_active`, переход `local → migration_pending → cloud_active`. Пока для `cloud_active` устройство показывает свои прежние XP и Coins и не меняет их.
2. **Включение выплат миссий:** нужны ваше решение, `AYRA_SERVER_MISSION_PAYOUTS=1` и включение вида `mission` в базе — после Q4.5.
3. **Дополнительные задания (self-report) и остальные награды** (ежедневная, первые действия, XP Журнала, личные квесты, достижения) на сервере не начисляются. Для `cloud_active` они приостановлены, пока у каждого не будет серверной проверки (Q4.6–Q4.7).
4. **Неделя (QH-7) и личные квесты (QH-8)** для `cloud_active` остаются на устройстве: без наград (их выплаты приостановлены), но и без серверной истины.
5. **Лимит частоты** — в памяти экземпляра сервера. Для оплачивающего маршрута нужен общий лимит в Postgres.
6. **Разные часовые пояса на устройстве и в профиле:** серверный день по поясу профиля; устройство не уходит назад, поэтому возможен день устройства «впереди» сервера до следующего открытия.
7. **Плашка** есть на странице заданий. На других экранах (Главная, Журнал) отказ в награде виден только как «не начислено».

## 8. Плейсхолдеры

- 60 запросов в минуту на аккаунт;
- тело до 2 КБ (проверка миссии — до 512 Б);
- до 5000 строк Журнала для проверки;
- ожидание ответа 10 с.
