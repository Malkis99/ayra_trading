# Q4.7 — follow-up: обход суточной паузы при смене возрастной группы

Статус: **зафиксировано, не исправлено.** Исправлять только после отдельного review владельца. Найдено при аудите SECURITY DEFINER-функций на пилоте (2026-11-25, только чтение).

## 1. Что найдено

- В базе есть функция `public.set_age_group(new_group)` (0001). Она проверяет вход, допустимые значения, **суточную паузу** при переходе на 18+ (по последней записи `age_group_changed` в `audit_log`) и пишет новую запись в журнал.
- Но у роли `authenticated` есть **прямое право** `UPDATE (age_group, …)` на `public.profiles`, а политика `profiles_update_own` разрешает менять свою строку.
- Приложение само меняет возраст **прямым UPDATE** при онбординге (`lib/auth/routing.ts`: `updates.age_group = answers.ageRange`). `set_age_group` приложение не вызывает.
- Триггеры на `profiles`: `tr_profiles_minor_mode` пересчитывает `minor_mode` из `age_group`, есть пауза для ника и `updated_at`. **Триггера, который проверял бы смену возраста, нет.**

**Итог:** пользователь может в любой момент сменить `16-17` на `18-24` одним UPDATE своей строки, без паузы и без записи в журнал. Пауза из `set_age_group` обходится.

Чего **нет**:
- изменить чужую строку нельзя (RLS: `auth.uid() = id`);
- выставить `minor_mode` напрямую нельзя (нет права на колонку, его считает триггер);
- повышения прав в базе нет.

## 2. Последствия для ограничений 16–17 (Pack, раздел 15.3, D-24)

Сейчас `minor_mode` используется **только на клиенте**: фильтры вариантов в Awakening (`lib/awakening.ts`, `lib/awakening-rules.ts`) и игра (`lib/game-context.tsx`). Серверных функций, закрытых для 16–17, пока нет: Connected/Verified, партнёрских предложений, платных подписок, личных сообщений.

- **Сегодня:** риск низкий. Ограничения существуют только в интерфейсе, а возраст и так указывает сам человек.
- **Когда появятся серверные ограничения 16–17:** обход станет существенным. Несовершеннолетний мгновенно станет «взрослым» и получит доступ к закрытому, а в журнале не останется следа смены.

Ограничение любой схемы: возраст указывает сам человек, так что пауза лишь затрудняет переключение, а не проверяет возраст. Как проверять возраст, решает владелец; это вопрос продукта и права (Pack 15.3: «проверить»).

## 3. Предложение (не реализовано)

**Рекомендуется:** правило в базе, которое срабатывает при любом способе записи, как пауза для ника (0003).

1. Триггер `BEFORE UPDATE OF age_group ON public.profiles` (SECURITY DEFINER, `search_path = public`):
   - первый выбор (`OLD.age_group IS NULL`) — без паузы, это онбординг;
   - переход `16-17` → 18+ — только если последняя запись `age_group_changed` старше паузы; иначе отказ `age_group_change_cooldown`;
   - каждая смена записывается в `audit_log` в той же транзакции.
2. `set_age_group` либо удалить, либо оставить тонкой обёрткой над тем же правилом, чтобы не было двух реализаций.
3. Тесты:
   - SQL: первый выбор, повтор в пределах паузы, после паузы, другой аккаунт, прямой UPDATE и RPC дают одинаковый результат;
   - e2e: онбординг не ломается.
4. Отдельная миграция; применяется к пилоту, затем к Production — только с разрешения владельца.

**Альтернатива:** отозвать `UPDATE (age_group)` у `authenticated` и перевести онбординг на RPC. Это хуже: правило держится на том, что все пути записи идут через RPC, а не на самой таблице.
