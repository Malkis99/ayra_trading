# Q4.7-Б2 — Чем доказывается достижение

Основа: `main` `effce56` (после merge #223). Блокер Б2 из `docs/q4-7-owner-decisions-launch-blockers.md`.

**Решения владельца, которые здесь выполняются:**
- **`stylist`:** `verified` только при независимом доказательстве исторического условия. Клиентского флага и даты регистрации недостаточно.
- **`firstTrade`:** `verified` только при доказательстве исходного `q_tradelog`, любая сделка в Журнале не годится.
- **Остальные достижения:** сверить с историческими условиями, добавить отрицательные тесты.
- **Недоказанное:** `pending_review`.
- **Ручное принятие:** `legacy_accepted`.

Новая миграция — `supabase/migrations/0021_game_achievement_proof.sql` (+ откат). 0020 не меняется, 0021 переопределяет только функцию плана и каталог. Ни одна миграция никуда не применялась.

## 1. Условие на устройстве и доказательство на сервере

По каждому достижению я прочитал код, который его открывает, и проследил историю этого кода в git.

| id | Условие на устройстве (код и история) | Что принимала 0020 | Что принимает 0021 |
|---|---|---|---|
| `firstQuest` | в истории есть квест (`checkAchievements`) | событие квеста в сверке | без изменений — совпадает |
| `streakDay` | 3 разных квеста за игровой день | ≥ 3 события квестов одного дня | без изменений — совпадает (день берётся из записи устройства) |
| `level3` | уровень 3 | уровень подтверждённого XP → verified; с принятым остатком → legacy_accepted | без изменений |
| `firstTrade` | в истории есть квест `q_tradelog` | этот квест, **или** награда `first:trade`, **или** любая строка `journal_trades` | **только квест `q_tradelog`**. `first:trade` — отдельная награда за первую записанную сделку, а сделка в Журнале может быть записана или импортирована без квеста |
| `consciousRefusal` | записан день без сделок (`recordNoTradeEntry` открывает его всегда) | `first:noTrade` или строка `journal_no_trades` | без изменений — совпадает: обе записи создаёт то же действие человека, импорт таких записей не создаёт |
| `firstNote` | новая заметка в форме заметки (`recordNoteSaved` открывает его всегда) | `first:note` или **любая** строка `journal_notes` | `first:note` или заметка, которую **написал человек**: не импортированная из файла (`importBatchId`) и не результат бэктеста (форма бэктеста достижение не открывает) |
| `firstPlan`, `firstReview`, `plans7` | проверяются только по списку планов. Приложение **ни разу не передало этот список** (с T6c-2a, `e0f0521`): `checkAndClosePlanQuests(plan, trades)` | строки `journal_day_plans`, `first:dayPlan` | **`pending_review`**: приложение не могло их открыть, совпадения с условием нет |
| `firstPropRules` | `recordPropRulesSaved` открывает его, но экран Журнала **выбрасывает новое состояние** (с T6d, `08fd336`): достижение только показывается, не сохраняется | строка `journal_accounts` с `propRules` | **`pending_review`**. Кроме того, у владельца экономики нет права читать `journal_accounts`: в 0020 такая заявка **обрывала всю активацию** (`permission denied`) |
| `firstScreenshot` | скриншот, прошедший проверки награды (`rewardedScreenshotHashes`) | награда `first:screenshot` | **`pending_review`**: `first:screenshot` дают за любое первое вложение, а засчитанный скриншот сервер не видит |
| `stylist` | надето хотя бы одно: `itemsEquippedCount ≥ 1` или есть слот снаряжения | `verified` у всех по правилу «у каждого стартовый комплект» | **`verified` только по записи снаряжения** в **принятом** снимке: в слоте лежит настоящий предмет гардероба именно для этого слота (каталог `lib/items.ts`, id и слоты не менялись с T4). Иначе — `pending_review` |
| `author`, `propDisciplined5`, трофеи недель | только на устройстве | `pending_review` | без изменений |
| `category:<id>` | лучший ранг «Моего пути» | оплаченный личный квест в сверке | без изменений |

**Почему для `stylist` не годятся флаг, счётчик и дата:**
- флаг — это сама заявка;
- `itemsEquippedCount` — тоже число с устройства, без записи о предмете;
- дата регистрации ничего не доказывает. Более того, стартовый комплект появился только в T4.1 (2026-10-06), в T3 снаряжение было пустым.

**Запись о снаряжении не принимается**, если:
- предмет не из своего слота (рубашка в слоте обуви);
- такого id не было в каталоге;
- id — строка, дробь, отрицательное или огромное число, объект или `null`;
- такого слота в игре не было;
- снаряжение пришло массивом;
- снимок поздний.

Огромное число не ломает запрос: id приводится к числу только после проверки, что это не больше двух цифр.

## 2. Что не меняется

- **XP и Coins.** Достижения их никогда не давали, тест P4 проверяет, что журнал наград не меняется ни при активации, ни при решении человека.
- **Записанные строки** не переписываются: у них остаётся `rules_version = 'q4.6'`. Новые получают `q4.7`.
- **Решение человека:** `game_mig_decide_achievement` → `legacy_accepted` с причиной и записью в журнал. `verified` руками не меняется.
- **Клиент, API, экономические флаги, Market, Production.**

## 3. Тесты

**Новый файл `supabase/tests/game_achievement_proof.sql`:**
- **P0** — каталог называет доказательство каждого достижения.
- **P1** — у аккаунта есть всё, что принимала 0020: сделка, 7 планов с разбором, правила проп-счёта, награды за первую сделку, первый план и первое вложение. Заметки только импортированные и из бэктеста, счётчик надетого есть, снаряжения нет. Итог: **ничего не `verified`**, ни у одного пункта нет «доказательства».
- **P2** — условие устройства выполнено: квест `q_tradelog`, надетые рубашка и брюки, заметка, написанная человеком → `verified` с точным доказательством.
- **P3** — 9 видов неверного снаряжения, снаряжение массивом, настоящий предмет только в позднем снимке → `stylist` не доказан.
- **P4** — активация:
  - строки записаны по правилам `q4.7`, `stylist` с источником `snapshot_record`;
  - человек принимает `firstPlan` → `legacy_accepted` с записью в журнал;
  - `verified` руками не меняется;
  - журнал наград: 1 строка / 40 XP / 10 Coins до и после.

**Изменённые проверки (стали строже, не слабее):**
- `game_achievements.sql` AC2 учитывает версию правил. С 0021 `firstPlan` и `stylist` ждут проверки, без 0021 ожидания прежние.
- `test-migration-admin.sh` T13a:
  - `firstTrade`, у которого есть только награда первого действия, теперь ждёт проверки — это отрицательный тест;
  - проверка «доказанное руками не меняется» перенесена на `firstQuest`.

**Добавлено в сценарии:**
- `test-migrations.mjs`, блок U:
  - 0021 применяется дважды;
  - тесты 0021, 0020, 0019 и 0018 проходят с 0021;
  - функция плана доступна только инструменту владельца;
  - откат отказывает, если есть строки по правилам `q4.7`;
  - откат возвращает 0020, и её тесты снова проходят с прежними ожиданиями.
- `test-concurrency.sh`:
  - N0 — 0021 на настоящем PostgreSQL, дважды;
  - N1 — 5 одновременных активаций: каждое достижение записано один раз и по правилам `q4.7`.

**Мутационная проверка** (тесты P1–P4 без P0 на базе с правилами 0020): **падают все четыре**.
- P1 — `permission denied for table journal_accounts`, это ошибка 0020, описанная выше;
- P2 — `stylist=verified/game_rule`;
- P3 — `stylist` verified при неверном снаряжении;
- P4 — `stylist=verified/game_rule`, правила `q4.6`.

С 0021 все четыре проходят.

## 4. Найдено по ходу (не исправлялось, нужно решение)

1. **`firstPlan`, `firstReview`, `plans7` на устройстве не открываются вообще:** приложение не передаёт список планов в проверку достижений. Это ошибка игры с T6c-2a.
2. **`firstPropRules` показывается, но не сохраняется** на устройстве. Это ошибка экрана Журнала с T6d.

Исправление этих двух мест меняет поведение игры на устройстве, поэтому это отдельная задача и решение владельца. Для переноса это значит: если такие достижения окажутся на устройстве, их примет только человек (Б3).
