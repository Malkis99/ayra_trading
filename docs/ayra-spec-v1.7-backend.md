# AYRA Trading — Spec v1.7: Схема базы данных, правила доступа (RLS) и серверная архитектура

Документ описывает реализацию T7a (база данных, RLS, вход по почте) и T7a.1 (порядок экранов, ошибки, защита от неверного адреса сайта).

---

## 1. Схема базы данных (Database Schema)

### 1.1 `public.profiles`
Таблица профилей пользователей, связанная 1:1 с `auth.users`.

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | UUID | PK, REFS `auth.users(id)` ON DELETE CASCADE | Уникальный идентификатор пользователя |
| `nickname` | TEXT | UNIQUE, CHECK `^[A-Za-z0-9_.-]{3,24}$` | Отображаемое имя (уникальное регистронезависимо через индекс `LOWER(nickname)`) |
| `locale` | TEXT | NOT NULL, DEFAULT 'ru', CHECK `IN ('ru', 'en')` | Предпочитаемый язык интерфейса |
| `timezone` | TEXT | NOT NULL, DEFAULT 'UTC' | Часовой пояс пользователя |
| `age_group` | TEXT | CHECK `IN ('16-17', '18-24', '25-34', '35+')` | Возрастная категория |
| `minor_mode` | BOOLEAN | NOT NULL, DEFAULT FALSE | Вычисляется автоматически триггером `tr_profiles_minor_mode` из `age_group` |
| `consent_at` | TIMESTAMPTZ | NULLABLE | Дата и время принятия Условий и Политики конфиденциальности |
| `consent_version` | TEXT | NULLABLE | Версия принятого юридического документа (напр. '1.0-draft') |
| `created_at` | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | Дата создания профиля |
| `updated_at` | TIMESTAMPTZ | NOT NULL, DEFAULT `now()` | Обновляется триггером `tr_profiles_updated_at` |

### 1.2 `public.audit_log`
Журнал аудит-событий безопасности.

| Колонка | Тип | Описание |
|---|---|---|
| `id` | UUID | PK, DEFAULT `gen_random_uuid()` |
| `user_id` | UUID | REFS `auth.users(id)` ON DELETE CASCADE |
| `event` | TEXT | Название события (напр. 'age_group_changed') |
| `meta` | JSONB | Дополнительные данные события |
| `created_at` | TIMESTAMPTZ | Время записи события |

### 1.3 Резервные таблицы T7c (Заблокированы RLS по умолчанию)
- `public.telegram_identities`: (`user_id` UUID PK, `telegram_id` BIGINT UNIQUE, `linked_at` TIMESTAMPTZ).
- `public.link_tokens`: (`token_hash` TEXT PK, `user_id` UUID, `expires_at` TIMESTAMPTZ, `used_at` TIMESTAMPTZ).

## 2. Таблица политик доступа (RLS Matrix)

Row Level Security включён на всех таблицах. Права на `public.profiles` ограничены на уровне колонок для роли `authenticated`.

| Таблица | Роль | Разрешённые операции | Условие RLS / Ограничения колонок |
|---|---|---|---|
| `profiles` | `anon` | None (запрещено) | Доступ полностью закрыт |
| `profiles` | `authenticated` | `SELECT` | `auth.uid() = id` (только собственная строка) |
| `profiles` | `authenticated` | `UPDATE` | `auth.uid() = id`. Разрешены только колонки: `nickname`, `locale`, `timezone`, `age_group`, `consent_at`, `consent_version`. Изменение `minor_mode`, `id`, `created_at` клиентом напрямую запрещено! |
| `profiles` | `authenticated` | `INSERT` / `DELETE` | Запрещено клиенту (создаётся триггером `handle_new_user`, удаляется CASCADE) |
| `audit_log` | `anon` / `authenticated` | None | Вставка выполняется только из `SECURITY DEFINER` функций (RPC `set_age_group`) |
| `telegram_identities` | `anon` / `authenticated` | None | Политики отсутствуют (доступ закрыт, используется только сервером) |
| `link_tokens` | `anon` / `authenticated` | None | Политики отсутствуют (доступ закрыт, используется только сервером) |

## 4. Инструкция по настройке для владельца (Setup Guide)

1. **Создание проекта в Supabase:**
   - Зарегистрируйте проект на [supabase.com](https://supabase.com).
   - Скопируйте **Project URL** и **anon / public key**.

2. **Настройка переменных окружения в Vercel / Vercel Preview:**
   - Добавьте `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` и `NEXT_PUBLIC_SITE_URL` в переменные окружения Vercel.

3. **Настройка Email Провайдера и Шаблона писем:**
   - В Supabase Dashboard перейдите в **Authentication** -> **Email Templates**.
   - Скопируйте содержимое файла `supabase/email-templates/otp.html` и вставьте его в шаблон Magic Link / OTP.

4. **Применение миграции и проверка RLS:**
   - В Supabase Dashboard откройте **SQL Editor**.
   - Выполните скрипт из файла `supabase/migrations/0001_init.sql`.
   - Выполните тестовый скрипт из `supabase/tests/rls.sql` для проверки правильности изоляции данных.

## 5. Что делать, если вход не работает (Troubleshooting)

| Симптом | Возможная причина | Что проверить |
|---|---|---|
| Письмо с кодом не приходит | Достигнут лимит отправки писем (Rate limit) или не настроен SMTP-провайдер в Supabase | 1. Подождать 60 секунд.<br>2. В Supabase Dashboard -> Authentication -> Rate Limits / Provider settings.<br>3. Проверить папку Спам. |
| Ошибка «Неверный или просроченный код» | Код был введён с ошибкой или истёк срок жизни OTP (обычно 5–15 мин) | 1. Проверить правильность 6–8 цифр.<br>2. Запросить код повторно по кнопке.<br>3. Убедиться, что ссылка из письма открывается в том же браузере. |

| Плашка «Ты на тестовом адресе» на `/login` | `location.origin` отличается от `NEXT_PUBLIC_SITE_URL` | 1. Для авторизации перейдите по ссылке на основной адрес.<br>2. Проверить значение `NEXT_PUBLIC_SITE_URL` в `.env.local`. |

## 6. Модель угроз и ограничения (Threat Model & Limitations)

1. **Клиентская авторитетность наград в T7a:**
   - На этапе T7a расчет XP, Coins и наград выполняется на клиенте для сохранения работоспособности локального гостевого режима.
   - **Ограничение:** Продвинутый пользователь может изменить локальное состояние в браузерном хранилище. Серверная авторитетность с ledger-журналом начислений и валидацией будет внедрена на этапе E1 (перед экономикой с реальной ценностью).

2. **Защита от перебора никнеймов:**
   - Запросы к RPC `is_nickname_available` выполняются с клиентским дебаунсом (debounce 300ms). В будущем на сервере будет добавлен rate limiting.

3. **Защита от Open Redirect:**
   - Параметр `next` при обработке `/auth/callback` и `/login` строго строгифицируется и проверяется функцией `sanitizeRedirectUrl`. Все внешние ссылки (напр. `http://`, `//`) отвергаются с возвратом на `/`.

## 7. Многовкладочный вход и защита /awakening (T7a.3)

### 7.1 Поток входа и функция `resolvePostLoginRoute()`
Единая функция `resolvePostLoginRoute()` определяет целевой маршрут пользователя после авторизации:
1. **Профиль с никнеймом:** Если в облачном профиле пользователя уже задан никнейм, выполняется переход на главную страницу (`/`) или указанный безопасный параметр `next`. Локальный никнейм устройства никогда не перезаписывает существующий никнейм профиля.
2. **Новый аккаунт без никнейма (Завершённый онбординг):** Если локальное знакомство гостя пройдено (`status === 'done'`), никнейм проходит валидацию (латиница `^[A-Za-z0-9_.-]{3,24}$`) и свободен по RPC `is_nickname_available`, никнейм автоматически сохраняется в профиль вместе с настройками (`locale`, `timezone`, `age_group`), а пользователь направляется на главную страницу.
3. **Конфликт никнейма:** Если никнейм уже занят или возникла ошибка записи, пользователь направляется на экран выбора нового ника (`/awakening?mode=conflict`).
4. **Незавершённое знакомство:** Если локальное знакомство не завершено (`status === 'inProgress'` / `'none'`), автоматическое сохранение никнейма не выполняется, и пользователь направляется на `/awakening` для прохождения знакомства с сохранённого шага.

### 7.2 Согласование вкладок (Cross-Tab Coordination Protocol)
Взаимодействие между вкладками осуществляется через `BroadcastChannel('ayra-auth')` с резервным каналом через события `storage` (`ayra_auth_event` в `localStorage`):
- **Сигнал `AUTH_SIGNED_IN`:** Отправляется вкладкой, завершившей вход.
- **Поведение вкладки на `/login`:** Если вкладка находится на `/login` и получает сигнал о входе из другой вкладки, она **не выполняет автоматический редирект**, а показывает карточку *«Вход выполнен в другой вкладке. Продолжай там.»* с кнопкой *«Продолжить здесь»* (`aria-live="polite"`, автофокус на кнопке).
- **Кнопка «Продолжить здесь»:** При нажатии вкладка запрашивает статус через `resolvePostLoginRoute()`, выполняет переход и транслирует сигнал `AUTH_CLAIMED`. Если входная вкладка была закрыта, кнопка продолжает корректно работать.

### 7.3 Защита `/awakening` от двух вкладок (Lease & Versioning)
Запись ответов в процессе знакомства на `/awakening` разрешена только одной активной вкладке через механизм аренды (Lease Manager):
- **Ключ аренды:** `ayra_awakening_lease` в `localStorage` хранит `{ ownerTabId, timestamp }`.
- **Обновление и TTL:** Владелец аренды обновляет метку времени каждые 5 секунд (heartbeat). Срок жизни аренды — 15 секунд. По истечении TTL аренда считаются свободной.
- **Только для чтения (Read-Only Mode):** Вторая вкладка переходит в режим только для чтения:
  - Все формы ввода, варианты ответов и навигационные кнопки блокируются (`disabled`, `aria-disabled="true"`).
  - Кнопка «Выйти» остается доступной.
  - Вверху отображается плашка *«Знакомство открыто в другой вкладке»* с кнопкой *«Продолжить здесь»*.
- **Перехват аренды и Версионирование:** При нажатии «Продолжить здесь» вкладка забирает аренду (`stealLease`). Перед записью ответов состояние перечитывается из хранилища (`localStorage`), а счетчик версий предотвращает затирание данных. Награда за прохождение знакомства остаётся идемпотентной.

## 8. Активное пространство и защита записей (T7a-B2 Active Space & Write Guarding)

### 8.1 Идентификация и переключение активного пространства (T7a-B3)
- **Единый источник истины (AuthState):** Состояние авторизации отслеживается через единый узел `AuthState` (`loading | guest | authenticated`). `ActiveSpace` вычисляется строго из `AuthState`: `"guest"` для незарегистрированного пользователя/гостя и `"account:<userId>"` для вошедшего.
- **Нейтральный скелетон во время загрузки:** В состоянии `loading` макет Shell отображает нейтральный скелетон без отображения персонажа или данных гостя/аккаунта.
- **Таймаут определения сессии (~1.5с):** Если по истечении ~1.5с состояние остаётся `loading`, отображается плашка «Проверяем вход…» с явной кнопкой «Продолжить без входа» (переход в `guest` только по кнопке). Автоматического сброса в данные гостя по таймауту нет.
- **Единый вызов `resolvePostLoginRoute()`:** При переходе `loading → authenticated` выполняется однократный вызов `resolvePostLoginRoute()`, гарантирующий отправку новых аккаунтов без данных на `/awakening`.
- **Блок диагностики владельца:** В Настройках (`Settings -> Аккаунт`) и на экране ожидания входа доступен свёрнутый блок «Диагностика» с состоянием `AuthState`, типом пространства, `onboarding.status`, причиной маршрута и кнопкой «Скопировать» без ПД и токенов.
- **Сброс памяти и кэшей при смене пространства:** При смене пространства (вход, выход, переключение) все провайдеры (`GameProvider`, `JournalProvider`, репозиторий вложений) сбрасывают внутренние состояния, таймеры, формы и загружают данные нового пространства.
- **Возврат гостя при выходе:** Выход из аккаунта переключает пространство на `"guest"`. Данные аккаунта остаются изолированными в локальном хранилище устройства под ключами `ayra:<userId>:...`.

### 8.2 Привязка операций и защита от устаревших записей (Write Guard)
- **Операция привязывается к пространству (boundSpaceId):** Любая запись в хранилище (включая асинхронные, IndexedDB, debounced автосохранения и flush) проверяет совпадение `boundSpaceId` с текущим активным пространством через `AppStorage.isWriteAllowed(boundSpaceId)`.
- **Отбрасывание устаревших записей:** Если активное пространство изменилось до завершения записи, операция отменяется с выводом предупреждения в консоль (без утечки ПД).

### 8.3 Принудительный сброс (Flush) и защита «грязных» форм
- **Принудительный Flush перед переключением:** Перед сменой пространства вызывается `AppStorage.flushSpace(spaceId)`, сохраняющий все неотправленные изменения старого пространства.
- **Согласование вкладок через BroadcastChannel('ayra-space'):**
  - При смене пространства вкладка транслирует сигнал `SPACE_CHANGED`.
  - Соседняя вкладка без несохраненных данных переключает пространство автоматически.
  - Если в соседней вкладке есть несохранённый ввод («грязная» форма), переключение откладывается и показывается плашка *«Аккаунт изменён в другой вкладке»* с кнопкой *«Обновить»*.
  - При нажатии *«Обновить»* происходит Flush несохраненной формы в старое пространство, а при ошибке выводится диалог *«Не удалось сохранить данные»* с возможностью скопировать текст.

## 10. Перенос гостевого профиля (C1, `/profile-select`)

### 10.1 Правило нового аккаунта (исправление входа по ссылке из письма)
Новый аккаунт — это аккаунт, у которого в **его собственном** пространстве (`ayra:<userId>:*`) нет завершённого знакомства. Такой аккаунт **всегда** идёт на `/awakening`, независимо от гостевых данных на устройстве:
- маршрут после входа читает только пространство аккаунта (`readAccountGameState`), никогда гостевое;
- Shell не принимает решений, пока хранилище и провайдеры не переключены на пространство аккаунта (`isSpaceReady`); страницы `/awakening` и `/profile-select` до этого не рендерятся;
- гостевой ник никогда не записывается в облачный профиль автоматически;
- провайдер игры помнит, из какого пространства загружено состояние, и не пишет его в другое пространство (ни при сохранении, ни при flush).

**Единый маршрутизатор после входа — `/auth/continue`.** Это единственное место, где решается «куда после входа»:
- `/auth/callback` только обменивает код на сессию и всегда перенаправляет на `/auth/continue?next=…`; ссылка вида `/?code=…` (запасной Site URL) middleware отправляет на `/auth/callback`;
- на `/login` ввод кода и кнопка «Продолжить здесь» ведут на тот же `/auth/continue`;
- `/auth/continue` ждёт `AuthState = authenticated`, переключения хранилища на пространство аккаунта и загрузки облачного профиля, затем один раз вызывает `resolvePostLoginRoute`. Если профиль не загрузился — 3 автоматических повтора, затем экран «Не удалось загрузить профиль» с кнопкой «Повторить» (главная не показывается);
- у аккаунта нет ника в облачном профиле (знакомство не завершено) → `/awakening`, независимо от гостевых данных и от `next`;
- Shell: вошедший пользователь, у которого профиль не загружен или нет ника, не видит страниц приложения (в том числе главную) — вместо них лоадер и переход на `/auth/continue`; исключения: `/awakening`, `/profile-select`, страницы входа и юридические.
- строка `profiles` создаётся только сервером (триггер `on_auth_user_created`); клиент читает её через `maybeSingle()`: нет строки → это новый аккаунт → `/awakening` (не ошибка). Ошибкой считаются только сбои сети/сервера (статус и код видны в диагностике под флагом `ayra_auth_debug`). Если строки нет и после знакомства — экран «Профиль не найден на сервере» (сохранить ник некуда), без цикла переходов. Проверка миграции: `supabase/checks/0001_status.sql`.

### 10.2 Когда предлагается перенос
Экран `/profile-select` показывается **после** знакомства аккаунта (последний шаг `/awakening`), если:
1. в гостевом пространстве есть реальные данные;
2. у аккаунта ещё нет своего прогресса (уровень 1, нет XP/Coins, нет сделок, счетов и заметок);
3. выбор ещё не записан (`ayra_profile_choice`).

Позже перенос доступен по выбору пользователя: Настройки → «Данные на этом устройстве» → «Скопировать в аккаунт» (пока у аккаунта нет прогресса).

### 10.3 Варианты
- **«Перенести данные гостя»** — прогресс, журнал и скриншоты гостя копируются в аккаунт; ник, ответы знакомства и внешность остаются аккаунта; облачный ник не меняется. Гостевые данные не трогаются.
- **«Не переносить»** — записывает выбор `fresh`.
- **«Решить позже»** — переход на главную без записи выбора.

Смена пространства в той же вкладке: `spaceTabChannel.notifyLocal()` вызывается при входе/выходе, после копирования и при переключении из другой вкладки (`SpaceChangeBanner`).

### 10.4 Настройки: «Данные на этом устройстве» (C2)
Карточка в `/settings` показывает профиль гостя (ник, уровень, число сделок) и действия:
- **«Экспортировать»** — JSON-файл `ayra-guest-ГГГГ-ММ-ДД.json` с гостевыми ключами `ayra_*`. Скриншоты (двоичные файлы) в файл не входят — указывается только их количество.
- **«Скопировать в аккаунт»** — только для вошедшего пользователя и только если пространство аккаунта на устройстве пустое. Облачный ник имеет приоритет над гостевым.
- **«Удалить данные гостя»** — только для вошедшего пользователя (пока активен аккаунт, гостевые данные не держатся в памяти). Подтверждение вводом `УДАЛИТЬ` / `DELETE`. Удаляются только гостевые ключи `ayra_*` и скриншоты гостя; ключи устройства и сессия входа не трогаются.
- **«Выйти и удалить данные аккаунта с этого устройства»** — подтверждение вводом `ВЫЙТИ` / `LOGOUT`. Сначала выход, затем удаление ключей `ayra:<userId>:*` и скриншотов аккаунта. Облачный профиль не меняется. До T7b журнал аккаунта хранится только на устройстве — диалог предупреждает об этом.

Автоматического удаления данных нет. Хранилище скриншотов очищается, а не удаляется, чтобы не ломать открытые соединения IndexedDB.

### 10.5 Тест входа по ссылке из письма (настоящий PKCE-поток)
`npx playwright test --config playwright.supabase.config.ts` поднимает локальный фейковый Supabase (`e2e/fake-supabase/server.mjs`: GoTrue `/otp`, `/token?grant_type=pkce` с проверкой S256, `/user`; PostgREST `profiles` и RPC), собирает production-сборку в `.next-e2e-supabase` и проверяет: гость с данными + вход нового аккаунта по ссылке в новой вкладке (через `/auth/callback?code=` и через `/?code=`) → `/awakening`, облачный ник пуст, гостевые данные не попали в аккаунт.

Диагностика входа (только чтение, без email и токенов): `NEXT_PUBLIC_AYRA_AUTH_DEBUG=1` при сборке или `window.__AYRA_AUTH_DEBUG__ = true` в консоли → строки `[AYRA:auth] …`.
