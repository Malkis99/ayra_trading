# Стабильные события и пересмотры календаря

Этап после #149. Ветка `fix/calendar-event-integrity`, база main `38e840a316ee13be22c4a96f104c2bcd5a12474c`.
Production, cron, частота upstream-запросов, платные сервисы и зависимости не менялись.

## Что исправлено

- Ключ идентичности отделён от времени публикации. В нём источник, регион, показатель,
  официальный UID (если дан) либо отчётный период, стадия. Период/стадия дополнительно проверяются
  при записи: повторно использованный UID не разрешает незаметно сменить период.
- BEA ICS использует UID, SEQUENCE, LAST-MODIFIED и STATUS, включая отмену без DTSTART.
  DTSTAMP не выдаётся за версию содержимого. Из нескольких версий выбирается новая, не последняя в файле.
- Изменения принимаются атомарно в Postgres под общей транзакционной блокировкой календарных записей.
  Перенос меняет starts_at существующей строки; ID, hidden, значения и связи с новостями сохраняются.
  Разные стадии/UID при совпадении даты могут иметь отдельный ID с хешем, не затирая старый ID.
- Исчезновение события из файла ничего не отменяет. Восстановление после отмены требует более новой
  подтверждённой версии; опубликованные цифры остаются на месте.
- Расписания без машинного фида остаются ручными. Для переноса сохранять исходную запись и добавлять
  проверенную поправку в `listed-corrections.ts`: исходный ID, новый UTC starts_at, возрастающий sequence,
  ссылка на официальный перенос. Не переносить недельный reference period вместе с датой релиза.
  Sequence здесь — версия проверенной ручной записи, не выдуманный SEQUENCE ведомства.
- Повторная выдача того же результата не создаёт дубль. Более старый ответ, другие единицы/сезонность/
  период или конфликт без достоверной свежести не заменяют подтверждённые значения.
  Наличие нового source_updated сравнивается с сохранённым, время скачивания не считается доказательством.
  Отсутствие новой версии в совпадающем ответе не стирает уже сохранённую версию.
- Null не превращается в ноль и не затирает actual/previous. BLS требует соседние календарные месяцы,
  EIA — соседние недели. Census использует свой точный reference month. DOL читает неделю из текста
  публикации; её явный revised previous может обновить actual предыдущей недели.
- BEA проверяет infoDate факта и предыдущего периода. Вторая оценка квартала не становится «Пред.»
  третьей оценки того же квартала. Неподтверждённое значение прошлого периода не подставляется.
- Ошибки чтения БД до запуска source-job тоже изолированы: один источник не останавливает остальные.
- При монтировании календаря и возвращении во вкладку браузер перечитывает только AYRA Supabase.
  Нет polling, upstream-запросов браузера и сброса фильтров. Дубли focus/visibility и параллельное чтение
  объединяются; ответ размонтированного компонента не обновляет состояние/кэш.

## Eurostat: фактическое покрытие и дальнейший план

Найден официальный JSON-транспорт **того же действующего календаря**, используемый его страницей:
[release calendar](https://ec.europa.eu/eurostat/news/euro-indicators/release-calendar?type=listMonth),
`/eurostat/o/calendars/eventsJson?start=...&end=...&theme=0&category=2`.
Read-only проверка дала HTTP200 и поля recordid, period, datasetCodes, title, euroindAuthor.
Например, запись22494472 указывает Retail trade, September2026, sts_trtu_m, 06.11.2026.
JSON **заменяет один прежний iCal-запрос**, не добавляется вторым. Окно запроса ограничено прошлым14/
будущими120 днями. Дневное время all-day записей остаётся11:00 Europe/Luxembourg, с CET/CEST.

| Уже поддерживаемый показатель | После PR | Почему / дальнейшее бесплатное исправление |
|---|---|---|
| Безработица EA | Автоматические actual/previous при наличии period и une_rt_m в календаре, точной серии/географии/единиц/SA в API | Без выбора последнего месяца. [Выпуск30.10.2026](https://ec.europa.eu/eurostat/en/web/products-euro-indicators/w/3-30102026-bp) отдельно подтверждает September2026; этот один проверенный fallback для старого iCal сохранён в коде |
| Розничная торговля EA | Автоматические actual/previous по period и sts_trtu_m в официальном календаре | VOL_SLS, G47, SCA, PCH_PRE, monthly. Нет пересчёта по близости даты. [Выпуск06.10.2026](https://ec.europa.eu/eurostat/web/products-euro-indicators/w/4-06102026-ap) подтверждает August2026 |
| HICP flash | Новые факты из общего latest-only набора не записываются; старые сохраняются | API может уже содержать final/revised. Нужен разбор конкретной официальной flash-публикации/проверенный vintage, не текущего общего ряда |
| GDP preliminary flash | Новые факты временно пусты; старые сохраняются | Подтверждение квартала в календаре не доказывает preliminary vintage числовой таблицы |
| GDP flash с employment | Аналогично, отдельная стадия | Не подменять поздней/final оценкой и не объединять с preliminary |

Для последних трёх следующий бесплатный путь: сопоставить официальный release record с канонической
публикацией Euro indicators, извлечь период/стадию и значения именно её таблицы; сохранить ссылку,
дату версии, единицы и доказательство сопоставления. Затем заменить соответствующую существующую
загрузку, либо повторно использовать уже загружаемые официальные метаданные, **без добавления polling**.
Если потребуется дополнительный HTTP-запрос/другой транспорт, представить отдельный небольшой план
владельцу. Не оставлять их исключёнными из roadmap и не покупать данные ради этого этапа.

Это не «вся Европа без фактов»: регулярные unemployment/retail сопоставляются автоматически через
официальные period/datasetCodes. При временном отсутствии значения именно за этот период факт
остаётся пустым до следующего разрешённого запроса. Расписание/существующие цифры не удаляются.
UI не показывает технических диагностик; закрытый market_feed_runs фиксирует конфликт.

## Ограничения, которые важно понимать

- Не обещаем доказать свежесть там, где её источник не сообщает. Конфликтующие BLS/EIA/Census
  значения без достоверного номера/времени версии сохраняются как диагностический конфликт,
  а подтверждённая цифра остаётся. Совпавший ответ позволяет зафиксировать baseline; это не разрешение
  перезаписывать его следующим неподтверждённым изменением. Census также сохраняет ограничения #149.
- Поздние пересмотры ищутся в уже полученном payload при обычном due-запросе, включая сохранённые
  released события за90дней. Это **не** дополнительные ежедневные запросы ради пересмотров.
  EIA отдаёт ограниченную историю, DOL только текущий release+revised previous; невидимые старые vintages
  из них не восстанавливаются. Annual historical archive не реализован.
- Eurostat JSON сейчас не сообщает SEQUENCE/LAST-MODIFIED/STATUS. Его recordid даёт устойчивую
  идентичность и period, но не доказательство порядка конфликтующих расписаний. Если нет достоверной
  версии, изменение уже сохранённого времени/отмена удерживаются с конфликтом до проверки.
  Parser поддерживает явные поля версии/статуса, если они присутствуют. Нельзя считать исчезновение отменой.
- Старые дубли и неоднозначные строки автоматически не объединяются. Неоднозначный matching не
  создаёт третью копию, а выдаёт конфликт. Старые потенциально неверные значения без provenance
  перечисляются отдельным запросом для проверки, не удаляются и не обнуляются.
- Новый collector до0012 сохраняет чтение сайта, но операции с новыми колонками/RPC fail closed;
  ошибки изолированы по источникам. Автоматического fallback к небезопасной прямой записи нет.

## Ручное применение 0012 владельцем

1. Проверить diff, зелёный CI и отсутствие другого занятого номера0012. Проверить собственный журнал
   SQL: история Supabase ранее была пустой при фактически применённых миграциях. Не запускать все
   старые pending migrations по признаку пустой history.
2. Сделать backup/export `market_events` и связей `market_news.event_id`. Выполнить
   `supabase/checks/0012_preflight.sql` **до применения** и сохранить результат. Он работает на старой
   схеме, показывает counts/fingerprint, точные дубли и возможные заполненные identity collisions.
   Если последняя выборка не пуста — остановиться и проверить, не установлена ли другая версия0012.
3. Сначала применить `supabase/migrations/0012_market_event_integrity.sql` в отдельной тестовой БД
   с копией событий. Миграция только добавляет шесть nullable полей и функции. Она не заполняет старые
   записи, не меняет ID/значения/hidden и ничего не удаляет. Частичный unique index касается только
   NOT NULL identity_key; у всех существующих строк поле остаётся NULL.
4. Повторить preflight: counts/факты/предыдущие значения/статусы/fingerprint должны сохраниться,
   если между замерами не было обычного сбора данных. Проверить `0012_status.sql`: columns_ready,
   writer_ready, rls_enabled, server_can_write=true; client_can_write=false.
5. Проверить тестовые сценарии по `supabase/tests/market_event_integrity.sql` **только на тестовой БД**;
   используемые реалистичные legacy fixtures и повторное применение также входят в test-migrations.mjs.
   Тестовый SQL не предназначен для production.
6. После собственного решения применить только0012 к рабочей БД и проверить preflight/status ещё раз.
   Затем развернуть одобренный код. Не менять cron; дождаться завершения старых invocations (route max60sec)
   и обычного следующего запуска. Старый collector не умеет новую защиту, поэтому не смешивать версии
   при итоговой проверке и не считать миграцию саму по себе включением новой логики.
7. Проверить закрытый `market_feed_runs`: успешные записи и явные conflicts. Однозначные legacy строки
   получают metadata при совпадающем расписании. ID сохраняются. Конфликтную строку не исправлять
   массовым DELETE/MERGE: сначала проверить official UID/период/стадию и согласовать точечное действие.
8. В календаре проверить actual/previous, перенос, отмену, возвращение во вкладку, RU/EN,360/1440 и фильтры.
   Запросы идут только к собственной БД. Новые колонки не требуются старому reader, дизайн не меняется.

Для отдельной проверки legacy provenance после миграции:
```sql
SELECT id, source, code, starts_at, actual, previous, reference_period, release_stage
FROM public.market_events
WHERE actual IS NOT NULL AND result_meta IS NULL
ORDER BY source, starts_at;
```
Это список «не доказано», не автоматическое признание цифр ошибочными.

SQL rollback с удалением новых metadata не предлагается: он лишил бы систему защиты. Возврат кода
не требует удаления новых колонок; решение об откате collector принимать отдельно, учитывая старую
прямую запись. Производственная миграция/merge этим агентом не выполняются.
